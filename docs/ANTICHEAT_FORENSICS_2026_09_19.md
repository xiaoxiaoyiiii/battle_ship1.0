## 6. 防作弊设计草案

漏洞链：**小号成本≈0（A） → 匹配可预测（B） → 结算无异常检测（C）**。

### 第一层：投降/快局结算降权（最便宜，先做）

- 投降发生在**第 1~2 回合且双方零有效攻击** → **完全不计分**（不算胜不算负）。
- 已有交火但局数过短 → 胜方得分**打折**（如 ×0.3）。
- ⚠️ **必须只有一份实现**：本项目死在"同一业务判断两份实现必然漂移"上（见 `CLAUDE.md` §10.1）。
  投降降权只能有一个入口（`_finalize_match` / `_ranked_settlement_allowed`）。

### 第二层：匹配规避

- 同 IP / 同 IP 段近期不匹配；
- 最近 N 局交手过的对手，冷却期内不再匹配；
- 同一 IP 只允许一个账号进匹配队列。

### 第三层：行为检测（治本，针对"1 回合六连沉"）

本项目的作弊**特征极其明显**，性价比最高的一条：

> **单回合内击沉对方全部船 + 对方零次有效攻击** → 高危信号。

正常对局不可能第 1 回合就 6 连沉（对方船位未知，要 6 发全中是极小概率）。
落地为「可疑对局」记录 + 累计阈值，**不自动处罚**，进人工复核队列。

### 第四层（可选）：账号关联

- 注册/进入排位时记录 IP 与 UA 指纹 → `account_links` 表；
- 同一 IP 下多账号在排位中互相交手 → 强信号；
- ⚠️ **只做关联分析，不自动封禁**，避免误伤网吧/校园网/合租等共用出口。

### 7.5 ★ 实施教训（写给下一个改这段的人）

1. **判据的输入必须来自同一套 id 空间**。
   第一版 `sweep_perfect_win` 拿 `matches.winner_id`（**user_id**）去对齐日志
   `detail.attacker`（**socket sid**）—— 两套 id 永远不相等 → 在已知 166 局作弊上
   **召回率 0%**，而 26 条单测**全绿**。
   → 改用**位置无关的形态特征**（本局只有一个玩家命中过 + 命中数 == 对手船数）。
   **教训**：单测全绿不等于规则有效，**必须在真实标注数据上量召回率**。

2. **"未知"不能退化成"满足条件"**。
   回合数取不到时默认 `0`，而判据是 `rounds <= 1` → 老格式日志全被误判成"第 1 回合"。
   → 未知一律用 `-1`，判据写 `0 <= rounds <= 1`。

3. **规则要区分"规则允许的行为"**。
   `zero_engagement_loss` 最初把"投降且零命中"也算成"不还手"，
   导致打了 4 回合才认输的正常玩家被判 `record`。→ 投降局对该条豁免。

4. **反作弊必须失败开放**：判据抛异常 → 放行正常结算。
   宁可漏一局，不可把正常玩家的对局结算搞崩（已写进 `test_assess_failure_does_not_block`）。

5. **清历史 ≠ 治本**：§7.3 已证明刷分会随清理而迁移（新建小号）。

6. **CLAUDE.md §11.12 的公告规矩是有守卫的**：`changelog.py` 的条目必须以
   `修复了/改了/新增了/优化了/调整了` 开头（`tests/test_changelog.py` 钉死）。
   写"清理了…"会被测试拦下 —— 守卫有效，别绕过。

## 8. 匹配规避（2026-09-20 已上线）

### 8.1 设计：**软规避 + 硬兜底**

规避规则天然与"尽快配对"冲突。深夜只有两个人在线、而他们恰好刚打完一局 /
恰好同 IP（同一个宿舍）时，**硬性规避 = 两个人永远配不上**，
表现为"点了匹配没反应" —— 这比刷分更伤正常玩家。

所以分成三档（只在 `match_guard.py` 一处实现）：

| 档位 | 规则 | 后果 |
| --- | --- | --- |
| **硬拦** | ① 同一账号（多标签页）② 同 IP **且该 IP 两个账号都脏** | 绝不配，一直等 |
| **软规避** | 同 IP、近来交手过的对手 | 有更好的选择时躲开 |
| **兜底** | 队列里只剩软规避的对象可配 | **仍然配**，但 `room.ranked=False` → 该局**不结算排位分** |

兜底那条是整个设计的关键：**能开局，但刷不到分**。想拿分就等第三个人出现。

优先度用打分（`pair_score`）：基准 1000，同 IP −400，近来交手 −300，
同 IP 且脏 −10000（等于不配）；等待时间每 10 秒 +1（避免有人被反复让位而一直排不上）。

调参集中在 `match_guard.py` 顶部：
`RECENT_OPPONENT_COOLDOWN_SEC = 1800`（30 分钟）、`RECENT_OPPONENT_LOOKBACK = 8`。

### 8.2 ★ 上线过程中撞出来的事故（最重要的一条教训）

**同 IP 规避一作用于回环地址，排位分会被静默全部关掉。**

- 现象：`tests/test_ranked_match.py` 整片变红（21 个用例），断言变成 `5 == 0`。
- 根因：测试夹具里两个客户端都是 `127.0.0.1` → 判成"同 IP" → 降权 → 兜底 →
  `room.ranked = False` → **排位分不结算**。而页面照常开局、接口照常返回、
  **零报错**，只是分数不动。
- 影响面：**任何本机 / 局域网 / 内网部署**都会中招，线上若走反代也会。
- 修法：`_usable_ip()` 把回环 / 私有 / 链路本地 / IPv4-mapped 地址**一律归一成"没有 IP"**，
  于是天然放行。只有**看起来像公网**的地址才参与同 IP 规避。
  判定刻意保守 —— 宁可漏判（少数人共用出口刷分，仍由 `anticheat` 在收益侧兜住）。

> 教训与 CLAUDE.md §10.13 同源：**"看着有、其实永远不触发"** 的反面 ——
> 这次是**"看着在拦，其实把正常功能一起关掉了"**，而且**不报错**。
> 守卫：`tests/test_match_guard.py::test_loopback_ip_treated_as_no_ip`。

### 8.3 另一个教训：装饰器之间**不能插函数**

加 `_client_ip()` / `_recent_foes()` / `_dirty_ips()` 时，我把它们写在了
`@socketio.on('find_match')` 与 `handle_find_match` **之间** ——
装饰器于是把 `_client_ip` 注册成了 `find_match` 的处理器，
调用时抛 `TypeError`（handler 参数对不上），**37 个用例全红**。
→ 新增辅助函数一律放在**装饰器之前**，或至少别插进"装饰器 + 它的函数"之间。

### 8.4 实现要点

| 文件 | 作用 |
| --- | --- |
| `match_guard.py` | **纯函数**：硬拦 / 打分 / 取对 / 是否结算（唯一一份规则） |
| `server.py` `_client_ip` | 取对端 IP。**只信 `remote_addr`，不读 `X-Forwarded-For`** |
| `server.py` `_recent_foes` | 该账号最近 8 局的对手（读 `matches`） |
| `server.py` `_dirty_ips` | 脏 IP 集合。**当前恒返回空集**（见下） |
| `server.py` `_mk_candidate` | 队列条目 → `Candidate` 的**唯一转换入口** |
| `server.py` `handle_find_match` | 改用 `match_guard.pick_pair` 配对 |

**IP 只存内存、不落库**：`match_queue` 条目上加了 `ip` 与 `enqueued_at` 两个键，
匹配完即随条目丢弃。**没有新增任何 IP 持久化** —— 采集 IP 是隐私决策，
要先写进隐私说明，本批刻意不做。因此"脏 IP 硬拦"这条规则**暂时不会触发**，
但线已接好：将来落库后只需在 `_dirty_ips()` 里补一条查询。

**只信 `remote_addr`**：线上实测确认**没有 nginx / 反代**（`run_prod.py` 直接
`0.0.0.0:5000`），所以 `remote_addr` 无法伪造；`X-Forwarded-For` 是纯客户端可写的头，
信它等于把规避规则交给攻击者。将来加了反代必须显式改并确认代理覆写。

## 10. 累计嫌疑度 + 阶梯封禁 + 管理后台（2026-09-20 已上线）

### 10.1 三层判据，别混

| 模块 | 判什么 | 输出 |
| --- | --- | --- |
| `anticheat.py` | **一局** | 单局嫌疑度（0~100+），`blocked` 则不给排位分 |
| `suspicion.py` | **一个人** | 累计嫌疑度 → 封禁等级 0~3 |
| `match_guard.py` | **怎么配对** | 同 IP / 近来对手规避（§8） |

累计的意义：单局判据再准也只能"不让这一局给分"——对方换个小号继续。
**真正拦得住的是累计**：一个人反复出现在可疑对局里，本身就是信号。

### 10.2 算法

```
累计嫌疑度 = Σ (单局嫌疑度 / 5) × 0.5^(距今天数 / 14)
```

- **折算系数 5**：约 5 局 `block` 档才到第一档封禁 —— 给误判留足容错。
  正常玩家即使有 10 局被误判成 `record`(30)，累计也只有 60 < 100，**不会被封**。
- **半衰期 14 天**：两周前的作弊权重减半，四周后 1/4。
  **人不该永远有罪** —— 这是"封禁可逆"的机制保证。
- **衰减有下限**（`DECAY_FLOOR = 1e-6`）：不许因为太久远就完全抹掉记录。
  （实测撞出来的：`0.5 ** (age/14)` 在 age≈1e5 天时会下浮成 0，与其依赖浮点
  精度碰巧不为 0，不如给个明确下限 —— 让这条性质是**设计出来的**。）
- **累计上限 1000**：防止展示出天文数字。

### 10.3 阶梯封禁

| 等级 | 阈值 | 后果 |
| --- | --- | --- |
| 0 | < 100 | 正常 |
| 1 | ≥ 100 | **禁排位**（休闲照常） |
| 2 | ≥ 200 | **禁匹配**（排位 + 休闲都禁） |
| 3 | ≥ 300 | **禁房间**（建房 / 进房都禁） |

能力逐级收紧且是**包含**关系，只有一份"最高允许等级"表
（`suspicion._CAP_REQUIRED_MAX_LEVEL`）—— 不做两套判断，避免白/黑名单有交集。

⚠️ **等级一律由嫌疑度推出来，绝不单独存**（与 `user_xp` 只存 xp 同一条理由）：
存两个字段迟早出现"嫌疑度降了但封禁还在"这种对不上的状态。
**唯一例外**是管理员手动干预 —— 那是人的决定，必须持久化。

### 10.4 管理员后台（只给站长用）

接口（`api.py`，全部先过 `_admin_required()`）：

| 接口 | 作用 |
| --- | --- |
| `GET /api/admin/me` | 我是不是管理员（前端据此显示入口） |
| `GET /api/admin/suspicion?limit=N` | 全服嫌疑度列表（降序）+ 等级定义 + 阈值 |
| `GET /api/admin/player/<uid>` | **单玩家完整报告**：嫌疑度 / 封禁等级 / 战绩 / 违规记录 / 干预历史 |
| `POST /api/admin/player/<uid>/override` | 手动处置：`{cleared:true}` 解封 或 `{level:0..3}` 指定等级 |
| `GET /api/admin/player/<uid>/history` | 干预历史（审计） |

**安全边界（三重，缺一条都是事故）：**
1. **复用既有的 `DEBUG_ADMIN_USER_IDS`**（env，线上已配你的 uid），
   **不新造第二套管理员概念** —— 两套必然漂移。
2. **白名单为空 = 谁都不是管理员**（默认安全）。绝不能写成"空就放行"。
3. 前端隐藏**不是**安全措施 —— 门禁在服务端，非管理员一律 403。

**前端入口**（`static/admin.js`）：
- 设置面板里多一个「🛡️ 反作弊管理」；
- **在个人信息卡上点「查后台」** → 直接跳到那个人的管理详情（就是"点头像快速查询"）。
  普通玩家**一个请求都不发**（`isAdmin()` 为 false 直接返回）。

### 10.5 ★ 实施中撞出来的两个坑

**① 注入清单不是改名映射（实测踩了）。**
`register_friend_backend(module, **names)` 里的 `**names` 只是**校验清单**，
真正的查找用**调用方传的名字**去 `getattr`。我最初写成
`admin_user_ids='_admin_user_ids_for_api'`（当成别名映射）→
`getattr(module, 'admin_user_ids')` 拿到 None → 白名单恒为空 →
**管理员自己也进不去**。且**不报错**，只有 403 和 6 个红测试。
→ 键必须等于真实函数名。

**② 环境变量只在 systemd 里，不在你的 shell 里。**
命令行直接跑脚本时 `DEBUG_ADMIN_USER_IDS` 是 None → `is_admin` 恒 false。
生产是 `systemd` 注入的，所以**线上正常、手测假红**。
验收脚本要带上 env 再跑，别据此判断"功能坏了"。

## 12. 隐私说明（做 IP 关联前必读）

**IP 属于个人信息**，《个人信息保护法》下收集需**告知并取得同意**；
用它做画像并对玩家采取措施，还可能触发第 24 条（自动化决策的说明与拒绝权）。
当前注册页**没有任何告知**，站点又是裸 HTTP。

**本项目已刻意避开这一点**：累计嫌疑度**只依据对局行为**（回合数、击沉数、
时间戳、账号 id），**没有采集任何新个人信息** —— 所以现在这套不需要隐私告知。

若将来要上 IP 关联，最低限度四条：① 注册页明确告知；② IP 加密存储 + 限期删除；
③ 只做标记、不自动处罚；④ 绝不把 IP 或关联关系透露给任何玩家（含申诉答复）。
