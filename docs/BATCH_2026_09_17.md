## 一、对局逻辑

### 1. 冻结：攻击次数被多扣一次；播报把死船也算进去（#2 #7）

**现象**：「冻结通过之后被冻结方的攻击次数计算出现问题」「冻结的战舰数目居然会把
已经死亡的战舰加进去」。

**根因**（同一个）：本项目的「击沉」**不把船移出 `player.ships`**（沉船留在列表里供
复活类卡回收），而这两处都按 `player.ships` 全量统计：

- `frozen_ship_count(player)`（`server.py`）→ 攻击次数 = `remaining_ships - frozen_ship_count`。
  `remaining_ships` 已经把沉船排除在外，死掉的那艘被**重复扣一次**：
  冻住 3 艘、其中 1 艘后来被打沉 → 期望 5-2=3，实际 5-3=2。
- `冻结` 分支的 `frozen_count` → 区域内**已经沉掉**的船也计入播报数字。

**修法**：

- `frozen_ship_count` 改走 `_alive_ships(player)`（`_is_ship_alive` 同时看沉船堆与命中数）。
- `冻结` 分支在打标记前 `if not _is_ship_alive(opponent, ship): continue`。
- 新增 `_thaw_ship()`，并在**复活**路径（`_revive_sunken_ships` / 死者苏生 /
  神机妙算重新部署）一并调用：沉船带着上一轮的 `frozen` 复活会继续被算进冻结数，
  等于凭空少一次攻击。（大回合推进的解冻循环只扫 `player.ships`，
  被轰炸/硫磺火焰移出列表的船会漏掉。）

**验证**：`tests/test_batch_2026_09_17_fixes.py`（4 条）+ `tools/e2e_batch_2026_09_17.py` V3。

### 2. 败者食尘：进战斗阶段后攻击次数又被算回 6（#3）

**现象**：「准备阶段的攻击次数确实归 0，但进入战斗阶段之后又根据船数更新成了 6 次」。

**根因**：卡面第二句「生效的大回合内双方的攻击次数都为 0」原先只在**放置完成**时写一次
（`handle_place_ships` 的 `polar_reversal_applied` 分支），而 `enter_battle_phase` 会无条件
调 `_recalc_attacker_attacks`（那是"按当前场地规则重算次数"的唯一权威实现）——直接覆盖成 6。

**修法**：新增**大回合级**判定 `_attacks_forced_zero(room)`
（`game_effects['zero_attacks_round'] == room.round`），三个会写 `attacks_remaining` 的收口
一律先过它：`_recalc_attacker_attacks` / `_sync_attacks_after_ship_change` /
`_apply_last_stand_attacks`；`enter_battle_phase` 里的五险一金触发也跳过
（否则它会把 0 回填成 3，等于当场把这个 0 抹掉）。标记写在 `room.game_effects = {}`
**之后**（那一行会清空房间级效果），进入下一个大回合时 `round` 变化自然失效并顺手 pop。

`polar_reversal_applied` 保留（放置完成时仍然置 0），是双保险。

**验证**：5 条 pytest（含"下一个大回合恢复正常"与两条"不许回填"的反证）+ 现场 e2e。

### 3. 越战越勇：发动当场就要 +1（#4）

**现象**：「成功使用之后应该立即给使用方增加一次攻击次数，而不是之后的攻击才开始生效」。

**根因**：`apply_magic_effect` 的越战越勇分支只置 `battle_spirit` 标记，+1 发生在
**下一次击沉**时（`_apply_attacker_damage_buffs`）。发动前提本身是"刚击沉了一艘"，
那一艘的 +1 拖到下一发才给，玩家看到的是"打完这张牌次数没变"。

**修法**：新增 `_grant_extra_attacks(room, player_id, n)`（教皇旨意 / 败者食尘生效时返回 0，
否则加次数并广播 `attacks_updated`），越战越勇置标记后立刻调用它。
同时把这张卡加进 `_last_attack_requirement_reason`：没有刚击沉就**在扣牌之前**拒绝
（卡面「否则无效」，与饮血同口径，牌留在手里）。

**验证**：3 条 pytest + 现场 e2e V2（真实击沉后发动，`5 → 6` 并收到 `attacks_updated`）。

### 4. 条件不满足却把牌吞掉（#5）

**现象**：「一部分卡牌因为不满足使用条件而被打出时，虽然效果没有生效，但是却把牌直接
吞掉了。应该是给使用方弹出广播说明不满足某某使用条件，然后并不会被消耗掉这张牌」。

**根因**：`handle_use_magic_card` 是**先扣牌进弃牌堆、再压连锁**，而一大批卡的条件要到
`apply_magic_effect` 结算时才判 —— 那些分支一律 `result['success'] = False; return result`，
`resolve_chain` 从不退还。涉及死者苏生/疗愈（没有沉船）、绝处逢生（<3 艘）、
神之宣告（<2 艘）、平等条约（没有船数变化）、余音绕梁（不在准备阶段）、
桃园结义（撞上无中生有）、缺目标的区域卡、失灵！/加百列之光（没有可无效化的目标）等
（全文件 38 处失败分支）。

**修法**：新增 `_refund_card_to_hand(room, player_id, card, result)`，在 `resolve_chain` 里
`apply_magic_effect` 返回后调用（`success=False` 且未被康）：

1. 卡已按**同一引用**在手牌 → 不动（防造牌）；
2. 按同一引用从 `magic_discard` 移除并 append 回手牌；
3. 找不到且是场地卡、且没贴在场 → 补回手牌（场地卡出牌时不入弃牌堆）；
4. 其余（如已被盗亦有道从弃牌堆偷走）→ **不补**，只记日志。
5. 成功退还时向施法者 `emit('message')`「X 未发动：<原因>，卡牌已退回手牌」+ 一条对局日志。

**安全性论证**（逐条核对 38 处）：没有任何一处是"先产生副作用再置 False"，全部是分支入口
直接 `return`；失败卡也不写 `magic_history`（`resolve_chain` 只在 success 时 append），
因此不影响失灵！/盗亦有道的"上一张卡"读取。被康的项在 `continue` 之前就返回了，天然不退还
（有反证测试）。

**明确不做**：`record_card_use` 仍在入链时刻计数（"打出过"的口径不变）；放置流程中途
「放弃」仍按既有约定作废（`cancel_placement` 不退还）——本次只处理"根本不满足条件就被吞"。

**验证**：9 条参数化 pytest + 2 条反证（正常发动仍消耗 / 被康不退还）+ 现场 e2e V1。

### 5. 死者苏生：能把船摆到"刚沉掉的那一格"（#6）

**现象**：「使原本沉船的那个格子恢复成未知格子，且在复活的选船位置界面那个原本沉船的
位置也是可选的」。

**根因**：占位检查只扫 `player.ships`，而**轰炸 / 硫磺火焰 / 牺牲**会把船从 `ships` 里
`remove()`（只留在 `sunken_ships`）。这些格子于是被当成空格 → 面板亮成可点；
点下去 `_clear_attacks_on_cells` 会清掉对方打在那格的攻击历史，那一格对对方就"变回未知"。
卡面写的是「摆放在对方没有打过的格子上」。

**修法**：新增 `_own_occupied_cells(player, ignore_sunken=False)`（`ships` ∪
`sunken_ships`），`_placement_error` 与 `_placement_blocked_cells` **共用**它
（这两份独立实现此前已漂移过一次）。`ignore_sunken=True`（神机妙算的"重新部署"）
语义不变 → 原位置仍可放，有专门的回归测试守着。

**验证**：3 条 pytest（含神机妙算反证、原沉船格攻击历史不被顺手清掉）。

### 6. 回光返照：清错了数组（#8）

**现象**：「没有正确清空使用者的棋盘，原本被打过的或者沉船的格子仍然会显示在使用者的
棋盘上」。

**根因**：清的是 `caster.attacks`，但两个数组是**不同坐标空间**：

- `caster.attacks` = 我打在**对方**棋盘上的格子（与本次重摆无关，清掉反而会让已探明的格子
  重新变成可打 = 白赚一炮）；
- `opponent.attacks` = 对方打在**我方**棋盘上的格子 → 卡面「也会清空对方视角中自己的棋盘」
  要清的正是它。

**修法**：改清 `room.players[opponent_id].attacks`，随后 `_emit_board_attacks(room)` 重推
（前端那两个列表是本地缓存，不重推会继续画着 ✕）。`revealed_positions` 的清理保留。

**验证**：2 条 pytest + 现场 e2e V4（`opponent_attacks == []` 且 `my_attacks` 仍有 1 条）。

## 二、UI

### 7. 仁王之盾改成"在自己棋盘上点船"（#1）

- 旧实现弹一个「选择船 1 (3,4) / 选择船 2 …」按钮列表，玩家得在坐标里猜哪艘是哪艘。
- 改为与克苏鲁之眼同一套交互：**在自己棋盘上点绿色高亮的战舰格**，再点一次取消，
  至多 3 艘，「确认 / 取消」。沉船格灰掉（服务端也会跳过），空格不可点，
  选择数实时显示，第 4 艘给出 toast 提示。取消会发 `cancel_magic_selection`
  释放服务端的待选择状态（否则 `magic_temp_data` 一直挂着 `shield_choice`）。
- `ship_indices` 仍按 `player.ships` 的**原始下标**回传（服务端契约不变）。
- 验证：`tools/renwang_board_check.mjs`（21 项，含沉船格反证、上限拒绝、取消路径）。

### 8. 连锁弹窗：对方发动的那张卡可预览（#9）

- 标题里的卡名做成可交互锚点（`.chain-request-card-ref`）：桌面悬停出效果浮层，
  触摸设备点一下出详情小窗；**点它不会发出任何 socket 事件**（不等于响应连锁）。
- 卡面数据取前端 `lookupCard()`（`window.magicCards` 41 张全量），服务端 payload 不用改。
- 验证：`tools/chain_preview_check.mjs`（25 项，含"点卡名零 emit"、触摸分支、
  以及"原有点卡出牌逻辑未被抢走"）。

### 9. 个人信息详情 + 排行榜头像/跳转（#10 #11）

- `db.get_user_rank(uid)`：与 `_get_leaderboard` 同排序口径（`wins DESC, longest_streak DESC`，
  只统计真打过一局的账号），用 `COUNT(*)` 算严格在前的账号数 —— **榜外账号也拿得到名次**。
- `/user_stats` 增加 `rank` 字段（`public_fields` 已含 `avatar` / `signature`）。
- 前端一份渲染三处复用：`buildProfileHead()`（头像 / 用户名 / 个性签名 / 第 N 名）+
  `buildStatsTable()`（名次 / 胜负 / 胜率 / 连胜）+ 历史战绩（仍可点开对局详情）。
  首页「个人战绩」、对局内「查看对手战绩 / 点右上角对手头像」、排行榜点名字都走
  `showUserProfile()`。
- 排行榜「玩家」列显示头像（没设头像回退默认图），头像与名字整体是一个可点按钮。
- 顺带修掉两处**静默失效**：`#show-opponent-stats` 按钮与右上角头像容器原先引用的是
  裸标识符 `showOpponentStats`，而它要等 `game_state` 处理器跑过才有定义 ——
  早期点击直接 `ReferenceError`，弹窗永远出不来、没有任何提示。
- 验证：`tools/profile_leaderboard_check.mjs`（25 项，含"精简数据不抛异常"的工具兼容守卫）
  + `tests/test_db_core.py` 3 条 + `tests/test_profile_rank_api.py` 3 条。
