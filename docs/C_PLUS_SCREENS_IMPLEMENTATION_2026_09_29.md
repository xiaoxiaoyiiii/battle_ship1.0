# C+ 周边屏幕实施方案

状态：**已实施（2026-09-29）**。本文是方案与验收口径；实施记录、逐屏与原型不同的理由、
门禁结果在 `docs/C_PLUS_SCREENS_REPORT_2026_09_29.md`，基线/差异/状态映射表在
`docs/C_PLUS_BASELINE_2026_09_29.md`。基于现有 C 竞技场与 `docs/ui_demos/arena-suite.html`
的十屏原型。与本文不同的一处（作用域**不绑主题预设**，见实施记录 §5.1）。

## 1. 目标与范围

将大厅、好友房、布船、图鉴、排行、档案、结算、观战、回放、设置统一为 C+ 风格：深蓝面板、紫色主操作、金色段位、清晰的信息分区。复用既有业务能力和服务端状态；本轮不重做已实现的首页和对局主屏。

原型是视觉和交互参考，不是生产实现。禁止直接引入 `arena-suite.js`、离线卡表、示例数字或示例计时器。现有游戏状态、接口、Socket 事件、卡牌规则仍为唯一数据来源。

## 2. 产品结构决策

- 原型十屏侧栏、页面编号、设计说明和前后屏切换只用于选稿，不进入正式游戏。
- 大厅、图鉴、排行等常规入口沿用正式导航。布船、结算、观战、回放按真实业务流程进入，不能通过导航绕过状态限制。
- 名片查看与个人资料编辑继续分开；保留现有四类查看入口及对局历史，不把查看界面塞进编辑弹窗。
- 设置沿用原入口与持久化机制；桌面采用分组双栏，手机采用纵向面板。保留原有壁纸、音效、观战和回放权限等项目。
- 宽屏优先复现 C+ 的层次和排列；手机按任务适配。图鉴、排行、设置允许内容滚动；实时对局沿用已有紧凑布局契约，不能照搬原型长页面。
- Demo 中的“双方准备”是演示交互。先核对正式房间状态机，按现有建房／入房／开局机制展示；不因 UI 改版新增握手协议。

## 3. 逐屏落地要求

| 屏幕 | 采用的设计 | 必须接回的真实行为 |
| --- | --- | --- |
| 大厅 | 房间卡片、状态筛选、搜索、加入区 | 真实房间状态、订阅与退出、房满／失效反馈、公屏与已有好友能力；不能用首页访问代替大厅订阅 |
| 好友房 | 双方席位、房号、邀请区、规则摘要 | 建房、加入、邀请、退出／解散和失效状态；按钮由真实状态驱动 |
| 布船 | 带坐标的海域、六艘计数、随机／清空、明确确认 | 6 艘单格船、取消放置、重复提交保护、断线恢复；确认提交真实船位 |
| 图鉴 | 可筛选卡牌网格、桌面详情栏、手机大卡详情 | 复用正式卡组件、完整效果文案与真实卡表；保留同名卡的现有语义，不另维护离线副本 |
| 排行 | 前三名展示、榜单、自己高亮 | 按接口实际支持的指标提供排序；保留分页、游客、加载／空态与档案入口 |
| 档案 | 指挥官名片、数据、荣誉、历史 | 真实战绩与解锁条件；编辑仅限本人；佩戴成功后刷新所有名片入口，失败可恢复 |
| 结算 | 胜负主视觉、积分、经验、数据与后续操作 | 服务端结果、平局／投降／掉线等原因、休闲／人机／排位差异、奖励展示与重连恢复 |
| 观战 | 双海域、公开战报、清楚的退出入口 | 复用净化后的观战快照；保留场地、连锁、观众列表、聊天与权限变化；不暴露隐藏船位或手牌 |
| 回放 | 双海域、时间轴、事件列表、播放控制 | 保留帧计算、船位／手牌／状态／重置时间线、1×／2×／4×、来源与截断提示、键盘操作、权限错误 |
| 设置 | 分类设置与即时视觉预览 | 按已有存储渠道保存；服务端权限以返回值为准；音量接真实音频模块；新增高对比／减少动效需覆盖真实组件 |

所有屏幕补齐：加载、空数据、请求失败、权限不足、内容过长、窄屏状态。没有真实来源的数值暂不展示。

## 4. 实施顺序与交付批次

### P0：确认基线与接口映射

记录当前工作区改动、目标屏截图和现有测试结果；逐屏登记 DOM id、事件监听、数据来源、加载与销毁逻辑。核对旧文档与当前代码，以当前行为为准。保留已完成的 C 首页／三区对局和用户其他未提交修改。

交付：差异清单、状态映射表、回归基线。遇到原型缺少的正式能力，先补进布局设计。

### P1：公共样式 + 图鉴（首个可评审版本）

提取页面标题、面板、筛选栏、状态标签、详情栏、加载／空态和移动抽屉样式，接入现有设计令牌。以图鉴作为端到端样板，验证卡面复用、长文案、搜索、筛选及移动详情。

验收：同一真实卡在手牌、图鉴与预览中的名称／类型／速阶一致；手机能阅读完整效果；无页面横向溢出、重复事件绑定或 ID 冲突。

### P2：排行 + 档案 + 设置

统一信息展示与个人设置，保留查看／编辑边界、现有入口和权限。增加原型中选定的可读性选项时，明确保存范围与默认值。

验收：排行榜查档案、本人编辑、徽章保存、跨入口刷新、刷新后的设置恢复均正确；无效请求有反馈。

### P3：大厅 → 好友房 → 布船

重排实时入口流程。所有席位、可用操作与等待文案绑定服务端状态；用两个真实浏览器走完整创建、邀请、加入、部署与开局。

验收：六艘上限、重复点击、房间失效、对方离开、断线恢复均不产生错误状态；桌面矮屏可见部署确认；手机触摸操作可用。

### P4：结算 → 回放 → 观战

先接真实结算与回放入口，再重排回放和观战。复用既有 `replayComputeFrame` 等数据处理，保持可见性规则和事件顺序。回放侧栏容纳真实手牌／状态信息；移动端通过抽屉或分页保留这些内容。

验收：至少覆盖胜／负／平或异常结束、休闲与排位、卡牌伤害、船位变化、棋盘重置、回放拖动与倍速、退出后计时器销毁，以及观战权限与隐藏信息不变量。

### P5：整体验收与逐批启用

跨屏验证从首页到大厅、部署、对局、结算、回放、返回首页的完整路径。校准配色、间距、焦点、触摸区及弹层层级。每批独立提交、独立验收，通过后再将对应屏幕设为默认。

## 5. 代码组织与兼容策略

- `templates/index.html`：只调整目标屏容器和布局类，保留被 JS／测试使用的 id。检查直接子选择器、fixed 后代与弹层挂载位置。
- 建议新增 `static/arena_screens.css`：用 `arena` 预设和目标屏根类限定作用域，复用 `style.css` 令牌；不把几千行原型 CSS 原样追加到公共样式。
- `static/game.js`：保留状态与事件链，仅调整渲染、筛选、详情选择、进入／退出收尾。局部复杂逻辑可拆模块，但不把全项目重构列为前置条件。
- `static/adaptive_layout.js`：只有实际涉及紧凑布局时才调整，避免周边页改变主对局布局判据。
- 后端 `api.py`、`server.py`、`spectate.py`、`replay.py`：先复用现有能力；发现确实缺少的字段后，单列接口变更与测试，不为示例数字扩表。
- 原有主题预设继续工作，明暗模式都验证。布局选择与颜色预设分开，避免破坏现有主题契约。

按屏设置开发期启用开关，例如 `data-arena-screens="v2"` 与屏幕列表，用于比较和快速回退；不向玩家展示选稿开关。优先保留一套带原 ID 的 DOM，CSS 可回到旧布局，避免复制整屏导致重复监听。若某屏的 DOM 变更无法通过开关恢复，明确采用回退该批提交。

## 6. 验证清单

| 范围 | 复用的验证入口 |
| --- | --- |
| 公共 DOM／主题／布局 | `dom_contract_check.mjs`、`fluent_style_check.mjs`、`fluent_css_metrics.mjs`、`ui_layout_check.mjs` |
| 图鉴／长文案 | `codex_realcard_check.mjs`、`card_text_fit_check.mjs` |
| 排行／档案 | `profile_leaderboard_check.mjs`、`profile_card_check.mjs`、相关 pytest |
| 大厅／布船 | `lobby_check.mjs`、相关布船规则测试、双客户端端到端流程 |
| 观战 | `spectate_check.mjs`、`dom_spectate_frame_check.mjs` |
| 回放 | `replay_check.mjs`、`dom_replay_frame_check.mjs` |
| 设置／音频 | `fluent_style_check.mjs`、`sfx_check.mjs`、`bgm_check.mjs` 与设置持久化检查 |

每批运行相关检查；整合结束再跑必要的完整回归。结构重排导致旧坐标断言失效时，按新的产品契约更新具体断言并记录原因，保留遮挡、可操作性和状态正确性检查。

视口：1440×900、1280×720、390×844；涉及紧凑交互时追加 320×568 和横屏 664×336。原型已做的 30 张截图只证明示例页面表现，不能替代正式数据、Socket 与权限验证。

## 7. 建议落地口径

默认采用 C+ 的视觉；首批只交付公共样式与真实图鉴，作为其余屏幕的组件与验收样板。之后按 P2—P5 推进，每批给出真实截图、验证结果、剩余差异。需要与原型不同的部分在对应屏说明，避免为了逐像素复制而遗漏现有功能。
