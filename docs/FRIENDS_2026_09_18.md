# 好友功能（2026-09-18）

> 作者原话：「我们可以开始新增一个加好友的功能了……你把我当成产品经理，你来给我意见我来决定是否可以。」

## 0. 产品判断（先定方向，再定实现）

**这游戏的真痛点不是"缺社交"，是「匹配等不到人」**（全服十几个人，休闲匹配经常空转）。
所以好友功能的**第一价值是「把熟人叫上来打一局」**，不是关系链本身。
这条判断决定了本批的重心：**在线状态 + 一键邀战**优先，私信/动态/好友排行往后排。

### 作者拍板的 5 条（2026-09-18）

| 决策 | 选择 | 理由 |
| --- | --- | --- |
| 关系模型 | **双向申请-同意** | 「好友」语义清晰；不会被陌生人单向订阅 |
| 本批重心 | **一键邀战优先** | 直接对着"没人一起玩"这个真痛点去 |
| 最近对手一键加 | **做** | 本服人少、用户名难记，这是获得第一批好友的唯一现实途径 |
| 隐私默认 | **列表私有 + 任何人可申请**（设置里可关） | 不暴露社交关系；同时新玩家不会被"只能加同局的人"卡死 |
| 上限与限流 | **50 好友 / 每小时 10 次申请** | 远超本服需要，同时挡得住脚本刷申请 |

### 直接做的护栏（不需要拍板，属于技术/规则层面）

1. **好友对战永远走自定义房**，不给段位分、不计战绩 —— 沿用"自定义房不给分"的既有规则，从根上堵掉互刷。
2. **必须有账号**才能加好友/被加；游客只能收到邀请链接，不进好友列表。
3. 申请与接受**幂等**；拉黑后对方既不能申请也不能邀战。
4. **好友不额外豁免隐私开关**：对方关掉的区块（战绩/历史/最爱卡/段位）好友一样看不到。
5. 前端所有东西（列表、状态、上限）从服务端拿，**不在页面里写死**。

### 本批明确不做

私信/聊天（局内已有聊天）、好友排行、赠送礼物、组队/语音、观战、好友分组、备注名、好友动态流。

## 1. 数据层（`db.py`）

```sql
CREATE TABLE IF NOT EXISTS user_friends (
    user_id    TEXT,      -- 边的起点
    friend_id  TEXT,      -- 边的终点
    status     TEXT,      -- 'pending' | 'accepted' | 'blocked'
    created_at INTEGER,
    updated_at INTEGER,
    PRIMARY KEY (user_id, friend_id)
)
```

**有向边 + 三种状态**，语义按状态而定（这是本表唯一需要理解的地方）：

| 状态 | 存几条 | 含义 |
| --- | --- | --- |
| `pending` | **一条** | 发起方 → 对方；「我发出的」= 我起点的 pending，`我收到的` = 我终点的 pending |
| `accepted` | **两条对称边** | 接受那一刻同时写 A→B 与 B→A。「我的好友」只需 `WHERE user_id=? AND status='accepted'`，查询不用两向 OR |
| `blocked` | **一条** | 拉黑方 → 被拉黑方；写之前先把两向的 pending/accepted 边都清掉 |

索引 `idx_user_friends_user(user_id, status)`。

⚠️ **为什么不用"一条边 + 双向查询"**：那种写法每个读路径都要 `(user_id=? OR friend_id=?)`，
既写不对索引、又容易在某一处忘记反向 → 出现"单向好友"。对称边把复杂度挪到唯一的写点（接受）上。

### DAO（类方法与模块级同名包装成对存在）

`get_friend_edges` / `get_friend_ids` / `get_friend_relation` / `send_friend_request` /
`accept_friend_request` / `remove_friend` / `block_user` / `count_friends` / `list_friends` /
`list_incoming_requests` / `list_outgoing_requests` / `count_requests_since`。

`get_friend_relation(a, b)` 返回 `'none'|'self'|'friends'|'pending_out'|'pending_in'|'blocked_by_me'|'blocked_me'`
—— **一个函数给出前端要的全部关系**，避免前端自己拼（前端拼就必然有第二份规则）。

## 2. 在线状态：为什么单独开 `presence.py`

`server.py` 里原有的 `online_users` 存的是 **sid 不是 uid**，而且同一人开两个标签页会有两个 sid
（`/api/online_count` 还在用它，语义不能动）。好友需要的是**按 uid 的在线状态**，所以：

- **新建 `presence.py`：纯内存、零依赖** —— 存在的唯一理由就是**避免 `api.py` 导入 `server.py` 造成循环导入**
  （`server.py` 导入 `api.py`，反向依赖必须有别的地方放）。
- 维护 `uid → 标签页计数` 与 `uid → {sids}`：多标签页要计数（开两个页面不是两个人），
  且按 uid 推事件时要发到**全部** sid（否则用户在另一个标签页上收不到）。
- 另外维护 `in_game` 标记：好友列表要能显示「对局中」（这样"邀战"按钮就能给出正确的禁用原因）。

## 3. 实时事件（服务端 → 客户端）

| 事件 | payload | 时机 |
| --- | --- | --- |
| `friend_request` | `{from_user_id, from_username, from_avatar}` | 有人给**在线的**你发申请 |
| `friend_accepted` | `{user_id, username, avatar}` | 你发出的申请被接受 |
| `friend_invite` | `{room_id, from_user_id, from_username}` | 好友邀你打一局 |
| `recent_opponent` | `{user_id, username, avatar, relation}` | **结算时**给双方各发一次（「最近对手一键加」的数据来源） |

- 一律只在对方在线时发；`server.py` 提供 `push_friend_request` / `push_friend_accepted` / `push_friend_invite`
  三个函数，**都能在无请求上下文时安全调用**（`api.py` 会在 HTTP 请求里调它们）。
- ⚠️ `disconnect` handler 内**不能同步 emit**（会卡死 eventlet hub）—— `mark_offline` 是纯内存操作可以，
  但**不要**在那里 emit 任何东西。
- ⚠️ 结算钩子（`recent_opponent`）挂在 `_finalize_match`（唯一收口），并且对 `db.get_friend_relation`
  要**防御式调用** —— 少一个 DAO 也绝不能把结算搞崩。

## 4. 接口（`api.py`）

| 接口 | 说明 |
| --- | --- |
| `GET /api/friends` | `{friends, incoming, outgoing, limits, counts}` |
| `POST /api/friends/request` | `{username}`；过频 429、满员 400 |
| `POST /api/friends/respond` | `{username, accept}` |
| `POST /api/friends/remove` | `{username}`（双向删，幂等） |
| `POST /api/friends/block` | `{username}` |
| `POST /api/friends/invite` | `{username}` → 建房 + 推送给对方；不在线时明确报"对方不在线" |

- 全部要求登录（未登录 401）。
- `GET /api/friends` 的好友行**只下发** `user_id/username/avatar/level/rank_label/online/in_game`
  —— 不下发战绩、历史、签名、任何凭据（本项目硬教训：接口整行下发必泄露）。
- 排序：在线 → 对局中 → 用户名。
- 定值放模块级常量（`MAX_FRIENDS = 50`、`FRIEND_REQUESTS_PER_HOUR = 10`）并**随接口下发**，
  前端不写死。

## 6. 实施记录

### 6.1 实施中发现的问题

#### ① api.py 在请求里 `import server` —— 一条 bug 造成三个"静默失效"（本批最大的一条）

**症状**（三条，看起来毫不相干）：申请接口回 `{"status":"sent"}` 但**对方收不到** `friend_request`；
接受回 `accepted` 但发起人**收不到** `friend_accepted`；邀战回 200
`{"error":"建房失败，请稍后再试"}`。三条都**没有**服务端报错、也**没有**异常日志。

**根因**：本地与线上都是 `python server.py` 启动的，那时模块名是 **`__main__`**。
api.py 里写 `import server` 会**把整个 server.py 再执行一遍**、得到**另一个模块对象**：
- 那份 `socketio` 不是正在服务的那个 → `emit` 出去**静默丢弃**（socket.io 对不存在的房间不报错）；
- 那份 `room_manager` 建的房在真进程里**根本不存在** → 邀战回一个**野 room_id**。

而生产是 `run_prod.py` 起的、模块名又正常 → **"本地坏、线上好"**，属于最难查的一类环境相关 bug。

**修法**（依赖倒置，见两处代码注释）：api.py **不再 import server**，改由 server.py 在 import 期
把**它自己那个模块对象**（`sys.modules[__name__]`）交给 `api.register_friend_backend()`；
api 侧只按名字现取。推送与建房**仍然各只有一份实现**（都在 server.py）。

**⚠️ 这条 bug 在 pytest 里永远复现不出来**：pytest 里 server 就叫 `server` 这个名字，
`import server` 拿到的是同一个对象、行为完全正常。所以守卫只能是**源码级**的 ——
`tests/test_friends_wiring.py::test_api_must_not_import_server_at_runtime`，
外加"注入真的发生了""建出来的房真的存在"两条。真机复现脚本 `.tmp/repro_invite.py`
（两个真账号 + 真 socket）才是这条的端到端证据。

#### ② 注入**函数对象**会架空全部 monkeypatch

第一版注入的是 `push_friend_invite=push_friend_invite` 这种**函数对象**：import 期就把引用绑死了，
`monkeypatch.setattr(server, 'push_friend_invite', ...)` 这类打桩**全部打到空处** ——
测试还会是绿的（`test_friends_api.py` 里 4 条靠打桩的用例）。改成**注入模块 + 调用时 `getattr`**，
两个目标同时满足，且有守卫 `test_backend_functions_are_resolved_lazily_so_monkeypatch_works`。

#### ③ `from api import app` 让 `api` 这个名字**根本没绑定**

server.py 是 `from api import app`，所以注入那行写 `api.register_friend_backend(...)` 会
`NameError` —— 而被我自己的 `except` 吞成一句警告（"注入失败只记日志"这个刻意的降级正好掩盖了它）。
**兜底逻辑会把"接错线"伪装成"降级运行"**，凡是带 except 的接线代码都要有一条断言"它真的接上了"
（`test_server_actually_injected_its_backend_module`）。

#### ④ 接口只写库、从不推事件（与 CLAUDE.md 坑 #13 同形状）

前端那两个 handler（`friend_request` / `friend_accepted`）一度是**死代码**：
`db` 写对了、接口返回值对了、库里查得到，但**从来没有人 emit 过这两个事件**。
纯函数测试、接口测试**全绿**。→ 守卫是"断言事件真的推出去"的三条用例
（`test_request_pushes_friend_request_event` / `test_accept_pushes_friend_accepted_event` /
`test_request_still_succeeds_when_target_is_offline`）。

#### ⑤ 统一推送实现：api.py 里那份重复的 emit 已删除

api.py 曾经自己 emit 一份 `friend_request`，server.py 又有一份 —— 两份实现必然漂移（坑 #1）。
现在 api 侧一律走注入进来的 `server.push_*`，api.py 里那份 emit 已删除（−785 字节的 `_friend_socketio()` 一并清掉）。

#### ⑥ 名片永远停在「加载中…」—— 一条零报错的**无限重渲染**

**症状**：查看一个**已是好友**的人的名片，卡片永远停在「加载中…」，`#add-friend-btn` 压根没渲染出来；
零 JS 异常、零 console.error、`/api/friends` 完全正常（"接口好的、页面就是不动"这一类最难查）。

**根因链**：`applyProfileFriendRelation` 发现"关系是好友、但卡上没有「邀战」按钮"时会
`reRenderProfileCard()` → `window.showUserProfile()`；而 `showUserProfile` 每次进门第一件事就是把容器
设成「加载中…」；同时 `fetchProfile` 把传给渲染的 `friendRelation` **写死成 `'none'`** ——
于是"重渲染出来那张卡"永远还是「加好友」、永远没有「邀战」→ 调用方又重渲染 → **无限递归**。
实测：8 秒内 `window.showUserProfile` 被调 **830 次**，卡片只在两次 `innerHTML` 写入之间活约 10ms，
所以任何 DOM 采样都只能看到「加载中…」（"卡片没渲染"这个判断本身就是错的，它是被反复擦掉）。

**为什么前三版都没修对**（`static/game.js` 里留着这三版演进的注释）：
① 全局布尔哨兵 + `showUserProfile` 进门复位 → 判定成"没重渲染过" → 同样的死循环；
② 改成 Set（只记"重渲染过"）→ 第二次打开同一个人的名片**直接跳过**关系计算，按钮永远停在「加好友」；
③ 改成缓存"关系本身" → 仍没解决"**重渲染出来的卡不带关系**"这个真正的病根。
直到把 `opts.friendRelation` 从调用点透传进 `fetchProfile` → `renderUserStatsHTML` 才收敛。

**教训**：
1. **重渲染这条路上，渲染函数的每个入参都必须能从调用点传进来**；写死一个默认值 = 把"重渲染"
   变成"死循环"。本批两处修法都是同一个动作：把关系**传下去**，而不是让下层重新猜。
2. 这类死循环**零报错、零日志**，只能靠**计数插桩**发现（8 秒 830 次）；读代码读不出来 ——
   所以"实测复现"这条规矩在本项目不是形式主义。
3. 无头工具里那条断言（"最终必须是「好友」+ 旁边有「邀战」"）**本身是对的**：它抓到了真 bug，
   只是根因在另一处。**别因为工具红了就去改工具**（除非工具确实错了 —— 比如 ⑦）。

#### ⑦ 服务端把**游客**当成了可加好友的人（结算 `recent_opponent`）

**症状**：登录玩家开自定义房 → 把邀请链接发给**没登录**的人 → 打完一局后，登录玩家结算屏上出现一个
**可点的「加好友」**，点下去必然 404「账号不存在」。

**根因**：自定义房的 `handle_create_room` / `handle_join_room` 用
`player_id = session.get('user_id', request.sid)` —— 游客的 `Player.user_id` 因此是**入座时的 socket sid**，
**非空但根本不是账号**。而 `_recent_opponent_payloads` 只判 `if not winner_user_id or not loser_user_id`，
函数注释里那句"双方都得有 uid 才发、游客对局自然被跳过"**不成立**。
匹配房没这个问题（`Player.user_id = session.get('user_id')`，游客恒 `None`），所以缺陷只在上面那条路上。

**修法**：判据从"非空"改成"**这个 uid 真的查得到账号**"（`db.get_user(uid=…)`，两侧都查），
与"必须有账号才能加好友/被加"那条护栏同口径。守卫：`tests/test_friends_realtime.py::test_guest_with_seat_sid_gets_no_recent_opponent`。

#### ⑧ 前端不认拉黑关系 → 又渲染出一个**可点**的「加好友」

服务端在拉黑关系下会下发 `blocked_by_me` / `blocked_me`，而 `game.js` 的 `FRIEND_RELATIONS`
只有 `none/pending_out/pending_in/friends/self` → 被判成"非法取值"**降级成 `none`** → 结算屏上出现
一个**能点**的「加好友」；点下去服务端回 200 但 body **只有 `status`、没有 `error`**，
前端 `apiReason()` 只认 error/message → 只能弹一句通用的「发送好友申请失败」。
**两处都修**：①`FRIEND_RELATIONS` 补上这两个取值 + 结算行渲染成「不能加好友」并禁用；
②`api.py` 在 `status == 'blocked'` 时**带上中文原因**（文案不区分方向 —— 服务端有意不告诉客户端谁拉黑了谁）。
> 查看面那条路（`resolveFriendRelation`）**拿不到** blocked（`/api/friends` 的响应里没有拉黑边），
> 所以那里不写死分支；点下去由服务端那句中文原因兜住 —— 这是"服务端才是裁决者"的既有口径。

#### ⑨ 工具里"照缺陷形状写的断言"会在缺陷修好之后翻红

`tools/recent_opponent_check.mjs` 的 `PB2` 当初是这么写的：**断言 body 里"没有 error"**（即"缺陷还在"）。
我在服务端补上中文原因之后它当场变红 —— **红的含义刚好反过来**。已把判据翻成正向（必须带原因）。
⚠️ 教训：把"记录缺陷"写成断言时，务必在断言文案里写清"这条绿 = 缺陷还在 / 变红 = 已修"，
否则后人（和下一次跑的智能体）会把它当成回归。

### 7.1 落点

### 7.2 三个刻意的取舍

1. **默认 1 = 开放申请**。默认关会让新玩家又回到"只能加同局的人"，正好与决策④写下的理由
   （新玩家不该被卡死）相矛盾。
2. **只下发给本人**（不进 `public_stats`）：别人不需要知道"这个人关掉了申请"，
   点下去由服务端回一句中文原因就够了。守卫是"**以别人的身份**直读 `/user_stats`、断言没有这个字段"。
3. **不锁死已经收到的申请**：关掉的是"以后别来"，不是"之前收到的作废"—— 一刀切会把用户
   本来打算同意的那条申请一起锁死，而且页面上看不出原因。

### 7.3 教训：改「必须全部出现」的契约，必须先 grep 全部载荷构造点

把字段加进 `WRITABLE_FIELDS` 的那一刻，**任何少发一个字段的保存都会整次被拒**（这是有意设计：
"允许缺字段 = 保持原值"会变成"保存了但没生效"这种最难查的静默失败）。实测代价：
**29 个既有测试立刻变红**（载荷构造器写死了 10 个字段），全是机械修改。
→ 与 CLAUDE.md 坑 #9 同形状：改共用契约先 grep 出全部调用点、逐个表态。
前端那份也在名单里 —— 只加复选框不补保存载荷，症状是"开关点得动、保存 400，
报错是「缺少字段 friend_requests_open」"。
