# 好友私聊（2026-09-19）

> 本文件是**冻结契约**：后端按 §3/§4 实现，前端按 §3/§5 实现，两边不必互相等。
> 作者（产品）确认的需求原文只有一句：
> 「新增好友私聊功能，要求可以保留聊天记录，聊天记录需要记录下时间，
>  好友私聊功能入口暂时还是放在好友窗口里面，等一会我的合作者会去更改游戏的 UI，让他来改就可以。」
> 因此**这一批只做"能用"**：临时入口 + 朴素样式，视觉与布局留给合作者。

---

## 0. 为什么是"私聊"而不是"局内聊天"的延伸

局内已有快捷语（`quick_chat.py`，第 4 批）。私聊要解决的是**另一件事**：
打完一局想约下一局、想留句话，而对方不在同一间房里。所以它必须**落库**（用户明确要求保留记录），
而不是像快捷语那样只活在房间内存里。

---

## 1. 作者拍板/我按既有护栏定的取舍

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 谁能聊 | **仅好友**（拉黑后双方都不能发） | 与既有护栏同一口径：「必须有账号才能加好友/被加」「拉黑后不能申请也不能邀战」。陌生人能私聊 = 骚扰面 |
| 记录保留 | **永久**（不清理、不滚动删除） | 用户明确要求"保留聊天记录" |
| 时间 | 每条带 `created_at`（epoch 秒）**与**服务端格式化好的 `stamp` | 「记录下时间」；`stamp` 的规则**只有一份实现**（`dm.py`），前端只渲染 —— 本项目栽过"同一规则两份实现必然漂移" |
| 分页 | 默认最近 **50** 条，`before=<id>` 游标往上翻 | 记录永久保留 → 必须有分页，不然聊久了会拖死页面 |
| 长度 | 单条 **≤ 300 字**；服务端**拒绝**（不是静默截断） | 静默截断会让用户以为自己发全了 |
| 限流 | 每个发送者 **20 条/分钟** → `429` | 与好友申请（10/小时）同一套思路 |
| 未读 | 收件人在**真的打开那段会话**时标记已读；好友行显示未读数 | 「谁给我发了消息」必须看得见，否则私聊等于没有 |
| 入口红点 | **不动**（仍是"待确认好友申请数"） | 那条契约被 `friends_check` T8b 钉着；把未读混进去会让"红点=申请数"这条既有断言失真。未读另在**行内**体现 |
| 实时 | 在线时 socket 收 `friend_message`；离线消息在下次打开会话时拉到 | 与 `friend_request` 同一套推送机制（`presence.sids_of`） |

### 本批明确不做

已读回执给对方看、撤回、图片/表情包、@、群聊、消息搜索、系统通知/浏览器推送、语音。

## 2. 数据层（`db.py`）

```sql
CREATE TABLE IF NOT EXISTS friend_messages (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    from_uid   TEXT    NOT NULL,
    to_uid     TEXT    NOT NULL,
    body       TEXT    NOT NULL,
    created_at INTEGER NOT NULL,          -- epoch 秒
    read_at    INTEGER DEFAULT 0          -- 0 = 未读
);
CREATE INDEX IF NOT EXISTS idx_friend_messages_pair ON friend_messages (from_uid, to_uid, id);
CREATE INDEX IF NOT EXISTS idx_friend_messages_unread ON friend_messages (to_uid, read_at);
```

- **不建会话表**：一对好友之间的会话由消息行本身表达（`(from,to)` 任一方向）。
  多一张会话表就多一处要同步的状态（本项目的老病根）。
- 所有 DAO **失败只记日志、返回安全默认值**（与 `add_profile_message` 等一致）。
- DAO（模块级包装成对存在）：
  `add_friend_message(from_uid, to_uid, body)` → `dict|None`
  `list_friend_messages(me, other, limit=50, before_id=None)` → `list[dict]`（**按 id 倒序取再正序返回**）
  `mark_friend_messages_read(me, other)` → 标记数
  `count_unread_messages(me, other=None)` → 未读数（`other=None` 时是总数）

## 3. 纯规则模块（`dm.py`，**单一真源**）

为什么单独一个文件（与 `quick_chat.py` / `achievements.py` 同一套路）：`api.py` 要下发这些规则，
若写进 `server.py`，`api.py` 就反向依赖 `server.py`（而 `server.py` 是 `from api import app` 的，会成环）。

- `MAX_BODY_LEN = 300`
- `PER_MINUTE = 20`；`check_rate(timestamps, now)` → 纯函数，房间/进程状态不驻留在这里
- `stamp(epoch)` → `'09-19 15:40'`（**全年份不显示**；跨年时显示 `'2026-09-19 15:40'`）
- `normalize_body(text)` → 去控制字符、去首尾空白、`\n` 压成空格（与 `profile_spec.normalize_status` 同口径）

## 4. 接口（`api.py`，冻结）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/friends/messages?username=<name>&limit=50&before=<id>` | 取与某人的会话（最新的在后）；`has_more` 表示还有更早的 |
| POST | `/api/friends/messages` `{username, body}` | 发一条 |
| POST | `/api/friends/messages/read` `{username}` | 把某人发来的都标已读 |

响应形状（**逐字段冻结，前端照这个写**）：

```json
// GET
{"status":"ok","has_more":false,
 "messages":[{"id":12,"from_uid":"…","to_uid":"…","body":"在吗","created_at":1758273600,
              "stamp":"09-19 15:40","mine":true}]}

// POST
{"status":"ok","message":{"id":13,"from_uid":"…","to_uid":"…","body":"在","created_at":1758273605,
                          "stamp":"09-19 15:40","mine":true}}

// POST /read
{"status":"ok","read":3}
```

错误一律 `{status:'error', error:'中文原因'}`：
401 未登录｜404 账号不存在｜403 不是好友或已被拉黑｜400 空消息 / 超长（点名"最多 300 字"）｜429 发得太频繁。

`GET /api/friends` 的每个 friend 行**新增 `unread`**（整数），并在 `counts` 里新增 `unread_total`
（**入口红点不读它**，见 §1）。

### Socket 事件（服务端 → 收件人）

`friend_message`，payload 与 GET 里那条同形（外加 `from_username` / `from_avatar` 便于直接渲染）：

```json
{"id":13,"from_uid":"…","from_username":"小红","from_avatar":"","body":"在吗",
 "created_at":1758273605,"stamp":"09-19 15:40"}
```

推送**只有一份实现**：`server.py` 的 `push_friend_message(to_uid, message)`，
由 `api.py` 经 `register_friend_backend` 注入后按名字调用（**别在 api.py 里自己 emit**，
也**别在 api.py 里 import server** —— 那会把 server.py 执行成第二份模块，见 CLAUDE.md 坑 #19）。

## 5. DOM 契约（前端，**冻结 id**；样式随便，合作者会重做）

入口放在**好友窗口里面**（用户指定）。列表视图与会话视图共用 `#friends-modal`，用 `hidden` 切换：

| id | 用途 |
| --- | --- |
| `#dm-panel` | 会话视图容器（默认 `hidden`） |
| `#dm-title` | 会话标题（对方用户名） |
| `#dm-list` | 消息列表容器 |
| `#dm-load-more` | 「加载更早的消息」按钮（`has_more` 为假时隐藏） |
| `#dm-empty` | 空会话占位（「还没有聊过，打个招呼吧」） |
| `#dm-input` | 输入框（`maxlength=300`） |
| `#dm-send` | 发送按钮 |
| `#dm-back` | 返回好友列表 |
| `.dm-row[data-mine="1\|0"]` | 单条消息行；内部 `.dm-body` 与 `.dm-stamp` |
| `.friend-unread` | 好友行上的未读数字（0 时 `hidden`） |
| `[data-friend-action="dm"]` | 好友行里的「私聊」按钮（与既有 `invite`/`remove` 同一套事件委托） |

前端纪律（与好友批一致）：
- 所有取数**只认服务端**（未读数、时间戳不许前端自算或自增）；
- 时间**只渲染 `stamp`**，不在前端重算格式；
- 任何写操作后**重新拉一次接口**对齐（不在前端数组里自己加减）；
- 发送成功后**用响应里那条 message** 追加，不自己造一条（否则 id/时间会与库不一致）。

三条纪律在本节的落法（都是本项目栽过的形状）：

1. **时间只渲染服务端给的 `stamp`**：`dmRowHtml` 里就是 `escapeHtml(m.stamp)`，不 `new Date`、
   不补零、不换格式 —— 格式化规则的唯一实现在 `dm.py` 的 `stamp()`。
2. **未读只认服务端**：页面上的未读数只有两个来源，都是服务端给的 ——
   ① `GET /api/friends` 的 `friend.unread`（渲染行时）；
   ② `POST /api/friends/messages/read` 的成功回执（把那段会话归零）。
   **唯一一种"累加"是"面板开着时重拉一次 `GET /api/friends`"**（见 `handleFriendMessageEvent`
   里那条注释：选它而不是前端 `+1`，因为 `+1` 就是第二份实现，迟早跟服务端的

3. **发送成功用响应里那条 `message` 追加**，不自己造 —— 自己造的 id 会跟库里不一致，
   而 id 正是往上翻的游标。

### 6.2 发现的问题 / 踩的坑

1. **旧的好友测试把 `unread` 当"契约漂移"判红**（3 条）：`tests/test_friends_api.py`
   里 `FRIEND_KEYS` / `counts ==` 是**集合相等**断言，本批按 §4 加了 `unread` /
   `unread_total` 之后必然红。**只改了那几处常量与整份比对**（本批在该文件的唯一改动），
   并在原地写了注释说明依据（契约 §4）。这类"形状冻结"断言的好处正在这里：
   多加一个字段会当场被拦下、逼着作者回去看契约。
2. **跨年判据是"相对读者此刻"，不是"相对今年"**：`stamp()` 写成"消息年份 ≠ **当前**
   年份"。若写成"时间更早"或"≠ 今年的年份"，在"去年的消息、去年看"时会把年份藏掉，
   而跨年永远是**相对看的人此刻**的。测试显式传 `now`，所以这条规则不依赖跑测试的日期
   （否则它只在 12 月 31 日才测得到）。
3. **`has_more` 不能由"这页取满了"推断**：恰好剩一整页时那种写法会给 `True`，
   前端于是显示一个点了没反应的「加载更早的消息」。本实现用一条 `EXISTS` 直接问库，
   并**专门写了一条"恰好剩一页"的用例**（`test_has_more_is_false_when_the_page_is_exactly_full`）。
4. **推送形状一开始有两处**：`api.py` 把接口自己那份 `message`（带 `mine` / `to_uid`
   这类**发送方视角**字段）整份推给 `server.push_friend_message`，一度把 `mine` 漏给收件人。
   收口成 `dm.PUSH_PAYLOAD_KEYS` + `dm.push_payload()`（唯一一份字段清单），
   两侧都走它 —— 这是"同一形状两处维护"的第一次复发，靠端到端断言
   （`推送不含发送方视角字段 mine`）才发现。
5. **限流账本刻意不放进程内存**：按 §3 的要求用**库里的真实行数**
   （`db.count_friend_messages_since(uid, now-60)`）。除了"不串房间"，
   它还顺带满足两条：被拒的那条不占配额（拒绝不会把窗口占满）、重启不丢。
   另有一条用例钉"**按发送者隔离**"（甲被限流时乙照发）——进程级 dict 会在那里红。
6. **`register_friend_backend` 加了能力清单**：注入的本来就是模块对象、`api` 侧按名字
   现取，所以"挂 `push_friend_message`"本身不需要额外接线；但如果只靠按名字现取，
   `server.py` 哪天改名/删掉这个函数，接口只会静默推送失败（**pytest 测不到**：
   pytest 里 server 就叫 `server`）。于是把清单做成**启动期校验**：名字取不到就在
   服务启动那一刻喊出来，而不是等用户发现"对方收不到消息"。
   —— 同时保留"只存模块、不存函数对象"，`monkeypatch.setattr(server, ...)` 照样生效。
7. **`api.py` 全程没有 `import server`**（也不许在函数里 import）：推送一律走
   `_push_friend_event('push_friend_message', ...)` → `_friend_backend(name)` 现取。
   CLAUDE.md 第 10 节第 19 条那个坑（`python server.py` 时 `import server` 会拿到
   第二份模块对象、事件静默丢弃）在本批没有复发，端到端那一步就是它的守卫。
8. **本机没装 `websocket-client`**：`python-socketio` 的 websocket 传输会连不上
   （客户端只打印一句警告，然后报"namespace 连接失败"）。端到端脚本显式
   `transports=['polling']` —— 推送走同一条 engine.io 会话，polling 一样能证明
   "事件真的到了那个人"。
9. **测试污染**：`friend_messages` 与 `user_friends` 是整个测试会话共用的表，
   本批的用例在夹具 teardown 里按 uid 回收自己造的消息与边。不回收的话，
   任何依赖"未读为 0 / 会话为空"的用例会在**别的文件里**假红（失败点不在肇事文件）。
10. **别人的在途改动会造成"另有红项"**：全量跑时 `tests/test_friends_api.py::
    test_invite_refused_when_inviter_is_in_game` 与 `tests/test_lobby.py::
    test_repeated_create_recycles_previous_waiting_room` 会红，但**单独跑都过**，
    且在本批改动**之前**的同一份工作区（去掉 `tests/test_friend_dm.py`）里同样红 ——
    属既有的跨文件顺序耦合，与本批无关，未在本批处理。

前端侧（本轮新增，按踩到的先后）：

11. **`insertAdjacentHTML` 之后同步读 `scrollHeight` 会读到过期值** —— "往上翻不跳位置"
    这条最大的一个坑。第一版的还原逻辑是
    `box.scrollTop += box.scrollHeight - 插入前的 scrollHeight`：实测插 13 条时
    `scrollHeight` 只报了 +812px，而真实内容涨了约 829.7px（**少 17.66px**），
    于是 scrollTop 补少了那么多，玩家看到的就是画面往下一跳。
12. **同一次操作里还有第二处位移，只补列表内部是补不掉的**：取完最后一页时
    `#dm-load-more` 变成 `hidden`，弹窗矮了 25.88px（内容区 17.66px），上面的内容整体上移 ——
    正在读的那条消息也跟着上移。第一版只盯列表内部，工具量到的偏差就一直是那 17.66px，
    而**产品代码自己量的偏差只有 0.7px**（两者口径不同，差点被误读成"工具写错了"）。
    最终改法：**量锚点自己在屏幕上的位置**（`getBoundingClientRect().top`），
    插入 + 更新按钮显隐之后把差值补进 `scrollTop`。实测偏差 **0.34px**，
    工具与产品代码（`window.dmAnchorDrift`）量出来的数完全一致。
13. **`hidden` 属性会被作者样式压过**：§5 冻结的是 `hidden` 属性，而 `.dm-list` / `.dm-head`
    都给了 `display:flex` —— 作者样式优先于 UA 的 `[hidden]{display:none}`，
    于是"设了 hidden 还看得见"。第 34 节补了一条
    `#friends-modal [hidden] { display: none !important; }`（作用域限定在这个弹窗里，
    与既有 `.hidden` 类那套互不干扰）；既有代码里 `#quick-chat-panel[hidden]` 是同款先例。
14. **登录接口有同 IP 限流，会把无头工具打成"静默降级"**：`api.py` 的
    `_rate_limited('login')` 是 **60 秒窗口内 10 次**；超了之后 `/login` 回 302 到 `/login`
    并 flash「操作过于频繁，请稍后再试」，而那次响应**照样会种 session cookie**
    （里面没有 `user_id`）→ 后续 `/api/profile` 一律 401。
    症状极具误导性：`friends_check` 把它判成"/api/friends 没上线" → **静默降级成离线模式**
    （网络类断言被 SKIP、全链路那几条判红），根因跟前后端都没关系。
    排查也绕：先用 curl 验 `Set-Cookie`、再用 python `requests` 对比，最后才在 `api.py`
    里找到那几行限流。处理：两个工具都改成**先 `/register`**（`api.py` 注册成功时直接种 session，
    正常路径一次 `/login` 都不用发），被限流才等窗口；而且**只有限流才等**，
    别的情况立刻交回断言。
15. **"未读归零"必须两侧都断言**：页面把 `.friend-unread` 隐藏了，可能只是前端把数字藏了，
    服务端那条消息还挂着未读。所以 `friend_dm_check` 的 D5 两面都验：页面这一侧 +
    **以对方（A）的身份直读 `GET /api/friends` 的 `unread`**
    （CLAUDE.md 第 10 节第 12 条：状态/隐私类断言只有服务端拦得住）。
16. **`apiPost` 返回的是 `{status, body}`，HTTP 码在 `status` 里**：写成 `resp.http` 是
    `undefined` → 一条**恒假的假红**；反过来拿 `status` 当业务结果判，就是一条**恒真的假绿**。
    工具第一版两种都写过一次，两处都留了注释。
17. **`has_more` 那条断言的判据不能写死条数**：工具会在同一个隔离库里反复跑，历史消息是累积的，
    "更早那一页还剩几条"取决于之前跑过几次。判据改成"**这一页真的插进去了**"
    （行数增加 + 新增那一段的 id 全部小于原有那一段），第二次跑照样绿。
18. **⚠️ 既有的 `friends_check` T3i 现在是红的，根因是**别人**在途的「好友邀战自动入房」**
    （`static/game.js` 的 `sendFriendInvite` 末尾那段 `joinRoomById(inviteRoom, {quiet:true})`，
    本批**一个字都没碰**）。证据链（全部实测，不是推断）：
    - 把本批三处改动全部还原成 `HEAD`（只换 `static/game.js` 一个文件，后端与工具都不动）
      → `friends_check` **66 / 0 全绿**；换回工作区那份 → 又是 65 / 1（只有 T3i 红）。
    - 只把 `sendFriendInvite` 里那段自动入房注释掉（其余原样）→ **66 / 0 全绿**。
    - 机制：T3a 里 B 点「邀战」会**真的把 B 送进第一间房**（地址栏 `?room=<第一间>`）；
      随后 A 经真接口邀 B 到**另一间房**，B 点「进入房间」时 `join_room` 被服务端按
      "你已经在一间房里"拒掉（`quiet:true` 所以页面上零提示），`gameState.roomId` 还停在第一间 ——
      而 T3i 判的正是"进了服务端这次给的那间房"，必然红。
      独立复现（只用一个浏览器 + 一个 python 账号、不碰前端源码）也确认：
      **B 没先进过任何房间时，点「进入房间」进的就是服务端给的那一间**（前端那条路本身是好的）。
    - 处理：**保持原样交给那个智能体修**（那是它的票面），本批只在文档里留证据 ——
      不改它的代码，也不为了把自己那 1 条刷绿去动别人的功能。
