# 「打完一张，剩下的手牌莫名消失」根因与修复（2026-09-14）

## 1. 作者反馈

> 每一次有手牌通过之后，剩下的自己的手牌总是会莫名其妙消失。
> 我无法描述具体场景，但是刷新网页之后就会重新出现。

关键信息有两条：

- **刷新就好** ⇒ 服务端手牌是好的，坏的是**客户端**那份。
- **无法描述具体场景** ⇒ 与"牌在手牌里第几位"有关，而不是与某张特定的卡有关。

## 2. 实测复现（`tools/hand_play_check.mjs`）

真实浏览器 + 真服务端，两个客户端，给自己发 2 张牌、给对方发 0 张
（对手没有速阶3 → 连锁会在同一个请求里结算），然后**真实点击**打出第 1 张：

```
出牌前: {"dom":2,"names":["五险一金","看破！"]}   服务端: ["五险一金","看破！"]
点击打出的牌: 五险一金
事件时序: [..., "emit:use_magic_card", "hand_updated:1", "hand_updated:1", "ack:use_magic_card"]
出牌后: {"dom":0,"names":[],"state":[]}          服务端: ["看破！"]
                              ↑ 界面手牌空了，服务端还有 1 张
```

界面手牌从 2 张变成 **0 张**，服务端一直是 `["看破！"]` —— 与作者描述完全一致。

## 3. 根因：前端"本地删牌"的兜底分支删错了人

时序（工具里有断言专门守它）：

```
handle_use_magic_card
  ├─ 扣掉打出的那张牌
  ├─ _advance_chain_window(room, opponent)
  │    对方手上没有速阶3 → 认为"无法响应"
  │    连续两次放弃 → 【在同一个请求里同步调用 resolve_chain】
  │    resolve_chain 收尾：向双方各推一次 hand_updated（此时手牌里已经没有刚打出的那张）
  └─ return ack   ← 客户端拿到 ack 时，早就收到过"新手牌"了
```

前端 `sendMagicCard` 的 ack 回调要"本地把这张牌从手牌里删掉"，旧实现是：

```js
const hits = [];  // 按 name+speed 身份找
...
if (hits.length) {
    removeAt = hits[Math.min(sentIndex, hits.length - 1)];
} else if (sentIndex >= 0 && sentIndex < gameState.hand.length) {
    removeAt = (gameState.hand.length === sentIndex + 1) ? sentIndex : -1;   // ← 元凶
}
```

那个兜底分支**只要触发就一定是错的**：能走到它，就说明手牌里已经没有任何一张
和打出的牌同名同速阶 —— 也就是服务端早已推过新手牌、牌早就离手了；这时再按旧下标
删一张，删掉的必然是**别的牌**。

而"打出**倒数第二张**"恰好满足它的判断条件：

| 手牌 | 打出 | 服务端推来的新手牌 | 兜底条件 | 结果 |
| --- | --- | --- | --- | --- |
| `["A","B"]` | A（index 0） | `["B"]`（长度 1） | `1 === 0+1` ✅ | 把 B 也删了 → **空手牌** |
| `["A","B","C"]` | B（index 1） | `["A","C"]`（长度 2） | `2 === 1+1` ✅ | 删掉一张 → 显示成 1 张（应 2 张） |
| `["A","B","C"]` | A（index 0） | `["B","C"]`（长度 2） | `2 === 1` ❌ | 正常 |

所以手牌越接近打完越容易撞上；这也解释了作者"无法描述具体场景"。

**为什么以前没被发现**：这个分支依赖"服务端先推新手牌、ack 后到"。
只有当连锁在同一个请求里结算（对手没有速阶3 / 无法响应）时才会这样；
对手手上有速阶3、会弹响应窗口时，ack 先到、`hits` 能按身份找到牌，那条错路径不触发。

## 4. 修法

### 4.1 前端：删掉错误的兜底分支（`static/game.js`）

只按身份找，**找不到就什么都不删** —— 服务端才是手牌的权威。
不按下标猜着删，是这个 bug 唯一正确的修法。

### 4.2 服务端：扣牌后立刻以自己为准推一次手牌（`server.py`）

`handle_use_magic_card` 扣牌之后此前**一个 emit 都没有**，要等连锁结算才推。
前端因此不得不"自己猜着删"，而猜就会猜错。现在扣牌后立刻推一份权威手牌，
前端不再需要靠本地推断。

### 4.3 顺手补上的两条防线（同一个"空白且不自愈"的病灶）

`updateHandUI` 是**先清空容器、再遍历 `gameState.hand`**：只要 hand 不是数组、
或里面混进坏条目，就会"清空了却没填回来"，并且此后每次刷新手牌都抛异常
→ 整块手牌空白，**只能刷新页面恢复**。这正是"刷新才好"的那种形态。

- `hand_updated` / `room_sync` 收手牌统一走 `applyHandPayload()`：结构不对就**忽略并请求重同步**，
  绝不拿坏数据覆盖；坏条目剔除。
- `updateHandUI()` 先在 DocumentFragment 里把整份手牌搭好，最后一次性替换容器内容；
  渲染张数与状态张数不一致时请求重同步。
- 新增 `request_hand_sync` 事件（只回给请求者本人）：客户端发现对不上就能自我纠正，
  **不必等玩家刷新页面**。

## 5. 回归与验证

| 层次 | 产物 | 结果 |
| --- | --- | --- |
| 单元 | `tests/test_hand_sync.py`（**8 条**） | 全绿 |
| 全量 | `python -m pytest tests/ -q` | **710 passed** |
| 真实浏览器端到端 | `tools/hand_play_check.mjs`（**15 项**，两个真页面 + 真服务端） | 全部通过 |
| 既有无头套件 | ui_layout / priority_prompt / priority_live / effect_badge / target_selection / papal_discard / chain_target / sfx / bgm / card_compendium / room_invite / stats_modal | 全部通过 |

**反证（红基线都是实测跑出来的，不是推断）**：

- 不修前端、只跑 `tools/hand_play_check.mjs` → 3 项红，且打印出
  `界面 0 张 / 服务端 1 张` —— 这就是作者看到的现象。
- 把 `applyHandPayload` 的校验去掉 → 2 项红（坏条目未被剔除、没有请求重同步）。
- 服务端时序断言（`hand_updated` 先于 `ack`）在修复前后都通过 ——
  它是本 bug 的**成立条件**，所以必须留在工具里当哨兵：一旦时序变了，
  这段代码的正确性前提也就变了。

## 6. 顺带说明：诊断工具

- `tools/hand_play_check.mjs` —— 回归工具（本文件的断言都在里面），
  含"真实点击出牌后界面手牌数 == 服务端手牌数"这条端到端不变量。
- `tools/repro_hand_blank.mjs` —— 诊断工具（非断言）：给两个真实页面装
  `gameState.hand` 赋值陷阱（记调用栈 + 触发事件名）、`updateHandUI` 异常陷阱、
  `showAlert/showMessage` 陷阱，用来定位"是谁把手牌改了"。
  ⚠️ 里面踩过一个坑：`test_clear_all_effects` 清的是**房间里所有人**的手牌，
  所以"给 A 发牌 → 给 B 清空"的顺序会把 A 的牌清掉，看着像 bug。
