# 落地实现方案（2026-09-23）· 已敲定版

把这几轮挑出来的设计落进真代码的**分期方案**。基线是 **C（卡牌竞技场）**：真卡手牌（R）、
两块棋盘都要看得清、移动端按 S 调优、目标选择按 T 加确认步。

> 配套材料：`docs/ui_demos/index.html`（21 版示意稿总览）· `docs/UI_DEMO_OPTIONS_2026_09_23.md`（取舍与代价）
> · 本文只管"怎么改真代码"。

**明确不做**（前几轮已淘汰）：复古风（像素 / 暖纸）· 手机端优先（作为方向，不等于不做移动端）
· 通行证 / 赛季等商业化内容 · L 的航线节点。

---

## 1. 动手前必须知道的六条约束

前几轮的教训都在这里，漏一条就会踩：

| # | 约束 | 为什么 | 相关工具/文件 |
| --- | --- | --- | --- |
| 1 | **id 一个都不能改** | `tools/*.mjs` 全按 id 点击；`dom_contract_check.mjs` 查悬空 id | `templates/index.html` |
| 2 | **布局断言两组** | 宽屏组：棋盘尺寸/浮窗零叠压/整条手牌在视口内/阶段按钮居中±3px/预览与聊天不重叠；紧凑组：**零纵向滚动 / 格子零遮挡 / 触摸 ≥40px / 开面板后棋盘仍可见** | `tools/ui_layout_check.mjs`（128+ 项） |
| 3 | **⚠️ pytest 里有断言源码字符串的用例** | 这是"完全重构"的**最大成本**：改了 CSS/DOM 文案可能直接让测试红，而它不告诉你为什么 | `tests/`、`docs/UI_REBUILD_PROPOSAL.md` §1.3 |
| 4 | **`.game-container` / `.game-content` / `.game-main-container` / `.screen.active` 不许有 transform / filter / backdrop-filter** | 它们有 `position:fixed` 后代（浮窗）；加了会让浮窗改基准 | `tools/fluent_style_check.mjs` 的 BREAKERS |
| 5 | **AC6 指标有预算** | 裸 hex ≤90 · 裸 rgba ≤180 · `!important` ≤40 · 重复选择器 ≤25 | `tools/fluent_css_metrics.mjs` |
| 6 | **令牌三层 + 7 预设的 AC4** | 结构/材质/颜色三层；换预设**只准换颜色**（圆角/间距/字号必须相同） | `static/style.css` 令牌区、`docs/FLUENT_UI_2026_09_21.md` §1 |

**另有一条来自 CLAUDE.md 的红线**：视觉改动**只允许**动颜色/阴影/渐变/transform/opacity/动画，
**不许动盒模型尺寸**。这条把下面的分期天然切成两半 —— 凡是动盒模型的期，都必须连带重定断言。

## 2. 分期（每期独立上线，每期都有门禁）

### Phase 0 · 摸清安全网（不改任何代码，0.5 天）

这一期的产出是**一张清单**，不是代码。

- `grep` 出 `tests/` 里所有断言 CSS 片段 / DOM 结构 / 文案的用例，按"会不会被 C 化改到"分类；
- 列出 `ui_layout_check.mjs` 里**会被盒模型改动影响**的断言（手牌、棋盘、浮窗三类）；
- 跑一遍基线：`pytest -q`、`ui_layout_check`（宽+紧凑）、`fluent_css_metrics`、`fluent_css_lint`、`fluent_css_diff_vs_head`，
  把**数字**记下来（尤其是 `dupSel` 与断言总数，后面每期都要对比）。

> 没有这一期，后面任何一期红了都不知道是新问题还是老问题。

### Phase 1 · 视觉层：把 C 的皮穿到现有结构上（1–1.5 天）

**只动颜色/圆角/阴影/材质/字体**，一个盒模型尺寸都不动。

- 令牌区新增 C 的一套：底色/面板/描边/强调色（紫金）→ 以**新预设**的形式加（`html[data-theme-preset="arena"]`），
  而不是覆盖 `fluent`；这样 C 与现有观感可共存，也顺便满足 AC4（形状令牌沿用 Fluent 那套）。
- `.btn` / `.modal-content` / `.log-container` / `.magic-card` / `.cell` / `.board` 的**配色与圆角**归到新预设。
- 门禁：`ui_layout_check`（宽+紧凑）**必须与基线逐项一致** · `fluent_css_metrics` **不比基线差** ·
  `fluent_css_lint` OK · `fluent_style_check --only set|presets|dark`。
- 风险最低的一期：**不改结构，128 项断言不可能变**（这正是它值得先做的原因）。

### Phase 2 · 卡组件与手牌（2–3 天，**要动盒模型**）

把 `static/style.css` 里的 `.magic-card`（现 64×92 紧凑 / 90×120 宽屏）换成 R 的真卡结构，
并接上手牌行为。

- **卡面结构**（照 MTG 官方分区 §201-213）：满幅插画 → 名牌 + 速阶宝石 → 独立说明框 → 类型条；
  比例取 **0.714**（= 实体 TCG 63×88mm，MTG 资产 744×1040 = 0.7154 交叉验证过）。
- **手牌扇形**按 Balatro 的公开公式（`cardarea.lua`）：总张角上限 **±5.73°**，每张步进 `0.2/n` 弧度；
  间距**按手牌上限算、不按当前张数**（这样抽牌/出牌时手牌不会整体重排）；弧顶比两侧高约视口高的 1.7%。
- **两级预览**：一级 = 悬停 `scale(1.05)`（Balatro 的悬停就是纯缩放）；二级 = 点击
  `translateY(-56px) scale(1.09)` + 右侧说明窗（这两档位移是我们自己的设计，市面没有公开数值）。
- **⚠️ 触屏没有 hover** → 移动端把两级压成一级：**点一下直接进二级**（抽屉里给可读大卡面），
  这是移动端唯一可行的等价物。
- `game.js` 的 `updateHandUI()` 要改：DOM 结构仍是"卡容器 + 名字/速阶/类型"三处文字（**与卡面美术的分工不变**：
  美术只负责底图、文字仍由 DOM 叠），只是多一层插画背景与卡框。
- 门禁：`ui_layout_check`（**手牌相关断言预计要重定**：整条手牌在视口内、手牌可点）· `pytest`（手牌渲染有测试）·
  `hand_play_check.mjs` · `fluent_css_metrics`。
- **这一期会碰到断言的红**，所以要连 Phase 0 的清单一起看。

### Phase 3 · 对局屏结构：两块棋盘（1.5–2 天，**要动盒模型**）

现在宽屏是**堆叠**两块棋盘，`docs/FLUENT_UI_2026_09_21.md` §10.3 记录了未修缺陷：
≤800px 高时第二块棋盘被手牌标题压住 12–18 格。三选一，**已定 P（主次）**，理由见 §3.1：

| 选项 | 改动 | 代价 |
| --- | --- | --- |
| **M 等大** | 两块都到 400px，并排 | 要重写宽屏 1200–1439 那段"为浮窗留白"的 padding；"两块同尺寸 ≥280px"这条断言不用改，并排后自动满足 |
| **P 主次** | 对手 460（焦点）+ 你 352 真棋盘 | 改动最小，但仍是不对称 |
| **U 我为主** | 你的 504 + 对手缩成 240 雷达盘 | 开火时视线要往角落跑（代价已写在示意稿里） |

- 同时把 **C 的「连锁叠牌」**搬回来（现在是 10 秒弹窗，错过就看不见谁响应了谁）：`#chain-prompt-container`
  改成"叠起来的三张真卡 + 倒计时"。
- 日志：宽屏常驻、窄屏收进 `#aux-dock`（现成机制）。
- 门禁：`ui_layout_check` 宽屏组（**棋盘/浮窗/手牌三类断言都要重定**）· `pytest`（`test_ui_review_fixes.py` 钉了棋盘尺寸）。

### Phase 4 · 目标选择态（1 天）

- 按卡的类型分流（这是回答"确认使用到底好不好用"的结论）：
  **无需目标**（失灵！/看破！…）→ 点两次即用；**需要目标**（神威！3×3 / 轰炸 整行列 / 增援 落格）→ 选完目标再确认。
- 依据：Hearthstone 的"松手即生效"是为**单点**目标设计的；本作是大范围，且两家**提交后都不能撤销** →
  按 Balatro 先选后确认。
- 实现要点：合法落点高亮（虚框锚点）· 已选区域实框 · **越界/非法不提交**（红框 + 确认置灰）·
  点空白 = 取消（不消耗卡）· 确认按钮文案随状态变。
- ⚠️ 现有实现是"点一次进待使用、再点一次尝试使用"，**改这个流程会动到 `tests/` 里断言该行为的地方**。
- 门禁：`target_selection_check.mjs` · `hand_play_check.mjs` · `magic_*` 相关测试 · `ui_layout_check`。

### Phase 5 · 移动端（1.5–2 天）——**三条实证问题，按此顺序修**

1. **`viewport-fit=cover`（一行 + 一处 padding，收益最高、风险最低）**
   `templates/index.html:5` 缺它，而 `static/style.css:3665/3978` 用了 `env(safe-area-inset-bottom)` →
   iOS 上**恒为 0**。**必须成对改**：加了 `cover` 就要补 `env(safe-area-inset-top)`，否则顶栏钻到刘海下。
2. **手机改"一屏一块棋盘"**：`adaptive_layout.js:135` 现在 390×844 判为 `stack`（两块 364px 上下堆），
   而实测可用高只有 **763px**（844−47−34）。改判据走 `tabs`（`#board-tabs` + `applyActiveBoard()` 都是现成的），
   格宽反而从 ~40 升到 55。
3. **手牌可读性**：紧凑档 64×92 的卡 + 中文效果文字 = 读不了。接 Phase 2 的真卡 + **点开抽屉给 200×280 大卡面**。
- 令牌按规范值：触摸 **48px**（Material 推荐；项目现在是 40）· 抽屉遮罩 32% 黑、顶部圆角 28dp、把手 32×4dp。
- 门禁：`ui_layout_check` 紧凑组（320×568 / 336×664 / 390×844 / 横屏 664×336）——**判据要重定** ·
  `dom_contract_check.mjs`。

### Phase 6 · 其余屏（每屏 0.5–1 天，按价值排序）

首页（C+I 综合，已在 M 里画过）→ 结算（V 已画）→ 卡牌图鉴（W 已画）→ 布阵 → 猜拳 → 大厅 → 排行榜 → 名片/设置。
**每屏单独上线**，跑该屏对应的 `tools/*_check.mjs`。

### Phase 7 · 卡面美术接前端（依赖出图）

`docs/magic_card_art_prompts.md` 已有 41 张竖版插画提示词（脚本生成，含覆盖率校验）。
出图后：卡面底图位（手牌 / 图鉴 / 连锁叠牌 / 结算）接上，**文字仍由 DOM 叠**（`.card-name` / `.card-speed` / `.card-type`），
与提示词文件里"美术不生成文字与卡框"的约定一致。

## 3. 五件事已敲定（依据 + 若要改的代价）

> 这五条我按前几轮的全部证据定下来了，不再挂"待你定"。每条都写了**依据**与**反向改动的代价**，
> 你如果想往回走，看"若要改"那一行就知道要动什么。

### §3.1 局内主次 → **P（对手 460 主 / 你 352 次）**

- **依据**：① 你说过"这个 C 真不错，就是局内稍微改一改"，P 是改动最小的那条（只把你那块从 200px 缩略图
  换成真棋盘）；② 这个游戏的动作发生在**对手海域**（你开火打的是它），保留它当焦点符合阅读顺序；
  ③ 352px 下格宽约 52px，高于项目 `MIN_CELL=40`，也高于 Apple HIG 的 44pt；④ U（我为主）的代价是
  "开火时视线要往角落跑"——那是我自己写在示意稿里的缺点，你从没认过这个代价。
- **副作用（可接受）**：手机上本来就走"一屏一块"，所以这个不对称**只在桌面体现**，手机上两块各自占满宽度，不吃亏。
- **若要改**：换 M 等大要重写宽屏 1200–1439 的留白 padding；换 U 要把对手盘缩成雷达面板。

### §3.2 用牌确认步 → **要，但按卡的类型分流**

- **依据**：① 你明确说"确认使用按钮不确定到底是好用还是不好用"；② 一手调研给出的先例是分类型的——
  Hearthstone 的"松手即生效"是为**单点**目标设计的，而本作的 神威！是 **3×3 区域**、轰炸是**整行整列**；
  ③ Hearthstone 与 Balatro **提交后都不能撤销** → 大范围目标配确认步更安全；④ Balatro 自己的主行动
  也是"先选、再按 Play 确认"。
- **具体规则**：无需目标的卡（失灵！/看破！…）保持"点两次即用"；需要目标的卡走"选完目标 → 确认"。
  按钮文案随状态变（未选目标时置灰成「请先在棋盘上选区域」）。
- **若要改**：全部退回"点两次即用"只需把那条分流判断关掉，但 3×3 误触会真发生（且不可撤销）。

### §3.3 卡牌图鉴的范围 → **先做纯前端版**

- **依据**：图鉴本身不依赖新数据（静态卡表 41 张已在 `static/magic_card.json`）；
  但"你用过 N 次 / 对手用过 N 次 / 首次见到"需要按用户聚合的统计，那是**新的服务端存储**，不该藏在 UI 批里。
- **本期交付**：网格 + 速阶/类型筛选 + 已见/未发现/选中三态 + 右栏卡面与效果全文。
- **列为可选增强**：使用次数与首次见到时间（要做的话单独开一批，含 DB 迁移照 `_add_column_if_missing` 的老规矩）。
- **若要改**：想一步到位就得先定统计口径（按账号还是按对局、是否计入人机），它会变成一批后端工作。

### §3.4 手机棋盘判据 → **改：宽度 < 560 一律走 tabs**

- **依据**：① iPhone 14 实测可用高 **763px**（844−47−34），而两块 6×6（632）+ 手牌（110）+ 顶栏（44）+ 操作（48）
  = **834 > 763**，数学上放不下；② 现在 `adaptive_layout.js` 在 390×844 上判为 `stack`（两块上下堆），
  只能靠 layout-tight/dense 硬压；③ 改走 `tabs` 后格宽反而从 ~40 升到 55；④ `#board-tabs` + `applyActiveBoard()`
  都是**现成机制**，不是新造。
- **落点**：`adaptive_layout.js` 的判据加一条"宽度 < MIN_BOARD*2+4（560）时优先 tabs"，
  即手机上不再进 `stack`；`side` 在手机上本来就不成立。
- **若要改**：保持 stack 就要接受"手机上一屏塞两块小棋盘"，并继续用 dense/tight 压。

### §3.5 卡面美术 → **不等真图，先用占位**

- **依据**：`docs/magic_card_art_prompts.md` 已经规定"美术只负责**底图**，卡名/速阶/类型由 DOM 叠"
  —— 也就是说美术与卡组件的**接口是分离的**：卡组件可以先上，底图后补。
- **本期交付**：按牌的语义给占位意象（雷达同心圆 / 火焰弧 / 断链叉 / 契约五芒…），手写内联 SVG。
- **Phase 7**：出图后按同一底图位替换，不动 DOM 与文字层。
- **若要改**：等真图会让 Phase 2 阻塞在出图上（41 张），而卡面样式与手牌手感的验证**不需要真图**。

## 4. 风险与对策

| 风险 | 症状 | 对策 |
| --- | --- | --- |
| pytest 源码字符串断言 | 改完 CSS/DOM 后测试红，但看不出与新设计的关系 | **Phase 0 先列清单**，每期只改清单内的用例并同步更新断言 |
| 布局断言重定"顺手放宽" | 新设计不满足老断言，就把断言改松 → 门禁失去意义 | 每改一条断言，在 `docs/` 写下**为什么旧口径不再适用**（照 §10.3 的写法） |
| CSS 静默坏块 | 少一个 `}` → 后面上千行规则整段失效（本项目踩过） | 每改一步就 `python tools/fluent_css_lint.py`，别只在最后跑 |
| 令牌层写死颜色 | AC6 裸 hex 超标 | 新预设的颜色只能加在令牌区，正文里一律 `var(--…)` |
| 手机改动"看着好了" | 触摸/遮挡只有量得出来 | Phase 5 每改一步跑紧凑组四档视口 |
| 卡面文字被裁/溢出 | 卡内说明框差几像素就切字（我这次踩过 4.5px） | 卡组件定尺寸后，用脚本量一遍文字盒高度，别靠眼看 |

## 5. 建议的推进顺序

```
Phase 0（半天，只出清单）
   → Phase 1（视觉层，不动盒模型 —— 这期能独立上线且 128 项断言全绿）
   → Phase 5.1（viewport-fit=cover，一行改动，先拿到"移动端不再有假留白"）
   → Phase 2 + 4（卡组件 + 目标选择：这两期是玩家最能感觉到的变化）
   → Phase 3（棋盘主次：按 §3.1 走 P）
   → Phase 5.2/5.3（手机一屏一块 + 大卡面抽屉）
   → Phase 6（其余屏，一屏一上线；图鉴按 §3.3 先做纯前端版）
   → Phase 7（卡面美术，等出图）
```

**想最快看到"像 C 了"**：Phase 1 + Phase 5.1（合计约 2 天，且都不动盒模型、不碰断言）。
**想最快看到"玩法手感变了"**：Phase 2 + Phase 4。
