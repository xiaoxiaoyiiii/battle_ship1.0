# 大厅系统（Lobby）设计与实施记录

> 2026-09-18。目标：把 `#lobby-screen` 从**空壳**做成真正的游戏大厅。
> 契约（事件名 / payload 字段 / 状态枚举）在本文件冻结；改动必须同步本文件、
> `tests/test_lobby.py` 与 `tools/lobby_check.mjs`。

---

## 0. 改造前的实测现状（为什么必须重做）

| 项 | 现状 |
| --- | --- |
| `#lobby-screen` | 有标题、一句"加入匹配队列"、一个从 `/api/online_count` 取来的数字、一个**永远填不进内容**的 `<ul id="lobby-players-list">` |
| 页面入口 | **没有任何入口**。`/lobby` 路由存在、SPA 路由也认，但首页/导航栏里没有链接（只能手敲 URL） |
| 实时性 | 零。数字只在进入页面时拉一次，之后永不更新 |
| 房间 | 看不到任何等待中的房间，只能凭 6 位房间号加入 |
| 聊天 | 只有**局内**聊天（`chat_message`，必须坐在房间里）；大厅没有公共频道 |
| 在线表 | `online_users` 是**裸 sid 集合**，没有名字 —— 想列"谁在线"根本列不出来 |

## 1. 冻结契约

### 1.1 事件（客户端 → 服务端）

| 事件 | payload | 说明 |
| --- | --- | --- |
| `lobby_subscribe` | `{player_name?}` | 进入大厅并订阅实时状态。**幂等**，重复调用不报错 |
| `lobby_unsubscribe` | `{}` | 离开大厅（不再收推送） |
| `lobby_refresh` | `{}` | 手动刷新一次状态；未订阅则顺带订阅 |
| `lobby_create_room` | `{name?, public?}` | 在大厅直接建房，ack 回 `{status, room_id, name, public}` |
| `lobby_chat_send` | `{message}` | 大厅公屏发言 |
| `close_room` | `{room_id}` | **解散自己主持的、还没开打的房**（2026-09-18 补；三条校验见 §2.6） |

### 1.2 事件（服务端 → 客户端）

| 事件 | payload |
| --- | --- |
| `lobby_hello` | `{key, name, guest}` —— 只发给刚订阅的那个连接；`key` 是它自己的身份键（当前 sid），前端靠它标"我" |
| `lobby_state` | 见 §1.3（广播给所有大厅成员） |
| `lobby_chat_history` | `{messages: [chat]}` —— 订阅时补发最近 LOBBY_CHAT_BACKLOG 条 |
| `lobby_chat` | `{key, name, message, ts}` |

> 身份键用 `key`（当前 sid）而不是 `user_id`：`lobby_state` 是一条广播
> （`to='__lobby__'`，一次 emit），不可能逐人改 is_me。前端把
> `lobby_hello.key` 存下来，渲染时自己比对。重连换 sid 时会重发 `lobby_hello`。
> 另一条路（逐人 emit 改 isMe）在局内聊天里可行，是因为**房间最多 2 人**，大厅不行。

### 1.3 `lobby_state`

```json
{
  "ts": 1758000000,
  "online_count": 12,
  "lobby_count": 3,
  "queue": {"casual": 1, "ranked": 2},
  "players": [
    {"key": "AbC123", "name": "小明", "guest": false, "in_lobby": true,
     "status": "idle", "avatar": "/static/avatars/x.png", "level": 7,
     "name_style": "", "title": "老船长",
     "rank": {"tier_id": "captain", "tier_name": "船长", "label": "船长Ⅲ 2350分"}}
  ],
  "rooms": [
    {"room_id": "ab12cd", "name": "小明的房间", "host": "小明",
     "players": 1, "capacity": 2, "created_at": 1758000000}
  ]
}
```

**status 枚举（四个）**

| 值 | 含义 | 判据 |
| --- | --- | --- |
| `idle` | 空闲 | 既不在匹配队列、也不在任何房间座位上 |
| `matching` | 匹配中 | 该 sid 在 `room_manager.match_queue` 里 |
| `in_room` | 在房间 | 坐在某个 `state == 'waiting'` 的房间里（建了房在等人） |
| `in_game` | 对局中 | 坐在某个 `state` 既不是 `waiting` 也不是 `game_over` 的房间座位上 |

> 判据顺序不能反：**matching > in_game > in_room > idle**。匹配成功后队列条目
> 立刻被 pop，matching 与 in_game 不会同时成立；但先判对局会让"刚配到、
> 还没进房"的一瞬显示成空闲。
>
> ⚠️ `in_room` 是**浏览器工具实测后补的第 4 态**：第一版把 `state != 'game_over'`
> 一律算 `in_game`，于是"按下创建房间"的人在大厅里显示成**对局中**——
> 而他们其实正闲着等人来。`waiting` 与"真开打了"必须分开。

### 1.4 房间列表的可见规则（四条，缺一条就会漏出幽灵房）

1. `state == 'waiting'`（已开局的不列）；
2. `not room.is_ai_room`（人机房列出来没意义）；
3. `room.public` 为真（**私密房只认房间号**，不列）；
4. **房主此刻仍在线**（房主 sid 在线表里）且房内恰好 1 人（可加入）；
5. **同一房主只列最新的一间**（防御层，见 §2.6）。

> 第 4 条是关键：房间的回收 TTL 是 **1 小时**（`_WAITING_ROOM_TTL`），
> 房主关掉标签页后房间还要在内存里躺一小时。不加这条就会在大厅里挂出一堆
> "点进去没人"的僵尸房。

### 1.5 常量

| 常量 | 值 | 作用 |
| --- | --- | --- |
| `LOBBY_ROOM` | `'__lobby__'` | socket.io 房间名（房间 id 是 uuid4()[:6] 十六进制，不可能撞名） |
| `LOBBY_CHAT_MAX_LEN` | 120 | 单条上限（服务端截断） |
| `LOBBY_CHAT_MIN_INTERVAL` | 1.0 s | 同一连接两条之间的最小间隔（防刷） |
| `LOBBY_CHAT_BACKLOG` | 30 | 补发给新进大厅者的最近消息条数 |
| `LOBBY_MAX_PLAYERS` | 200 | players 列表上限（按连接时间排序取前 N） |
| `LOBBY_STATE_TICK_SECONDS` | 4.0 | 兜底定时广播间隔（只在有成员时发） |
| `LOBBY_PROFILE_TTL` | 60 s | 头像/称号缓存时长（避免每次广播都查库） |

## 2. 服务端实现

### 2.1 在线表：`LobbyManager.presence` 取代 `online_users`

改造前 `online_users = set()` 是**裸 sid 集合**，没有名字 —— 而大厅必须显示
"谁在线"。新结构：

```python
lobby_manager._presence: dict[sid, {'name', 'user_id', 'connected_at', 'profile', 'profile_at'}]
lobby_manager._members:  dict[sid, {'name', 'joined_at'}]   # presence 的子集
```

**单一口径**：`/api/online_count` 改读 `len(lobby_manager.presence)`，
`online_users` 整个删除（全仓只有 4 处引用，均已改）。两个在线结构 = 两份实现
= 必然漂移（见 CLAUDE.md 通用教训二）。

`_members` 是 `_presence` 的子集：**只有真的站在大厅页面上的连接才收实时推送**，
否则每个对局中的玩家都会被大厅广播打扰。

### 2.2 广播点

`_broadcast_lobby_state()` 被这些地方调用（每条都是"列表内容真的变了"）：

- `lobby_subscribe` / `lobby_unsubscribe` / `lobby_refresh`
- `find_match` / `cancel_match`（status 变了）
- `create_room` / `join_room`（房间列表变了）
- `disconnect`（有人掉线）—— **必须放进后台任务**，不能在 disconnect
  处理器里同步 emit（eventlet 会把 hub 卡住，见 CLAUDE.md §9）

另加一个 **4 秒兜底定时广播**（`_ensure_lobby_ticker`，与 `_ensure_reaper`
同一套写法，在 `handle_connect` 里幂等启动）。它只在 `member_count() > 0` 时
才真的 emit，用于兜住"某条路径漏了 hook"的情况。

### 2.3 名字从哪来

连接建立时只有**登录用户**能拿到名字（`session['username']`）。游客的名字
是在首页输入的，直到 `find_match` / `lobby_subscribe` 才送上来。因此
`LobbyManager` 提供两个入口：

- `add_connection(sid, name, user_id)` —— `handle_connect` 调用；
- `update_identity(sid, name, user_id)` —— 后续任何拿到名字的地方调用
  （`find_match` / `lobby_subscribe` / `create_room` / `join_room`）。

名字做了清洗：去首尾空白、截断到 24 字、空串回落 `'游客'`。

### 2.4 房间名与可见性（新增房间级状态）

按项目硬规矩「新增房间级状态三件齐」：

1. **`GameRoom.__init__` 初始化**：`self.name = ''`、`self.public = True`；
2. **明确消费点**：`build_lobby_state()` 的房间列表 + `handle_create_room` 的写入；
3. **回归测试**：`tests/test_lobby.py::test_room_defaults_are_lobby_safe`。

`handle_create_room` 新增两个**可选**字段 `name` / `public`；不传时
`name=''`（前端回落成"房主名+的房间"）、`public=True`。默认公开是
**有意的**：大厅要能列房间，默认私密等于这个功能不存在。

### 2.5 大厅聊天

- 只有大厅成员能发言（`lobby_manager.is_member(sid)`），非成员静默丢弃；
- 空消息 / 纯空白丢弃；超过 `LOBBY_CHAT_MAX_LEN` 截断（**不报错**，与局内聊天同口径）；
- 频率：同一 sid 两条间隔 < `LOBBY_CHAT_MIN_INTERVAL` 时丢弃并回一条提示；
- 服务端存**原文**，转义交给前端（`escapeHtml`）——与局内聊天一致。

### 2.6 「一人一间等待房」与解散房间（2026-09-18 修复批）

**缺陷原貌**（作者截图）：大厅房间列表挂着 **7 间一模一样的房** —— 同名、同房主、
都是 1/2。复现确认「**一次点击 = 一间房**」（ack 正常、界面也正常跳到自定义房界面），
所以不是双击或重复绑定，而是**旧房永远不会消失**：

- 等待房的回收 TTL 是 1 小时（`_WAITING_ROOM_TTL`）；
- 大厅的可见规则只要求「房主仍在线」—— 而房主就是他自己，当然一直在线上。

两条规则各自都"没错"，合起来却把 7 间房全留在了榜上。

**三条修法**

1. **`_recycle_host_waiting_rooms(player_id)`**：建房前先回收自己上一间
   **`waiting` 且房内恰好 1 人且那个人就是自己**的房。规则变成
   「一个玩家同时最多主持一间等待中的房，再次建房 = 换一间」。
   ⚠️ 只回收 `waiting` 的 —— 已开打的房**绝不能**被房主一键回收（那会坑掉正在等他的对手）。
2. **`_lobby_visible_rooms` 按房主去重**（§1.4 第 5 条）：正常路径下第 1 条已经保证了一人一间，
   但历史遗留（本批上线前建的房）或日后新增的建房路径都可能绕过它 —— 列表层再兜一次，
   大厅就永远不会出现"同一个人的一串同名房"。
3. **新增 `close_room` 事件 + 自定义房界面的「解散房间」按钮**：等待房此前
   **没有任何主动出口**，建错了只能干等一小时。三条校验（少一条就是漏洞）：
   ① 房存在且仍是 `waiting`；② 房内**恰好 1 人**；③ 那 1 人就是**调用者自己**
   （用与建房同一条口径取 key：登录态 = session user_id，游客 = sid）。

### 4.2 实施中实测到的 3 个真问题

> 三个都不是靠读代码发现的，而是**跑起来才暴露**的 —— 这正是本项目"先实测再下结论"的由来。

**① 房主离线的僵尸房**（设计时就想到了，写进了 §1.4 第 4 条）
房间回收 TTL 是 1 小时（`_WAITING_ROOM_TTL`），房主关掉标签页后房间仍在内存里。
只按 `state == 'waiting'` 过滤的话，大厅会挂出一堆"点进去没人"的房间。
判据加上「房主 sid 仍在线表里」之后消失。

**② 建房者被显示成"对局中"**（★ 只有跑起来才会发现）
第一版 `_lobby_player_status` 把 `state != 'game_over'` 一律算 `in_game`。
可是**按下「创建房间」的人就坐在自己那间 `state='waiting'` 的房里** ——
于是大厅里所有开过房的人都显示"对局中"，而他们其实正闲着等人来。
`tools/lobby_check.mjs` 的「A 离开大厅后仍显示在线」那条断言把 `status` 打了出来，
一眼看到 `"对局中"` 才发现。
👉 修法：把等待房单独拆成第 4 态 `in_room`（契约 §1.3 已同步）。

**③ 公屏历史把实时消息冲掉**（★ 同一形状在 CLAUDE.md 里已经记过一次）
第一版 `lobby_chat_history` 的处理是 `clearLobbyChat()` + 重新铺一遍历史。
但**"补发的历史"与"实时推送"是会重叠的**：自己刚发的那条已经上屏了，
紧接着到的历史把整段冲掉 —— 症状是 **A 自己看不到自己的消息、B 却看得到**。
这条在第二次跑工具时才复现（第一次跑时服务端刚重启、历史是空的，所以全绿）。
👉 修法：服务端给每条消息一个单调 `seq`；前端 `applyLobbyChatHistory` **只补缺的**、
插在最前面，**绝不碰已有内容**；`appendLobbyChat` 按 `seq` 去重（历史 ∩ 实时）。
`tools/lobby_check.mjs` 里补了一条专门的回归断言（重新订阅一次，消息不许消失）。

**④ 连点「创建房间」→ 大厅堆出一串同名房**（★ 作者截图报的，见 §2.6）
上线后作者截图：大厅房间列表挂着 **7 间一模一样的房**。实测复现确认
「一次点击 = 一间房」（ack 正常、界面也正常跳到自定义房界面）—— 所以**不是**双击或重复绑定，
而是**旧房永不回收**（等待房 TTL 1 小时 + 房主一直在线，两条规则各自都没错）。
修法见 §2.6（一人一间 + 列表去重 + 解散房间出口）。

**⑤ 工具自身的一个假红**：`gridTemplateColumns` 的 computed 值是
`minmax(0px, 1fr) minmax(0px, 1fr) …`，按空格 split 会把 3 列数成 6 列。
改成数 `fr` 的个数。

**⑥ 工具自身的第二个假红（残留浏览器）**：修完第 ④ 条后重跑工具，出现两条莫名其妙的失败
（`A 自己那条标成 .me`、`B 的列表出现测试房`），而 `在线人数` 显示 **3** ——
工具只开了 2 个浏览器。原因是**上一次运行留下的 Edge 孙进程还在连着服务端**：
`proc.kill()` 只杀掉直接子进程。修法：`close()` 里也按 profile 路径做一次清理
（工具开头本来就有 `preClean`，收尾补上对称的一份）。
👉 通用：**任何"用进程清理"做隔离的工具，收尾必须和开头对称**，否则失败会以
"数据对不上"的形式出现在**下一次**运行里，而报错指向的却是被测功能。

### 4.3 视觉

`style.css` 第 30 节。宽屏三列（在线玩家 / 房间列表 / 公屏），窄屏（≤900px）单列。
在线玩家行用**两行网格**而不是一行 flex —— 三列布局下每块面板只有约 250px 宽，
一行里塞「头像 + 名字 + 等级 + 段位 + 状态徽章」时名字会被挤成"截…"（截图实测），
改成头像占左列、名字与元信息各占一行的两行网格后名字能拿满右侧剩余宽度。

颜色**零写死**（全部走 `--primary` / `--primary-rgb` / `--border*` / `--muted` /
`--glass` / `--panel-border`），因此换主题预设、切深浅色都自动跟随；
本节**没有**用 `transform` / `filter` / `backdrop-filter`（第 12 节第 12 条）。

## 5. 本批**不做**的（避免范围蔓延）

- 好友 / 私聊 / 组队；
- 大厅分页（上限 200 人，超出直接截断）；
- 房间密码（只有公开/私密两态，私密 = 凭房间号）；
- 观战 / 复盘（仍是 CLAUDE.md §11 的 P2-9/10）。
