# 大师难度 AI 设计规格（2026-09-21）

> 目标：新增第 4 档人机难度「大师」。接近人类高手但**可以赢**——会读局势、会用几乎所有手牌、会在关键节点嘲讽。
> 本文是实施前的规格。**实施时以 grep 结果为准，本文行号只是线索。**

---

## 0. 一句话

现有 AI 是「从 9 张安全卡里挑最便宜的，然后闭眼随机开炮」。大师 AI 要变成
**「读局势 → 挑最该打的那张牌 → 自己回答这张牌需要的交互 → 按情报开炮 → 打完收尾」**。

### 1.1 现状里的四个缺陷（本次一并处理）

1. **「余音绕梁」在白名单里但 100% 打空**：它要求 `current_phase=='preparation'`（9604），
   而 AI 先进战斗阶段才出牌（5310→5315）→ 每次被 `_refund_card_to_hand` 退回。
   且 `_ai_maybe_play_magic` 返回的 `True` 只表示「进了连锁」，不代表效果生效。
2. **「回光返照」让 AI 硬死锁**：`room.state='placing_ships'`（10999）且只通知施法者=AI，
   而 AI 没有摆船入口 → `enter_end_phase` / `end_turn` 全被拒 → 回合永远交不出去，真人零提示。
   「败者食尘」（9870）同构，只是可能靠真人先摆而自愈。
3. **「教皇旨意」对 AI 是自杀**：打出后 `attacks_remaining = 0`（9787），
   而 AI 完全没有「弃卡换攻击 +2」的代码。
4. **`_ai_turn_loop` 无上限、无「正在跑」标记**：40×0.3 + 20×0.5 + 20×0.5 ≈ 32s+，
   且 `_maybe_run_ai_turn` 有 4 个触发点（3067/3152/4847/5196），
   重摆棋盘后可能并发起两个 turn loop（未复现，但代码里无 guard）。

## 2. 非目标（明确不做）

- **不改 easy / normal / hard 的任何行为**。三档代码路径保持逐字不变。
- **不让 AI 作弊**。见 §4.1——这是硬约束，不是「尽量」。
- 不做多步搜索 / MCTS（信息不完全，收益配不上延迟与可测性代价）。
- 不改段位/统计口径（人机本来就不计分，保持现状）。

## 3. 架构

新增纯规则模块 **`ai_brain.py`**，与 `ranks.py` / `anticheat.py` / `match_guard.py` 同一路数：
**纯函数、无 I/O、无 socket、无全局状态**，因此可纯单测。

```
server.py  ──(仅 difficulty=='master')──▶  ai_brain.py
   │                                          │
   ├─ 出牌时机 / 回合循环（接线）              ├─ choose_card()      手牌打分
   ├─ _request_ship_pick 的 AI 分支            ├─ choose_attack()    开炮决策
   ├─ 区域/行列/格 目标                        ├─ resolve_ship_pick() 选船
   ├─ 挑牌（弃牌堆/牌堆/对方手牌/数值）        ├─ resolve_target()   选区域/行列/格
   ├─ 放置流程应答                             ├─ resolve_choice()   挑牌/数值
   └─ 嘲讽 emit                                ├─ resolve_placement() 新船放哪
                                               └─ choose_taunt()     关键节点台词
```

**为什么单独成模块**：本需求真正的风险是「AI 打出一张需要自己回答交互的牌 → 回合永久卡死」，
症状是**不报错、不掉线、只能下一局才发现**。这类 bug 只有纯函数单测能提前钉住；
把决策逻辑内联进 11,400 行的 `server.py` 等于把风险全推到线上。

`server.py` 的接线点一律写成 `if _master(room):` 一行分支，**默认路径完全不动**。

## 4. 决策函数规格

所有函数签名统一：

```python
def choose_attack(room, ai_id: str, rng: random.Random) -> tuple[int, int] | None
```

`rng` 注入而非用全局 `random` —— **为了可复现**（测试要能钉死具体招法）。
所有函数必须对残缺状态安全：拿不到必要信息时返回 `None`，由调用方兜底，**绝不抛异常**。

### 4.1 硬约束：AI 不许作弊

AI 代码跑在服务端，**理论上能看到 `room.players[opponent].ships`（对方船位）**。
一旦读了，AI 就变成全知，强度是假的，玩家也会立刻察觉。

**规章：`ai_brain.py` 只允许读「真人玩家在该座位上也能看到的信息」白名单：**

| 允许 | 不允许 |
|---|---|
| 自己的手牌 / 船 / 攻击次数 / 效果标记 | `opponent.ships` 的**位置与存活** |
| `room.players[me].revealed_positions`（自己探明的） | `opponent.magic_hand`（除「明智埋葬」按卡面**明示可见**时） |
| `opponent.remaining_ships`（界面上就显示） | `opponent.effect_flags` 里未公开的部分 |
| `room.magic_discard`（弃牌堆公开）、`magic_history` | `room.magic_deck` 的**顺序与内容** |
| `room.last_attack`、`game_logs`、场上已发生的公开事件 | `room.players[opponent].ships` 的任何遍历 |

**守卫测试（必须写）**：源码级断言 `ai_brain.py` 不出现 `opponent.ships` / `.magic_deck`
之类越权读取；再加一条行为测试——把对方船位改到不同位置、其余状态不变，
**`choose_attack` 的输出分布必须完全一致**。这条测试是「AI 不作弊」的唯一硬保证。

### 4.2 `choose_attack(room, ai_id, rng) -> (x, y) | None`

船是**单格船**（6 艘各占 1 格，6×6 棋盘），所以没有「船形推理」的余地，
情报就是全部优势。规则：

1. `known` = 自己已探明的敌船位置（`revealed_positions`）− 已轰过的格子。
   非空 → 从中挑一个（**必中**）。
2. 否则 → 在「未轰过的格子」里均匀挑。
3. 无候选 → `None`。

> 这一条单独就能明显提升强度：现状是连自己探明的位置都不打。

**现状对比**：`server.py:5334` 是 36 格均匀随机，`revealed_positions` 一次没读。

### 4.3 `resolve_ship_pick(room, ai_id, reason, rng) -> ship | None`

按**目的**分策略，替换现有的 `random.choice`：

| reason | 策略 |
|---|---|
| `demon_contract` / `divine_decree` / `dice_sacrifice` / `trap_sacrifice`（要牺牲） | 挑**信息价值最低**的船：优先挑「周围格已被对方轰过」的（对方已排除那片区域，等于没有额外信息） |
| `kraken_eye`（要被窥探） | 同上——挑泄露代价最小的，不是随机送一条 |
| `shield_choice`（仁王之盾，多选） | 优先血少/靠前的船，凑满上限 |
| `trap_setup`（守株待兔） | 挑**最可能先被打**的船（对方已探明区域附近的），让陷阱尽早触发 |

只从 `_alive_ships` 里选（沉船不能抵账，已有测试钉住：`test_alive_ship_selection.py:153-165`）。

### 4.4 `resolve_target(room, ai_id, card, rng) -> dict | None`

返回 `{'target_area': {...}}` / `{'target_line': {...}}` / `{'target_cells': [...]}` / `{'ship_indices': [...]}`，
形状必须与现有 `confirmMagicTarget` 接受的一致。

评分函数（对任意候选区域/线/连续段）：

```
score = 100 × (区域内自己已探明的敌船数)
      + 1   × (区域内未被轰过的格子数)     # 信息价值
      - 50  × (区域内自己的船)             # 神威等对己方有害的卡要反向
```

- **范围卡**（神威 / 冻结 / 探测雷达，3×3）：枚举全部 16 个位置取最高分。
- **行列卡**（轰炸）：6 行 6 列取最高分。
- **连续段**（硫磺火焰，6 格连选）：滑窗取最高分。
- **给自己船加盾/标记**（仁王之盾、守株待兔）：按 §4.3。
- 神威打**对方棋盘**时用上面的分；打**己方棋盘**时把「自己的船」权重取负。

### 4.5 `resolve_choice(room, ai_id, kind, options) -> any | None`

| kind | 卡 | 策略 |
|---|---|---|
| `wangyang_choice` | 亡羊补牢 | 从弃牌堆窗口里挑**价值最高**的那张（用 §4.7 的牌价值表） |
| `bury_choice` | 明智埋葬 | 候选含**对方手牌（卡面明示可见）**→ 优先埋掉对方**最能翻盘**的那张（按牌价值表取最大） |
| `taoyuan_choice` | 桃园结义 | 按牌面给的选项取价值最高者 |
| `lingqi_choice` | 灵气复苏 | 选数值 x：自己船多就保持自己船数，落后则在允许范围内取「对方船数 − 1」 |
| `pending_dice_discard` | 命运骰子 3 点 | 弃**价值最低**的一张 |

> 「明智埋葬能看对方手牌」是卡面明示的规则，不属于作弊。

### 4.6 `resolve_placement(room, ai_id, kind, candidates) -> (x, y) | None`

用于增援 / 死者苏生 / 滥竽充数 / 绝处逢生 / 神机妙算 re-deploy / 回光返照 / 败者食尘。

规则：**在合法候选里最大化「对方没轰过的邻格数」**——即尽量放在对方**已经轰过**的格子
（对方无法重复轰同一格，放在那里等于免挨打）。

⚠️ **实施前必须先核实每张卡对候选格的限制**（例如滥竽充数的卡面写「未被对方打过的空格」，
那就不能放已轰格）。**以各卡分支实际算出的 `candidates` 为准**，本函数只在给定候选里挑。

### 4.7 `choose_card(room, ai_id, rng) -> int | None`

返回手牌下标。分两步：

**(1) 牌价值表**：模块级常量 `CARD_BASE_VALUE`，**47 张可摸到的卡每张一个值**（不许留空）。
定标规则（不是拍脑袋，按这个推）：

```
进攻性（直接减少对方船数）  80-95   例：轰炸 90、神威！ 85、克苏鲁之眼 70
资源/手牌（换牌、抽牌）     55-75   例：无中生有 70、亡羊补牢 65
防守/续航（回血、加盾）     50-70   例：疗愈 65、仁王之盾 60、卧薪尝胆 55
条件性（需前置才能生效）    +10    在基础值上叠加；条件不成立时归零
重摆类（回光返照/败者食尘） 30-45   局面越差越加分（见下面的局势乘子）
```

完整数值表是**实现阶段的交付物**，本文只定标定规则——因为数值要靠真机对局调，
写死在规格里反而会误导。

**(2) 局势乘子** = 基础值 × 条件因子：

| 因子 | 说明 |
|---|---|
| 前置条件 | 「溅射 / 雷达子弹 / 越战越勇 / 饮血」要求 `room.last_attack` 刚命中或刚击沉 → **条件不成立时价值归零**（现状是白打退牌） |
| 阶段门禁 | 「余音绕梁 / Freezing！」只能在准备阶段 → 由调用方在准备阶段单独给一次出牌机会（见 §5） |
| 局势 | 落后时进攻卡加分、领先时防守卡加分；手牌少时「无中生有」加分 |
| 牌数预算 | 大师每回合上限 **3 张**（现状 1 张）。预算耗尽即停止出牌，避免倒光手牌 |
| 不可打 | `can_play_magic_card` 返回 False 的一律跳过 |

排序后取最高分且**严格大于阈值**的一张；没有就返回 `None`（宁可不出，也不白打）。

### 4.8 `choose_taunt(room, ai_id, event, rng) -> str | None`

- `event` 由调用方在关键节点传入，取值见 §6。
- 台词表做成**数据 + 纯函数**（照 `quick_chat.py` 的形状），每个 event 一组候选。
- **同一 event 每局最多触发一次**、**两次嘲讽间隔 ≥ 20 秒**（防刷屏）。
- 返回 `None` 表示这次不说话。

## 5. 回合循环改造

现状（`_ai_turn_loop` 5300-5366）：`进入战斗 → 出一张卡 → 等连锁 → 轰完 → 结束阶段 → 交回合`（固定脚本）。

大师改为**决策循环**（普通/困难继续走原脚本，一行不改）：

```
进入准备阶段（仅大师）
  └─ 若手牌里有「余音绕梁 / Freezing！」等仅准备阶段可打的牌 → 给一次出牌机会
进入战斗阶段
loop（最多 N 轮，N 有上限）:
  1. 若存在「等我回答的交互」（选船/目标/挑牌/放置）→ resolve_* 回答它，continue
  2. 若上一次攻击刚命中/刚击沉，且手牌里有「依赖刚命中」的卡且值得打
     → 立刻打出来，continue        # ★ 必须在下一炮之前，否则窗口就没了
  3. 若 attack 次数 > 0 → choose_attack 选一格开炮，continue
  4. 若出牌预算未耗尽，且 choose_card 认为有值得打的牌 → 打出来，continue
     # ↑ 攻击次数用尽后仍要走这一步：卧薪尝胆 / 疗愈 / 场地卡 / 抽牌
     #   都可能在没有攻击次数时依然值得打
  5. 否则 → break
结束阶段（沿用现有重试逻辑）
交回合（沿用现有重试逻辑）
```

⚠️ **顺序是本循环最容易写错的地方**：步骤 2 必须在步骤 3 **之前**。
若写成「先开炮、打完再考虑出牌」，那么每次命中后循环都会直接开下一炮，
「溅射 / 雷达子弹 / 越战越勇 / 饮血」的窗口永远被自己错过——这正是
「卡在卡池里、却永远用不对时机」的成因。

**为什么必须交错**：现在「先出一张卡、然后一路轰完」的结构下，
「溅射 / 雷达子弹 / 越战越勇 / 饮血」这些**依赖刚命中**的卡永远是废牌——
只有把出牌和开炮交错起来，它们才可能被用对时机。

### 5.1 防卡死（本设计的重点）

#### 5.1.0 现状的三个洞（已核实）

现有看门狗 `_tick_turn_timeouts`（server.py:7083）会让大师 AI 正好掉进去：

```python
7093:  if room.state != 'attacking': continue      # 回光返照把 state 改成 placing_ships → 不管
7095:  if room.is_ai_room: continue                # 「AI 自己会走完回合」→ 整类房间跳过
7114:  if (pending_placement or pending_shenji or _my_ship_picks(...)): continue   # 有待办就不催
```

**「AI 自己会走完回合」在 AI 只打 9 张无交互卡时成立；放开到 45 张时当场失效**，
而唯一的兜底还会主动跳过这些房间。所以不能只在现有看门狗里加东西。

#### 5.1.1 判据必须是「在等谁」，不是「多久没动」

⚠️ **反面设计（会毁掉真人对局）**：「房间 T 秒无状态变更就强制推进」——
这个判据**分不清「AI 卡住」和「真人正在长考」**。真人想 30 秒完全正常，
而现有代码在等待点选时**故意不催**（7114-7116 注释：「等待点选是玩家正在操作」）。
任何「全局无进展就推进」的规则都会推翻这个有意的设计，把真人正在思考的一手搅掉。

**正确判据**：

```
① 先算「这个房间现在在等谁」（responsible）：
     有待办（pending_ship_picks / pending_placement / pending_shenji）
         → responsible = 该待办的 owner
     否则
         → responsible = room.current_attacker

② 按责任方身份给**不同**额度：
     responsible 是 AI   → AI_STALL_SECONDS（默认 15s）→ 超时执行强制推进
     responsible 是真人 → **完全沿用现有 TURN_TIMEOUT_SECONDS（90s），一行不改**
```

要点：
- **真人的额度与语义一个字不动**：90 秒、每次有效操作重新计时、等待点选时不催，
  全部保留。真人想多久还是多久。
- **AI 用独立的更短额度**（新增 `AI_STALL_SECONDS`，与 `TURN_TIMEOUT_SECONDS` 分开，
  后者是给真人用的、可由环境变量配）。AI 正常 1-3 秒就动完，15 秒已非常宽裕；
  超过 15 秒只可能是卡住。
- 因此**强制推进只会在「AI 是责任方」时触发，永远不会碰真人的思考时间**。

#### 5.1.2 分层

| 层 | 做什么 |
|---|---|
| **L0** | 不卡：brain 回答所有交互（§4） |
| **L1** | AI 回合墙钟上限：`_ai_turn_loop` 加计时 + 轮次上限；超时走收尾 |
| **L2** | **`_force_advance_turn(room, why)`**：清掉阻塞项 + 推进回合，**大声记日志**。这是「直接跳过卡死」的原语 |
| **L3** | 不按 `state` 门禁：必须覆盖 `placing_ships`（自动摆船，复用 `_ai_place_ships`）与 `preparation` |
| **L4** | 责任方停滞检测（§5.1.1）：AI 责任方 15s → 强制推进 |
| **L5** | 连续 N 次强制推进仍失败 → 判和/作废对局并释放房间。**保证房间一定被释放** |

#### 5.1.3 逃生按钮：「卡住了？点这里试试」（**仅人机房**）

**定位**：这个按钮是**专为人机对战设计的**——大师 AI 放开 45 张卡后，
最可能卡住的是 AI 那一侧。**不做真人对局的救援**（真人对局的方案见 §5.1.4）。

**为什么在 AI 房里它是安全的**：AI 房间只有**一个真人**（就是请求者本人），
不存在「代另一个真人推进回合」的滥用口子。所以裁决可以很简单：

```
socket: force_continue {room_id, player_id}

  房间不是人机房        → 拒绝：「这个功能只用于人机对战」
  房间不是这个人的       → 拒绝
  责任方 == 请求者自己   → 清掉**他自己名下**的死待办，让他能继续
  责任方 == AI          → _force_advance_turn(room, 'user_requested')，推 AI 一把
  房间本身正常          → 什么都不改，返回「看起来一切正常」
```

**位置**：局内界面常驻一个小控件（底部 dock 的「日志 / 聊天」那一排），
文案 `卡住了？点这里试试`。**不做成弹窗**。
当服务端判定「责任方是 AI 且已停滞超过 15 秒」时，把这个控件**高亮**出来
（只高亮，不弹窗）。

**要点**：

- **正常状态下点它不改变任何对局状态**，所以可以放心让它常驻。
- 频率限制：同一玩家 10 秒内只能触发一次（沿用 `quick_chat` 那套限流思路）。
- 每次真正执行了修复都要 `add_game_log`，让玩家能看到「已清除卡住的状态 / 已推进电脑回合」。
- 修复后向双方 emit 一次房间同步（`game_state`），让前端从服务端真相重建，
  避免前端还挂着已经失效的弹窗。

#### 5.1.4 真人对局的卡死救援（**本批不做，留待大师 AI 落地后**）

作者定的方案：真人对局不做这个按钮，改成**超时自动行动**——
到点了就由 AI 托管：自动选船 / 自动开火 / 自动结束阶段，让对局自己往前走。
这实质上是「把卡住的那一方临时交给 AI 托管」，需要大师 AI 的决策层先存在，
所以排在 B 批之后。

**⚠️ 前置**：本批的 `_force_advance_turn` 与 `_responsible_party` 是为它打的底，
两个函数都要写成「责任方无关」的（不写死只处理 AI），将来托管直接复用。

#### 5.1.5 其余三条

1. **AI 摆放入口**：给 `_start_placement` 的 AI 分支接 `resolve_placement`，
   解开「回光返照 / 败者食尘 / 增援 / 死者苏生 / 滥竽充数 / 绝处逢生 / 神机妙算」的死锁。
2. **并发守卫**：`room.ai_turn_running` 标记 + `finally` 清理，防止重摆棋盘后
   两个触发点（3067/4847）同时起 loop。
3. **残留待办清理**：交回合前若发现 `pending_placement` / `pending_shenji` /
   `pending_ship_picks` / `pending_dice_discard` 里还留着自己的项，先由 brain 消费掉；
   消费不掉则显式清并记日志（**绝不留下没人消费的待办**）。

## 7. 无头快速模拟器与离线调权重（强度量化的前提）

### 7.1 为什么必须先有这个

**当前一局游戏要 30 秒以上**：`_ai_turn_loop` 每开一炮 `time.sleep(0.3)`（5336），
全程走 socket.io handler 与 Flask 请求上下文。跑 10⁴ 局要几天。

而这个模拟器是**三件事的共同前置**：

1. §5.1 的防卡死测试（大规模随机对局，验证「房间一定会被释放」）
2. §8 的逐卡「无残留」测试（45 张卡 × 多种局面）
3. 强度量化与离线调权重（本节）

**一份投入，三处收益**——所以它排在实施顺序第一位。

### 7.2 它是什么

一个**无 socket、无 sleep、无 Flask 上下文**的对局驱动：
直接调用对局层的纯函数（建房 → 摆船 → 猜拳 → 逐回合动作 → 结算），
双方都可以是 AI（不同难度），支持注入固定随机种子以复现。

必须具备：固定种子可复现、可只跑「某一回合的某一决策」、可批量并行。

### 7.3 强度量化（模拟器落地后立刻能做）

让**大师 vs 困难**自动对打 N 局（建议 1000 局起），输出胜率与置信区间。
**这是「大师到底强了多少」唯一的真实来源**，代替任何人的主观判断。

### 7.4 离线调权重（用进化搜索，不是强化学习）

大师 AI 的决策本身就是一组可调参数——**这就是权重向量**：

| 参数组 | 维度 |
|---|---|
| `CARD_BASE_VALUE`（45 张卡各一个值） | 45 |
| 局势乘子（落后/领先/手牌数/血量差） | ~10 |
| 出牌阈值、每回合预算、条件卡加成 | ~5 |
| **合计** | **~60 维** |

做法：
1. 固定**对手池**（现有困难 AI + 历史版本大师，防止「只赢当前自己」）
2. 每个候选权重跑 N 局自对弈，算胜率作为适应度
3. 用 **CMA-ES / 爬山** 在这 60 维上搜；10⁴–10⁵ 局对无头模拟器是可行量级
4. 胜出的权重**落成数据表**（不是模型文件），可 review、可回滚、可手改

> 这本质就是「训练」，但每一步看得懂、可复现、可回滚——与仓库现有风格一致。

### 7.5 明确不做：神经网络 / 策略梯度

三条实际理由（不是「太难」）：

1. **信息不完全性吃掉了大部分收益**——对方船位未知，拟合/搜索的收益远不如「别做蠢事」
2. **这个仓库每周都在加卡**——今天训好的网络，下一批新卡进来就得重训；
   而权重表改两个数就行
3. **不可审查**——项目每个规则模块都是可单测的纯函数。黑盒网络进来后，
   出问题只能看着它乱打

### 7.6 过度拟合警告

自对弈只能对着**自己的 AI** 调，**不等于对人类强**。
标定必须以**真人实战胜率**为准（作者本人与大师对局的战绩），
不能只看自对弈数字好看。

### 7.7 实施顺序

```
A. 无头快速模拟器 + 评测台        ← 最先做；B/C/D 的共同前置
B. 启发式大师 AI（含 §5.1 防卡死）
C. 离线权重进化搜索（自对弈）
D. 用真人实战标定
```

**强度的大头在 B（启发式），不在 C（调参）。** 现状是「闭眼随机开炮 + 有情报不用 +
条件卡永远用不对时机」，光把这三件事做对强度就上一个台阶；C 是在这个基础上追最后一截。

### 一条关于度量工具的教训

模拟器的 `ExistingAIPolicy` 原本**自己抄了一份** `random.choice(candidates)` 和
`_ai_choose_magic_card`。后果：改了真正的 AI，胜率数字**纹丝不动**
（实测前后都是 464/536）——它量的是复刻品，度量工具形同虚设。

**已修**：`choose_attack` / `choose_card` 现在委托 `server._ai_choose_attack` /
`server._ai_choose_card`（server 侧的**唯一实现**），并补了 `choose_card_targets`。

> 教训：**度量工具必须调用被测对象的唯一实现，不能复刻它**。
> 复刻出来的工具会给出"稳定但无意义"的数字，比报错更危险（CLAUDE.md 教训 #15 的反面）。

**同族再犯一次（2026-09-21 第 2 批）**：委托接上了，但**参数没接对**——
`_ai_choose_card` 新增了 `cards_played`（每回合出牌预算），驱动器不传就永远按 0 走。
更严重的是**房间级难度**：`master vs hard` 两个座位都是 AI，而房间只有一个
`ai_difficulty` 字段，于是对手也套用了大师的卡池与开炮逻辑 ——

### ⚠️ 本批踩到的三个"静默失败"（都已修 + 已加守卫）

1. **`AREA_CARDS` 从 set 改成 dict → 大师一张牌都不出。**

   兜底 `except Exception` 吞掉 → 所有卡都判成"打不了"。
   **症状完全没有告警**：被拒动作 0、卡死 0、胜率还是个正常数（43.7%）。

2. **`看破！` 没有闸门 → 大师把整套手牌逐张打出去、逐张被拒。**

3. **字段名与脏值**：亡羊补牢的确认字段是 `chosen_index`（写成 `card_index`
   只回一句"无效的卡牌选择"，看起来像 AI 挑错了牌）；

   直接比大小，而 `magic_temp_data` 与客户端字段做过合并（白名单挡键名、不挡类型）
   → 脏值让 `int > str` 抛 TypeError，而这在回合循环里就是**永久卡死**。
   → 两处都修了，并补 `test_ai_consume_own_choice_never_raises` 用残缺状态逼一遍。

> 教训：**"兜底 except" 与"零被拒动作"合起来会制造假象**。
> 判断"AI 到底有没有在工作"，不能只看"有没有报错/卡死"，

**① `绝处逢生`：从"打中即胜"里算不出便宜。**
卡面是「牺牲全部战舰 → 放 1 艘 → 接下来击沉对方即胜」，看上去是绝境翻盘神器。
闸门已经收得极紧（**只在对方只剩 1 艘时才打**），实测**仍然在扣分**：

```
带着它   68.5%
去掉它   71.9%     ← 同一批 1000 局
```

原因：对方剩 1 艘时，我本来有 **5~6 次攻击机会**，命中率随次数累积；
牺牲掉全部战舰之后只剩 **1 次**攻击、且必须打中对方那唯一一格 ——
等于**把已经很高的胜率换成 1/36 的抽奖**，而且自己只剩 1 艘，
对方下一次反手就结束。**"击杀即胜"的收益被"只剩一发"的成本吃光了。**

**② 牺牲哪艘船：我写的"更讲道理"的启发式没有变得更好。**
我原本的判据是"邻里被轰过的格数最多 → 泄露代价最小 → 该牺牲"。
我把它改成"周围一格都没被搜过的船最不该牺牲"（听起来显然更对），

```

```

→ 回退到旧版，并把两版都留在 `tools/master_ablation.py` 的
  `ship_old` / `ship_new` 里，随时可复测。**"讲得通"不等于"更强"。**

4. 目标 ≥ 80%：当前 71.2%

> 关于 80%：本批只有 +1.0，而**排除了两张"看起来更强"的卡**。
> 剩下的空间已经不在"多开几张卡"上（34 张里每张都量过是正收益），
> 更可能在**决策质量**上：例如 `choose_attack` 仍然只按"已探明/未打过"二分，
> 没有利用对方**攻击历史的分布**（哪里被打得多 = 那一片他探过）。
> 这是下一步值得试的方向，但它属于"调模型"而非"调权重"。

## 13. 验收标准

1. ★ **大师 AI 能连续打完 ≥ 20 个回合一次不卡死**；且**坏 brain 逃生测试**通过

6. 「AI 不作弊」两条守卫测试通过。
