# 移动端自适应布局（紧凑模式）

> 2026-09-12。修复「对局界面在手机上不可用」的一批缺陷。
> 证据口径：无头 Edge（CDP）+ 已在运行的服务端，实测 6 个视口。

---

## 1. 问题（实测，不是推测）

对局界面原本是**桌面多浮窗**范式：日志（`.log-container`）、局内聊天
（`.in-game-chat-container`）、卡牌预览（`.magic-card-preview`）三个
`position: fixed` 窗口盖在一条长文档上，断点阶梯（1439/992/768/600）
**只改尺寸、从不改结构**。等比压到手机上就出现下面这些问题。

修复前（`node tools/ui_layout_check.mjs` 红基线：**32 项不通过**）：

| 视口 | 文档总高 | 首屏内棋盘可见 | 滚到棋盘后被浮窗盖住的格子 |
| --- | --- | --- | --- |
| 320×568 | 1728px | **0%** | **36/36（全部）** |
| 336×664（截图机型） | 1760px | **0%** | 12/36 |
| 390×844 | 1868px | 12% | 5/36 |
| 430×932 | 1874px | 0% | 24/36 |
| 664×336（横屏） | 1908px | 0% | 8/36 |

其它实测项：

- **浮窗互相叠压**：日志 ∩ 魔法卡预览 = **273×181**；聊天 ∩ 阶段卡 = **337×123**；
  日志 ∩ 投降按钮 = 55×19。宽屏（≥1440）下这些重叠为 0，说明问题出在"范式没换"。
- **玻璃互相采样**：两个浮窗都带 `--glass` + `backdrop-filter: blur(10px)`，
  叠在一起时上层把下层糊成一片（用户截图里魔法卡面板中央那团白雾就是它）。
- **手牌够不着**：`#magic-system` 由 `createMagicCardUI()` 追加到 `#game-screen` 末尾，
  实测落在 **y≈1577**（视口高 664），比棋盘还靠下——每回合要用的东西要滚两屏。
- **触摸目标不足**：棋盘格 320px 下 20.3px、336px 下 35px；`#toggle-log` 13×17、
  投降按钮 64×37、阶段按钮 134×39。
- **移动端原语缺失**：`dvh` 0 处、`env(safe-area-inset-*)` 0 处、`@container` 0 处、
  `orientation` 媒体查询 0 处、`pointer: coarse` 0 处。
- **空状态浪费**：「未选择魔法卡」占 220px（首屏 33%），而首屏里棋盘出现 **0 次**。

## 2. 设计

**按可用空间，而不是设备类型选布局。** 由 `static/adaptive_layout.js` 计算后
在 `body` 上打类，CSS 只负责渲染：

| 模式 | 触发条件 | 布局 |
| --- | --- | --- |
| `wide` | 宽 ≥ 1200 **且** 高 ≥ 700 | 维持原有桌面浮窗布局，一行不动 |
| `compact` | 其余情况 | 一屏网格：HUD / 棋盘舞台 / 手牌 / 面板槽 |
| `layout-tight` | compact 且 高 ≤ 480（横屏手机） | 棋盘独占左列，HUD 与面板槽做成右列 |
| `layout-dense` | compact 但舞台塞不进最小棋盘 | 常驻手牌条收进面板槽，高度让给棋盘 |

紧凑模式下**页面本身不滚动**（`overflow: hidden` + 高度取自 `visualViewport`），
每个区域各自内部滚动，因此棋盘不可能被挤出首屏：

```
┌─ HUD ──────────── 回合 / 投降 / 双方剩余战舰 / 阶段按钮 ─┐  auto
├─ 棋盘切换条 ───── 仅当舞台放不下两块棋盘时出现 ──────────┤  auto
├─ 棋盘舞台 ─────── 尺寸由可用空间反推，永不被覆盖 ─────────┤  1fr
├─ 手牌条 ───────── 常驻、横向滚动（dense/tight 时收进面板槽）┤  auto
└─ 面板槽 ───────── 卡牌详情 / 日志 / 聊天 三选一 ─────────┘  auto
```

**三个浮窗搬进面板槽三选一**，所以在物理上不可能再互相叠压，也不可能压到棋盘。

### 关键实现点

- **DOM 搬家可逆**：`applyPlacement()` 在进入紧凑模式时把 `.log-container`、
  `#in-game-chat-container`、`#magic-card-preview`、`#magic-system`
  以及两个头像角标移入面板槽 / HUD；回宽屏时按进入前记录的 parent + nextSibling 精确还原。
  实测 1600×1000 下三者重新变回 `fixed`、面板槽 `display:none`、手牌回到 `#game-screen`。
- **棋盘尺寸反推**：`updateBoardMode()` 依次尝试 `side`（左右并排）→ `stack`（上下堆叠）
  → `tabs`（我的/对手切换），取第一个能保证格子 ≥ 40px 的方案；
  `--board-size` 只锁宽度，高度由 `.cell` 的 `aspect-ratio` 反推，**格子永远是正方形**
  （同时锁 height + max-height 会在舞台变矮时压成扁格子）。
- **面板槽展开不能让棋盘饿死**：`clampDockHeight()` 按"展开后棋盘仍拿得到最小尺寸"
  反推 `--dock-max`；展开时手牌条同时收进卡牌页，把高度让出来。
- **触屏停用拖拽浮窗**：`window.__adaptiveDragDisabled` 让两个拖拽工厂在开始时退出。
  这不只是体验问题——`makeFloatingDraggable` 的 resize 回写会拿"流内 rect"当坐标，
  把宽屏下的浮窗位置写坏（表现为聊天框跑到左上角），因此 resize 回写也必须跳过。
- **它屏不受影响**：所有布局规则都挂在 `body.layout-compact.layout-ingame` 下，
  登录/大厅/排行榜照旧。

## 3. 验证

```bash
# 端到端：宽屏 9 项 + 6 个紧凑视口的 9 项 + 面板槽展开后再 4 项
node tools/ui_layout_check.mjs --shots .tmp-shots

# 前端契约（HTML/CSS/JS 三处必须同时成立）
python -m pytest tests/test_mobile_adaptive_layout.py -q
```

`ui_layout_check.mjs` 的紧凑组不变量（每个视口都跑）：

1. 无水平溢出；
2. 对局页**不产生纵向滚动**（`scrollHeight <= innerHeight + 2`，"一屏"）；
3. 至少一块棋盘可见；
4. **棋盘格子零遮挡**（逐格 `elementFromPoint` 命中自身）；
5. 格子尺寸 ≥ 触摸下限（视口高 < 420 时为 36px，见下）；
6. 棋盘整体落在视口内，不需要滚动；
7. 面板之间零叠压（排除包含关系——面板槽里装着日志/聊天/手牌）；
8. 可点元素均不小于触摸下限；
9. 手牌够得着（常驻手牌条在视口内，或收在面板槽的卡牌页里）；
10. 展开面板槽后，3~7 仍成立。

修复后：**全部通过**（修复前红基线 32 项不通过）。

## 4. 有意的取舍

- **336×664 这类机型上只能同时看到一块棋盘**，自动切换：轮到我方时显示对手棋盘
  （要打的那块），轮到对手时显示我方棋盘（要看被打的那块），手动切换保持到下次轮次变化。
  实测 430×932 及以上可同时显示两块（上下堆叠，43~48px 格子），
  768×1024 可左右并排（52px 格子）。
- **视口高 < 420 时触摸下限放宽到 36px**：336px 高的横屏下，
  6×6 棋盘即使占满整列也只有 ~40px，再留任何 chrome 都到不了 40px。
  紧凑模式下横屏走"棋盘左列 + HUD/面板右列"，实测 46px 格子，已优于竖屏。
- **紧凑模式下隐藏自己的昵称**（保留对手昵称）：两个"头像 + 昵称 + 剩余 N 艘战舰"
  chip 在 320~336px 宽下必然换行，白吃一行高度；自己叫什么自己知道。
- **"查看对手战绩"从 HUD 挪进日志页**：它会把对手 chip 挤成两行（文字叠字），
  又是个低频入口。
- **宽屏阈值 1200×700 不是设备判断**，而是"桌面浮窗 + 900px 主列"放得下的下限。
