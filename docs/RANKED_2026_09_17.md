# 段位系统 + 排位模式（2026-09-17/18）

> 作者原话（逐条）：
> 「做一个段位系统。段位名字用**二级水手 / 一级水手 / 水手长 / 三副 / 二副 / 大副 /
> 轮机长 / 船长 / 大舰长**这九个，前八个每个再分 Ⅰ Ⅱ Ⅲ 三个小段位（Ⅰ 最小 Ⅲ 最大）。
> **每个小段位提升需要 100 排位积分**，比如赢了加 20 分，水手长Ⅱ90分 → 水手长Ⅲ10分。
> 大舰长要先到船长，而且在船长段位里排名前 50 才能升。船长和大舰长要能显示全服排名
> （船长Ⅲ1200分#60 这样，大舰长就 #20）。个人信息里要显示段位，加一个
> **是否允许别人查看我的段位** 的开关。排行榜页再加一个**段位榜**，
> 记得突出段位高低。每个段位要有自己的图标，**段位越高需要越精致越高级**。
> 段位越高也解锁更多的名片底色/头像框/称号，你刚好也新增一些。」

本文档 = 设计稿 + 冻结契约 + 实施记录。**冻结契约部分（§2~§7）改了要同步改代码注释**。

## 1. 段位规则（唯一真相源 = `ranks.py`）

| # | 段位 | id | 起始分 | 小段位 |
| --- | --- | --- | --- | --- |
| 1 | 二级水手 | `sailor2` | 0 | Ⅰ 0-99 / Ⅱ 100-199 / Ⅲ 200-299 |
| 2 | 一级水手 | `sailor1` | 300 | 同上（每级 300 分） |
| 3 | 水手长 | `bosun` | 600 | |
| 4 | 三副 | `mate3` | 900 | |
| 5 | 二副 | `mate2` | 1200 | |
| 6 | 大副 | `mate1` | 1500 | |
| 7 | 轮机长 | `engineer` | 1800 | |
| 8 | 船长 | `captain` | 2100 | 船长Ⅲ 从 **2300** 起，往上只累分 |
| 9 | 大舰长 | `admiral` | —— | **晋升制，没有分数段** |

- 一个小段位 = 100 分，一个段位 = 3 小段位 = **300 分**。
- 赢 **+20** / 输 **−15** / 最低 **0 分**（封底）。
- 作者给的例子「水手长Ⅱ90分 → 水手长Ⅲ10分」= 全局 **790 → 810**。
  ⚠️ **`label` 里的"90分"是"本小段位内已攒的分"（`progress`），不是全局分**。
  这两个数差着两个小段位，实施时第一版测试就把它当成 690 了（见 §9.1）。
- **船长Ⅲ 之上不再变形**：继续累分、进度条单调增长。
  ⚠️ 第一版小段位用 `% 3` 算，于是 2700 分被算成**船长Ⅱ**、3000 分算成**船长Ⅰ**
  （分越高段位越低）。现在 `sub_index()` 在顶段饱和在 Ⅲ。
- **大舰长**：`can_promote_to_admiral(points, captain_pool_rank, pool_size)` 三个条件全满足：
  ① 已到船长段；② **船长池内**排名 ≤ 50（`ADMIRAL_RANK_LIMIT`）；
  ③ 船长池人数 ≥ 50（`ADMIRAL_MIN_CAPTAINS`）。
  - ③ 是**护栏**：本项目玩家基数还很小，没有它的话"池子里只有 3 个人，人人排名 ≤ 50"
    → 注册即大舰长，这个段位就没意义了。**今天没有任何人能到大舰长**，这是预期的。
  - `ADMIRAL_STICKY = False` → **动态**称号：条件不再满足会掉回船长。
- **两个"排名"是两回事**（别混）：
  | 用途 | 取值 | 口径 |
  | --- | --- | --- |
  | **晋升判定** | `captain_pool_rank` | 只在船长池（积分 ≥ 2100）里排 |
  | **展示文案** | `server_rank` | 全服所有打过排位的账号里排 |

### 1.1 文案（`rank_view(...)['label']`，前端**直接用，不许自己拼**）

| 情况 | 文案 |
| --- | --- |
| 普通段位 | `水手长Ⅱ 90分`（进度分） |
| 船长 / 船长Ⅱ | `船长Ⅲ 2300分 #60`（累计分 + 全服排名） |
| 大舰长 | `大舰长 #20`（不带分数） |
| 没打过排位 | `二级水手Ⅰ 0分`，`server_rank` 为 `None`（**不许出现 `#0`**） |

## 2. 段位数学的唯一真相源

和 `leveling.py` / `achievements.py` 同一条规矩：**规则只有一处实现**，
服务端算好、前端只渲染。`ranks.py` 是纯模块（只依赖 stdlib），所以
`db.py → ranks` 与 `profile_spec.py → ranks` 这两条依赖都没有环。

对外 API：`tier_of_index` / `tier_by_id` / `normalize_points` / `apply_delta` /
`sub_index` / `progress` / `points_tier_index` / `rank_view` / `solve_delta` /
`can_promote_to_admiral` / `is_admiral` / `constants` / `tier_floor`。

⚠️ **前端不许重算曲线**：`progress` / `to_next` / `label` / `tier_id` 一律吃服务端给的值。
理由与"同一个业务判断有两份实现一定会漂移"（`CLAUDE.md` §11 通用教训二）完全相同。

## 2.5 每局加减分：多因子（2026-09-18 作者要求「变得和经验一样」）

> 作者原话：「可以把加分机制改一改 变得和经验一样就是很多因素都可以影响这一局的加分扣分多少
> 比如说连胜 终止连败 闪电战这种的」。
>
> 结构与 `leveling.py` **逐条对齐**：`base` + 一串 `bonuses`（明细），
> **`total == base + sum(bonuses)` 有断言保证**，明细与总数永远对得上。

### 胜局

| key | 标签 | 值 | 条件 |
| --- | --- | --- | --- |
| `base` | 胜利 | **+20** | 恒定 |
| `win_streak` | 连胜加成 | **+2 × N**（封顶 +10） | N = 本局是第几连胜（含本局），N ≥ 2 才给 |
| `streak_break` | 终止连败 | **+8** / **+12** | 终结 2~3 连败 / ≥4 连败 |
| `blitz` | 闪电战 | **+6** | ≤180 秒 **或** ≤5 个大回合 |
| `flawless` | 零伤获胜 | **+8** | 自己一艘船都没沉 |
| `sinks` | 击沉 N 艘 | **+1 × 击沉数**（封顶 +6） | |
| `upset` | 越级挑战 | **+6** / **+10** | 对手段位高 1~2 段 / 高 ≥3 段 |

满配 = 20+10+12+6+8+6+10 = **+72**。

### 败局（负值基础 + 减免）

| key | 标签 | 值 | 条件 |
| --- | --- | --- | --- |
| `base` | 失败 | **−15** | 恒定 |
| `brave` | 虽败犹荣 | **+5** | 击沉 ≥5 艘 |
| `underdog` | 输给高段位 | **+5** | 对手段位高 ≥2 段 |
| `pity` | 连败保护 | **+4** / **+7** | 本局是第 3~4 连败 / ≥5 连败 |
| `fast_loss` | 速败减免 | **+3** | ≤180 秒落败（快速局不重罚） |
| `cap` | 减免上限 | 负值补平 | 败局最终 delta **不低于 −5** |

⚠️ **必须有 `cap` 这一行**：减免项最多能加 +20，会把 −15 顶成**正数**
（输一局反而加分）。所以败局的总量封在 −5，超出部分用一行显式的负值补平 ——
**「明细加起来 == 总数」这条不变**，而不是偷偷把某个 bonus 改小
（那样明细就撒谎了）。0 分封底仍然在更外层生效。

### 哪些数从哪来

| 因子 | 来源 |
| --- | --- |
| 连胜 / 连败 | ⚠️ **必须在 `record_match` 之前取**（见下） |
| 用时 / 大回合数 | `room` + `_match_started_at(room)` |
| 双方沉船数 | `_alive_ships()` 口径（**不是** `len(player.ships)`：沉船不移出列表） |
| 双方段位 | `ranks.points_tier_index(db.get_user_rank_row(uid)['points'])` |

⚠️ **★ 取数顺序是这条功能的命门**：`users.current_streak` 只数**连胜**
（输一局会被清零），而且 `_finalize_match` **先**调 `record_match`（它会把这一局
算进连胜、把败者的连胜清零）**后**才结算段位。所以"本局之前的连胜/连败"必须在
`_finalize_match` **开头**取好（那时库里还是赛前状态），否则读到的是**含本局**的值 ——
表现为"第一局胜利就显示 1 连胜加成"，而且**不报错**。
连败没有单独的列，从 `matches` 表按 timestamp 倒着数连续负场（同样要在写库前数）。

### 下发给前端的形状（在原有 `rank_changed` 上**追加**）

```python
{
  ...原有字段（role/delta/clamped/points_before/points_after/before/after/...）...,
  'base': int,                           # 基础分（+20 / -15）
  'bonuses': [{'key','label','value'}],  # 明细（label 是给玩家看的中文，服务端给）
  'breakdown_total': int,                # base + sum(bonuses)（封底之前）
  'segments': [...],                     # 进度条动画路径（与 leveling.segments 同形）
}
```

`segments` 由服务端给的理由与等级系统完全相同：**进度条这条"曲线"只能有一份实现**，
前端只管按段播动画（一段一个 `from → to`；走满的那段 `sub_up=True`，前端在那里播
"条子重置后继续涨"）。

### 规则快照（帮助页与结算面板都吃这一份）

`ranks.scoring_table()` → 上面两张表的机器可读版本（含 `label` / `value` / `condition`
自然语言），并挂在 `ranks.constants()['scoring']` 上。
**帮助页与结算面板都从它渲染，不在 HTML 里硬编码任何数字** ——
否则"帮助里写 +20、代码里是 +25"这种漂移迟早出现（本项目通用教训二）。


### 3.1 新表 `user_rank`

```sql
CREATE TABLE IF NOT EXISTS user_rank (
    user_id       TEXT PRIMARY KEY,
    points        INTEGER NOT NULL DEFAULT 0,
    is_admiral    INTEGER NOT NULL DEFAULT 0,   -- 只作审计痕迹；判定是动态复算
    ranked_wins   INTEGER NOT NULL DEFAULT 0,   -- **只统计排位局**
    ranked_losses INTEGER NOT NULL DEFAULT 0,
    updated_at    INTEGER
)
```

- **不存"段位名"**：存一份就会漂移（分数改了段位没改）。等级/小段位/进度全部现算。
- 索引：`idx_user_rank_points(points DESC, updated_at)`（榜序）、
  `idx_user_rank_points_asc(points)`（数船长池人数）。

### 3.2 排序口径（**三处共用，必须一致**）

```
ORDER BY points DESC, COALESCE(updated_at, 0) ASC, user_id ASC
```

后两段是**定序用**的：同分时"先到的排前面"稳定，不会随查询计划抖动
（否则同分玩家的 `#60`/`#61` 会来回跳，看着像 bug）。
全服名次用 `COUNT(*)` 算严格在前的行数 + 1，所以**榜外（100 名之后）也算得出名次**。

### 3.3 `show_rank` 加列迁移（第 5 个展示开关）

`user_profile` 是第 1 批建的表，生产库已有行 → `CREATE TABLE IF NOT EXISTS` 是空操作，
只能 `PRAGMA table_info` 先判存在再 `ALTER TABLE ADD COLUMN`（`_add_column_if_missing`）。
默认 **1 = 公开**。这类失败只记日志不外抛（`init_db()` 在 import 期跑）。

### 3.4 DAO

`get_user_rank_row` / `get_rank_map` / `add_rank_points` / `set_rank_points` /
`ranked_leaderboard` / `count_rank_at_least` / `captains_ordered` /
`get_rank_position` / `get_rank_position_map`，**类方法与模块级包装成对存在**
（本项目按模块级名字打桩，只写类方法会被绕过 —— 第 2 批为此吃过假红）。

⚠️ `get_rank_position`（段位名次）与既有的 `get_user_rank`（战绩榜名次，按 wins）
**不是一回事**，名字刻意错开。

### 3.5 `add_rank_points` 的两个坑（都踩过）

1. **`excluded.points` 已经被夹过**：SQL 写成
   `points = MAX(0, user_rank.points + excluded.points)` 时，若 `VALUES` 里是
   `MAX(0, ?)`，负分在插入前就被夹成 0 → **"减分"等于没减**（只有胜负场次在涨）。
   正确写法是**绑两次 delta**：`VALUES(..., MAX(0, ?), ...)` 给首次建行用，
   `ON CONFLICT ... points = MAX(0, user_rank.points + ?)` 用原始 delta。
2. **0 分封底要在 SQL 里做**（`MAX(0, ...)`），不能只在 Python 里判 —— 并发下会漏。

## 4. 排位模式（`server.py`）

### 4.1 配对

- `find_match` 的 payload 增加 `mode`：`'casual'`（默认）或 `'ranked'`，非法值当 `casual`。
- `RoomManager.match_queue` 的**队列条目多一个 `mode` 键**，只在同 mode 之间配对。
  ⚠️ **订正一条长期过期的描述**：`CLAUDE.md` §4 写的是「三列平行数组
  `[sids, names, user_ids]`」，那是 **2026-09-11 之前**的形状；现在它是
  **单结构列表**（每项一个 dict `{'sid','name','user_id'}`），2026-09-11 的有序性
  修复就是为了消灭"平行数组漏改一个使用点 = 错位"。所以本次是**给 dict 加键**，
  不是"3 列变 4 列"；分工时按旧描述写会白走一圈。
  即便如此，使用点仍要逐个表态：入队 / 出队 / 同账号去重 / 取消 / 配对扫描。
- **只在同 mode 之间配对**。
- **排位必须登录**：未登录排位 → emit `error`，文案 `'排位模式需要先登录'`；休闲局游客照旧可排（别误伤）。
- `room.ranked` 在 `GameRoom.__init__` 初始化（新增房间级状态三件齐：初始化 + 消费点 + 回归测试）。
  自定义房 / 人机房恒 `False`。`mode` **不另存一份**，由 `ranked` 推出来（避免两份状态漂移）。
- `game_state` 与 `_build_room_sync`（重连快照）都带 `ranked` / `mode`
  —— 重连后不知道自己在打排位，结算表现就会错。

### 4.2 结算门槛（三条全满足才加减分）

```
room.ranked  AND  count_stats  AND  _match_really_started(room)
```

⚠️ **`_match_really_started` 不是 `_match_started_at`** —— 后者在
`room.match_started_at` 缺失时会**退回 `room.created_at`**（建房时间，含"等人入座"），
而 `created_at` 是 `GameRoom.__init__` 无条件打的点，所以对**任何真实房间**
`_match_started_at(room)` **恒非 0**，拿它当门禁等于**没有门禁**。
`_match_started_at` 那个回退是给"闪电战用时"用的（它自己注释里写了）。

漏掉这一点的后果不是"少给分"，而是一个**刷分口子**：两个账号匹配成功后
**在摆船阶段直接投降** → 对手立刻白拿 +20，反复刷就能刷到船长段。
所以门禁只看**显式的开打打点** `bool(getattr(room, 'match_started_at', None))`
（该点由 `handle_rps_choice` 在猜拳结束、真正进 `attacking` 时打）。

**★ 这条教训值得单独记**：一个"会兜底"的取数函数，和"这个事实到底成不成立"
**不是一回事**。本项目在壁纸批已经吃过同形状的一次（兜底取"目录里最大的媒体文件"
把 `preview.jpg` 挑出来冒充动态壁纸）。**凡拿兜底函数当判据，先问：兜底值会不会让判据恒真？**

| 场景 | 给分？ | 理由 |
| --- | --- | --- |
| 排位局正常打完 | ✅ | |
| 猜拳结束（真开打）后中途投降 | ✅ | 否则"打不过就拔线"变成免责 |
| **赛前投降**（还在摆船 / 猜拳没完） | ❌ | 还没真开打；堵"匹配即投降"的刷分口子 |
| 休闲局 | ❌ | 不是排位 |
| 人机局 | ❌ | 打电脑不能刷段位（与"人机不计 `users.wins`"同一条口径） |
| 自定义房 | ❌ | 可以互刷 |

结算仍然**收口在 `_finalize_match` 一处**（第 2 批已经收口，这里只追加一段）。

### 4.3 事件 `rank_changed`（逐字）

结算后给**每个真人玩家单独** emit：

```python
{
  'role': 'winner' | 'loser',
  'delta': int,                 # **实际**变化量（封底时小于 -15）
  'clamped': bool,              # True = 撞到 0 分封底
  'points_before': int, 'points_after': int,
  'before': {...rank_view...}, 'after': {...rank_view...},
  'promoted': bool, 'demoted': bool, 'tier_up': bool, 'tier_down': bool,
  'admiral_promoted': bool, 'admiral_demoted': bool,
  'admiral_reason': str,        # 中文原因（没晋升时说明还差什么）
}
```

- `before` / `after` 是 `ranks.rank_view()` 的**原样返回**，其中 `server_rank` 用
  **结算之后**再取的 `db.get_rank_position(uid)`。
- ⚠️ **必须先读旧分再写**，且 `after` 要**重新读库**得到，不许用 `before + delta` 算
  （0 分封底时那样算是错的）。
- `clamped` 取自 `ranks.apply_delta(before, delta)` 的第二个返回值。
- 大舰长晋升要**两个玩家都写完分之后**再统一算一次船长池（否则先写的那个看到的是旧池子）。

### 5.1 隐私的两条边界

1. `show_rank = 0` 时，**别人**读到的 `rank_info` 是 `None`（不是空 dict —— 那会让前端
   画出「二级水手Ⅰ 0分」这种假信息）。**本人永远看得到自己的段位。**
2. ⚠️ **段位榜不理会 `show_rank`**：榜是公共竞技数据，关掉"段位公开"之后**仍然在榜上**。
   这是有意的产品决定（作者只说了"是否允许别人查看我的段位"，指的是个人信息里那块）。

> **第 3 批的硬教训在这里复用**：隐私过滤只有服务端拦得住，前端断言会假绿。
> 所以测试必须**以别人的身份直接读接口**，而且**两侧都要断言**（主人看得到 / 别人看不到）。

### 5.2 `rank_info` 的形状 = `ranks.rank_view()` 的原样返回

`tier_id` / `tier_name` / `tier_index` / `sub` / `progress` / `points` / `to_next` /

### 9.0 协议级 e2e 抓到的四个真问题（**比单测有价值**）

`.tmp/rank_e2e.py`（真实服务端 + 真实 socket + **真登录**：HTTP 登录拿 session cookie，
再把同一个 cookie 交给 socket）跑出来 26 项。它抓到的东西是 pytest 测不到的：

1. **★「会兜底」的取数函数不能当判据**（详见 §4.2）。`_match_started_at(room)` 会退回
   `room.created_at`，而 `created_at` 无条件存在 → 门禁恒真 → **赛前投降照常给分**，
   也就是"匹配成功立刻投降"可以把分刷给对面。红基线实测：败者 100 分投降后变成 **85**
   （`assert 85 == 100`）。改成只看显式打点 `_match_really_started` 后三条验收用例全绿。
   👉 **凡拿兜底函数当判据，先问：兜底值会不会让判据恒真？**
2. **★ `test_win_game` 调试桩不结算**：它只设 `room.state/winner` 再 emit `game_over`，
   **不调 `_finalize_match`** → 返回 success 却一分不加、一条 `rank_changed` 都不发。
   用它验"打完一局给分"会得到"成功但没反应"，而且**看不出原因**（这正是一类最难查的假绿）。
   真正走结算的路径是**炮击击沉 / 投降 / 掉线判胜**。e2e 改用**投降**之后一次通过。
3. **匹配房的 `player_id` 必须用服务端下发的值**，不能用客户端自己的 `sio.sid`：
   实测两者**不同**（`sio.sid=AnZno3aiv_SBf8FtAAAG` vs 服务端 `player_id=DfFh0YNSvJL9xZERAAAH`）。
   用错的表现是 `place_ships` / `test_win_game` 全报"无效的房间或玩家"，
   于是"赛前投降不给分"那条**假绿**（什么都没发生，分数当然没变）—— 与第 2 条同一种假绿。
4. **0 分封底时 `delta` 是 0，不是 −15**：`delta` 按契约填**实际**变化量
   （`after - before`），所以败者在 0 分时输一局拿到的是
   `{delta: 0, points_before: 0, points_after: 0, clamped: true}`。
   ⚠️ **前端不许直接渲染 `delta`**（会显示「±0」）：`clamped && delta === 0` 要显示
   「已到 0 分下限，本局未扣分」。这一条已同步给前端。

另外两条 e2e 自己的坑（记下来免得后人重踩）：`place_ships` 的形状是
`[{'positions': [{'x':..,'y':..}]}]`（不是 `[{'x':..,'y':..}]`，错了报"战舰缺少位置信息"）；
猜拳**两边必须出不同的手**，都出 rock 会永远停在"平局，重新猜拳"、对局永远进不了
`attacking`。而猜拳阶段服务端**只推 `rps_result`、不推 `game_state`** ——
判"有没有进 attacking"要连 `rps_result` 一起看。

#### ★★ 抓到一个"语义写反"的真 bug：终止连败看错了人

`loss_streak_broken` 第一版直接取**败者**赛前的连败数，注释还写了"两个名字是同一份事实的
两种读法"。**这个推理是错的**：「终止连败」讲的是**胜者自己**之前连了几场败、这一局把它终结了。
写反之后两个方向都错：

* 打赢一个正在连败的人 → 胜者白拿「终止连败」；
* 真正自己止住连败的人 → 一分没有。

而且**不报错**：`base + Σbonuses == total` 这条恒等式照样成立（它只管加总，不管每项对不对）。

**它是怎么被抓到的**：写了一条**真实 socket 连打三局**的探针（`.tmp/rank_streak_probe.py`），
打印每局的明细分项 —— 期望看到"局1 首胜无连胜加成 / 局2 有连胜加成 / 局3 有终止连败"。
实测：
```
局 2 胜者: base +20 ｜ 2 连胜 +4、闪电战 +6 ｜ 合计 +30
局 3 胜者: base +20 ｜ 闪电战 +6 ｜ 合计 +26      ← 该出现「终止连败」却只有闪电战
```
修掉之后局 3 变成 `base +20 ｜ 终结连败 +8、闪电战 +6 ｜ 合计 +34`。

**★ 教训（比这个 bug 本身重要）**：**"两个名字是同一份事实的两种读法"这种自我说服，
一定要落到"这两个名字分别属于谁"上再验一遍。** 上一个批次刚在"活船/死船"上吃过同形状的
苦（同一个口径在多处复用，答错不报错只算错）。这次的判别方法很便宜：
**把两个玩家的数分别打印出来**（胜者的连败数 vs 败者的连败数），一眼就能看出反没反。
回归测试：`test_streak_break_is_the_winners_own_losing_streak` +
`test_beating_a_losing_player_gives_the_winner_no_streak_break`（正反两条都钉住）。

#### 其余实施中发现的问题

1. **`round` 从 1 起 → `blitz` 的「≤5 大回合」判据几乎每局都成立**。
   这本身不算 bug（一局只打了一个大回合确实是速胜），但它让
   `tests/test_ranked_match.py` 那些"干净一局 == +20"的旧断言全红（落库 126 而非 120），
   且**报错信息指向不了原因**（其中一条是间接失败：用 `CAPTAIN_FLOOR - 1 + WIN_POINTS`

#### ⚠️ 工具假红一条：**别把本地验证服务起在 5061 端口**

收尾跑工具时踩到一个很费时间的坑：工具报 `fetch failed`（Node 侧）与
「等待超时：页面加载」（浏览器侧），但同一个地址用 `curl` / `Invoke-WebRequest`
**都是 200、2 毫秒返回**，服务端日志也没有任何异常 —— 看起来像"服务器卡死了"，
其实服务完全健康。

根因：**5061（以及 5060）在 Fetch 规范的「被阻止端口」表里**（SIP / SIP-TLS）。
Node 的 `fetch` 与 Chrome 都会**在发出请求前就拒掉**这个端口，而 `curl` / .NET 不管这套。
所以表现是"只有我要用的两个客户端连不上"。

👉 **本地起验证服务避开这些端口**（5060/5061、6000、6665-6669、6697 等）。
本次最后改用 **5071** 之后，两个工具立刻全绿（截图工具也一样）。
这条与"工具假红"是同一类：**先怀疑工具与端口，再怀疑产品**。
