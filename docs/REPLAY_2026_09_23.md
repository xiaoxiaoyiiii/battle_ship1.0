# 对局回放（2026-09-23）

> 需求：在自己/别人的**战绩**里点开某一局 → 「对局回放」按钮 → **全透视**回放
> （双方船位 + 双方手牌都可见）、**以每次行动为一步**、可暂停/上一步/下一步/倍速、
> 进度条标出关键节点（使用某卡、击沉战舰）、鼠标移到节点能看那一步发生了什么。
> **没有思考时间**，固定速度播放。

---

## 0. 一句话设计

**回放 = 现有 `game_logs` 的步骤序列 + 两条稀疏时间线（船位 / 手牌）+ 棋盘重置标记。**
不存每步全量快照（那会让体积涨 5~10 倍），棋盘标记按时序从 attack 步反推（与观战同一套朝向逻辑），
再叠上重置事件。落库走**独立表 + 独立按需接口**，**绝不塞进 `match_logs.logs`**（那一列会随
`show_history` 公开给所有人，而且战绩接口每次都全量下发它）。

## 1. 实测账（2026-09-23，线上机器与生产库实测，不是估算）

| 项 | 实测值 |
| --- | --- |
| 服务器内存 | 总 **1866 MB**，可用 **777 MB**，**swap 已用 608 MB** |
| 服务常驻 | **55.8 MB RSS**（cgroup 43 MB） |
| 磁盘 | 40 GB，**19 GB 可用** |
| 生产库 | `battleship.db` **2.7 MB** + WAL 4.1 MB |
| `match_logs` | **293 行**；每局日志 **中位 6.6 KB**、最大 23 KB；**中位 35 步**、最多 117 步 |
| 行动类型 | `attack` 7706、`magic` 1734、`result` 184、`quick_chat` 87、`system` 7 |
| 规模 | `matches` **342 行**、`users` **34**、`user_profile` **8**；单人最多 204 局 |
| `matches` 的 id 形态 | uuid **484** / `ai-*` **176** / 游客 sid **24**（共 660 个座位） |
| 两边都是真实用户的对局 | **152 / 342** |

**结论：保留 30 局不用降，反而偏小。** 一条回放 ≈ 6.6 KB（日志）+ 1~2 KB（时间线）≈ **8~10 KB**。
30 局/人：今天全服所有回放约 **3 MB**；涨到 1000 活跃用户也只有 **~30 MB**，对着 19 GB 可用磁盘是噪声。

**真正的风险是内存不是存储**（可用 777 MB + 已在 swap）：

1. 回放**绝不进内存缓存** —— 不放模块级 dict、不加 `lru_cache`，只在"写"与"看"的瞬间各存在一份；
2. 记录器每局常驻内存 —— 契约原写"≤30 KB"，**实测做不到，已按实测修正**：
   真对局 20 局实测 **中位 92.6 KB / 最坏 153.4 KB**（落库那份 blob 中位 22.1 KB / 最坏 39.4 KB，
   约 229 B/步）。差 3~5 倍的原因是 CPython 里"每步一个 dict + text + detail dict"的固定开销，
   **不是实现冗余**（时间线已是稀疏+增量）。砍掉全部字段只省 8%，不值得，故**接受实测值**。
   量级判断：50 个并发房间 × 153 KB ≈ **7.5 MB**，对 777 MB 可用内存是噪声；
   真正会出事的是"回放留在内存里"，那条由 `_finalize_match` 的 `finally: replay.reset(room)` 保证。
   本机生产只有 34 个用户，真实并发房间远小于 50。
   `MAX_STEPS=2000 × 229 B/步 ≈ 458 KB`，与 512 KB 硬上限**自洽**（不存在"步数没超但 blob 超"的静默路径）；
3. 读的时候**只读一条**，并有 **512 KB 硬上限**：超限拒收并报警，绝不让坏 blob 打爆 1.8 GB 的机器。

另有一个必须同时改掉的缺口：战绩列表 `api.py:878` 默认 `limit=20`，存 30 局会有 10 局够不着。
前端战绩列表请求提到 **30**，代价是 `/user_stats` 单次响应 ~132 KB → ~200 KB（30 行 × 6.6 KB）。

## 2. 数据模型

```sql
CREATE TABLE IF NOT EXISTS match_replays
(
    match_id        TEXT PRIMARY KEY,
    winner_user_id  TEXT,            -- 真实 user_id；游客/人机座位为 NULL
    loser_user_id   TEXT,
    created_at      INTEGER NOT NULL,
    bytes           INTEGER NOT NULL,
    version         INTEGER NOT NULL,
    replay          TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_replay_winner ON match_replays (winner_user_id, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_replay_loser  ON match_replays (loser_user_id,  created_at DESC);
```

**为什么自带参与者两列**：实测 `matches.winner_id` 里混着 uuid / `ai-*` / 游客 sid，
长度上无法可靠区分 —— 从它反推"参与者是谁"是不可靠的。自带两列才谈得上"按人保留 30 局"与"参与者鉴权"。

`user_profile` 加 `allow_replay`：`_add_column_if_missing('user_profile', 'allow_replay', 'INTEGER DEFAULT 1')`，
配套 `ALLOW_REPLAY_DEFAULT = 1`，与 `allow_spectate` 同一套写法（教训 #14：老表加列只能判存在再加）。

## 3. 记录器（`replay.py`，纯模块）

**铁律**：`replay.py` **运行期不许 `import server`**（教训 #19）。

- **步**：`room.replay['steps']`，每步 `{i, kind, actor, text, detail}`；
- **船位时间线**：只在船位真变时记 `{step, p1:[{x,y,alive}], p2:[...]}`；
- **手牌时间线**：只在手牌真变时记 `{step, p1:[卡名], p2:[...]}`；
- **棋盘标记不存**：按步从 attack 步反推，再叠 `board_resets`（`{step, side}`）。

**喂数据只有两处，判据只有一份**：

1. `add_game_log(room, ...)` 末尾调 `replay.note(room, entry)` —— 一处覆盖现有 **38 个**行动记录点；
2. 当前**没有日志**的行动，在它们的**单一实现点**上调 `replay.note_action(room, kind, label, detail)`：
   `handle_end_turn` / `handle_enter_battle_phase` / `handle_enter_end_phase` /
   `handle_place_ships` 收尾 / `handle_rps_choice` / `handle_surrender`（约 6 处）。
   ⚠️ 这 6 处**不往游戏内日志加行** —— 游戏内日志的显示保持原样，不顺手改一个既有玩家可见功能。
3. **棋盘重置**复用第 5 批为观战加的 4 个失效点（`_mark_spectate_board_dirty`：
   `_clear_attacks_on_cells` / 灵气复苏 / 败者食尘 / 回光返照）—— **一处地方、两个消费方**。

**终局**：`replay.finalize(room)` 产出最终 JSON（`version` / 双方显示名 / `steps` / 两条时间线 /
`board_resets` / `nodes`）。**关键节点由服务端算一次**，前端不重新推导（两套判据必然漂移）。

**硬上限**：步数 ≤2000、blob ≤512 KB。触限就**截断 + 明确标注"此回放被截断"**，不静默。

## 4. 保留策略（每人最近 30 局）

写入点：`db.record_match(...)` 加 `replay=` / `replay_participants=` 参数，**同一个事务**里插
`match_replays`（`match_id` 由 `record_match` 内部生成，只有这样才能原子绑定，也才保证"有回放必有对局行"）。

**清扫（唯一实现，在 db.py）**，每次插入后对两个真实参与者分别做：

- 取该人 `matches` 按时间倒序**第 30 条**的时间戳 `cutoff(U)`；不足 30 条 → 不淘汰；
- 遍历该人**早于** `cutoff(U)` 的对局：对手不是真实用户 ⇒ 删；对手是真实用户但那一局仍在其窗口内
  ⇒ **留着**（共享的一条回放不能被先超窗的一方删掉）；两边都超窗 ⇒ 删；
- 每插入只枚举被淘汰的 1~2 条，不扫全表；
- **孤儿清扫**：`matches` 行被管理端回滚工具删掉时（教训 #28）对应回放一并清掉。

**不记录**：双方都不是真实用户（游客 sid 局，谁都读不到）；任一真实参与者 `allow_replay` 关着。

## 5. 权限与隐私

**开关**：`user_profile.allow_replay`，默认 **开**。UI 放设置面「隐私」区、
`#settings-allow-spectate` 旁边，状态**只来自服务端**（进设置面拉 `GET /api/replay/setting`），
保存失败必须提示 —— 照抄观战开关那一套。

**开关语义：任一方关掉 ⇒ 这一局就不留回放。** 只有这个语义真能保护关掉的人；否则你关了、
对手照样能反复研究你摆船。判定在 `_finalize_match` 收口处一次，新增
`_replay_allowed_for_match(winner_user_id, loser_user_id)`。

**读权限：能看你战绩的人都能看。** `GET /api/replay/<match_id>` 放行当且仅当：

- 请求者是**该局参与者**（`winner_user_id`/`loser_user_id` == 自己），**或**
- 该局某个真实参与者 `show_history = 1`（实测默认 **0 = 不公开** ⇒ 默认只有双方能看到）。

**假设 A1**：回放接口**要求登录**（游客 401）。观战已是"只限登录用户"，回放比观战敏感得多
（它泄露船位），不给匿名抓取留口子。代价：匿名浏览别人战绩能看列表、看不了回放。

**失败方向**：`get_allow_replay` 读库失败按**不开**处理（fail-closed，不记录）并**打日志报警**。
与观战相反（观战 fail-open），因为这里的错误方向是"泄露隐私"而不是"少个功能"。
**日志必须响** —— 吞掉等于没有守卫（教训 #34）。

**绝不做**：回放接口**不发任何 socket 事件**；`replay` 相关键**永不进 `SPECTATE_EVENTS`**；
`_build_spectate_snapshot` **永不读回放表**。三条都写成源码级守卫。

## 6. 后端接口

| 接口 | 作用 |
| --- | --- |
| `GET /api/replay/<match_id>` | 鉴权后返回 `{success, replay, you_are}`；`you_are` 服务端算好（`p1`/`p2`/`null`），**不下发任何 user_id** |
| `GET /api/replay/setting` | 读开关（状态只来自服务端） |
| `POST /api/replay/setting` | 写开关，`{'allow_replay': bool}`，非布尔 400 |
| `/user_stats`（改） | history 每行加 **`has_replay` 布尔**：`LEFT JOIN match_replays mr ON mr.match_id = m.id`，取 `mr.match_id IS NOT NULL`。**只取布尔，绝不取 blob** |

读接口内部：`MAX_REPLAY_BYTES` 校验 → `json.loads` → 校验 `version` → 返回。
**解析失败 ⇒ 明确报错 + 打日志 + 顺手删掉这条坏回放**，不静默返回空（教训 #32）。

## 7. 前端回放界面

**独立新屏 `#replay-screen`，不改造观战屏。** 硬决定：观战屏的棋盘渲染**故意**只会画"已轰过的格"，
其安全前提是"手上根本没有船位数据"；一旦让它学会画船，某次改动就可能把船位漏给观众。
所以新屏、新 DOM id（`#replay-board-1/2`），棋盘渲染**新写一份**，只共用 CSS 类
（`.cell/.hit/.miss/.sunk`）与 `magic_cards.js` 的卡名映射。

**入口**：`renderMatchDetailHTML(matchData, playerId)`（`game.js:4595`）加「对局回放」按钮
（带 `data-match-id`），`has_replay` 为假时置灰并写明"这局没有可回放的行动"。
点击用**事件委托**绑在 `#match-detail-content` 上 —— 容器每次重建，逐次绑监听必漏（大厅踩过同一个坑）。

**布局**（模仿观战屏骨架，去掉观战席与聊天）：

- 标题（双方名 + 胜负 + 时间）、顶栏（回合 / 阶段 / 场地魔法 / **速度** / 退出）
- 左右两块**全透视棋盘**（船格可见；命中 / 击沉 / 落空三态 + 船体）
- 侧栏：**双方手牌**（只读卡名）+ 对局日志 + 当前连锁（有则显示）
- 底部：`上一步` / `播放·暂停` / `下一步` / `退出` + **进度条**

**步进与状态解算**（客户端纯函数，一处实现）：

- 第 k 帧棋盘标记 = `steps[0..k]` 里的 attack 步，叠上 `board_resets` 中 `step ≤ k` 的重置；
- 船位 = 船位时间线中最后一个 `step ≤ k` 的条目；手牌同理；
- `上一步/下一步` = 改 `k` 后整体重画（≤2000 步直接重算，不需要 checkpoint）；
- **没有思考时间**：每步固定时长（默认 900 ms）÷ 倍速；档位 `1× / 2× / 4×`，`setTimeout` 链驱动，
  暂停即清定时器。

**进度条**：track + 按 `i/(n-1)` 绝对定位的节点标记，节点来自服务端 `nodes`（`{step, kind, label}`）。
**hover → tooltip** 显示那一步做了什么；**点击节点跳转**；**拖拽 track 任意位置 seek（并自动暂停）**。

## 8. 守卫清单（每条都必须证明"能红"）

1. **观战永不碰回放**（源码级）：`spectate.py` / `_build_spectate_snapshot` / `renderSpectateBoards`
   出现 `replay` / `match_replays` / 船位字段即判红；
2. **回放路径永不 emit**（源码级）：`replay.py` 与三个新接口出现 `emit(` / `socketio` 即判红 ——
   一旦漏，船位会直接进对局房间；
3. **观战不变量 1 复跑**：观战者每一帧仍无船位、无未公开坐标 + **自我校准腿**（注入假泄漏帧必须变红）；
4. **`/user_stats` 不含回放 blob**：30 局历史的响应字节数必须在上限内；
5. **鉴权三情形双向**：参与者可看 / 非参与者且 `show_history=0` 拒 / 非参与者且 `show_history=1` 放；
6. **开关语义**：任一方关 ⇒ **没有**回放行写入；双方都开 ⇒ 有（反向腿必须有）；
7. **保留 30**：第 31 局进来后最老那条被删；**共享回放**在一方超窗、另一方没超窗时**必须还在**；
8. **孤儿清扫**：删掉 `matches` 行后回放也被清；
9. **无内存缓存**（源码级）：`replay.py` 不许有模块级 dict、`get_match_replay` 不许挂 `lru_cache`；
10. **字节上限**：合成超限 blob → 拒收 + 明确报错（**不是**静默空）；
11. **记录点不漏**：38 个 `add_game_log` 点、6 个 `note_action` 点、4 个 `board_reset` 点逐个断言产生步骤；
12. **`allow_replay` 列迁移幂等**：重复 `init_db()` 不炸、老库能升级。

## 9. 边界与失败模式

| 情形 | 处理 |
| --- | --- |
| 某局 0 步（生产里**真有**这种行） | `has_replay=false`，按钮置灰写明原因 |
| 游客 sid 局（实测 24 个 id） | 不记录（谁都读不到） |
| 人机局（占战绩大头） | 记录；只有人类那侧的开关生效（AI 无设置） |
| 回光返照 / 灵气复苏 / 败者食尘重排棋盘 | `board_resets` 时间线；**不能**只靠 attack 反推（第 5 批那个 bug 的回放版） |
| 滥竽充数临时船回合末被收回 | 船位时间线必须跟着变 |
| 管理端回滚工具删了对局 | 孤儿回放被清扫 |
| 回放 JSON 解析失败 | 明确报错 + 日志 + 删掉这条坏回放 |
| blob 超 512 KB / 步数超 2000 | 拒收 / 截断并**明确标注**，绝不静默 |
| `Player` 缺失或设置读库失败 | 跳过该侧但**打日志**（fail-closed 方向见 §5） |

## 10. 明确假设

- **A1**：回放接口**要求登录**（§5 已说明取舍）。
- **A2**：`allow_replay` 默认 **开**（与 `allow_spectate` 一致）；但**默认外界看不到**
  （`show_history` 默认 0），所以上线不会一次性把所有人的对局公开。
- **A3**：保留 **30 局**（实测证明 30 完全放得下）；同时把前端战绩列表请求从 20 提到 **30**。
- **A4**：**没有 `match_logs` 的旧局不会凭空有回放**（实测 342 局里 49 局没有日志行）——
  历史局无法补录，只有本批上线后的新对局才有回放。公告与文档如实写，不假装能回放旧局。
- **A5**：回放**不含观战席与聊天**；但保留局内 `quick_chat` 作为步骤（它本来就是对局的一部分）。
- **A6**：回放**不给观众看、也不能被观战入口打开**；两个功能各有各的入口与通道。

## 11. 已知风险 / 不覆盖

1. **首帧时序**：`add_game_log` 在各 handler 里是"效果生效前"还是"后"调用，需逐点核对。
   若某处在前，该步的船位/手牌变化会**晚一步**显形。缓解：稀疏 diff 会累计到下一条记录，
   最坏是视觉差一步；用 E2E 逐帧比对钉住。
2. **6 个 `note_action` 点**落地时需确认是唯一实现点，避免漏记或重记。
3. **真机长局**：只在生产数据上算了体积，**没测过** 2000 步极端局的真实播放流畅度。
4. **多标签并发看回放**：不在本批验证范围。
5. **大回放对低端手机的渲染**：不覆盖（棋盘只有 36 格，风险低）。
6. **旧局补录**：不做（A4）。
7. 本批**不动**观战任何代码；若落地时发现必须动，先停下来说明再决定。

## R2. 观战与回放的隔离（本批最重要的安全边界）

- 回放是**独立一整屏** `#replay-screen`，`#spectate-screen` 一个字都没改；
- 棋盘渲染**新写一份**：`renderReplayBoard` / `replayCellOf`，自己的 DOM id `#replay-board-1/2`，
  只共用 CSS 类（`.cell`/`.hit`/`.miss`/`.sunk`）与 `magic_cards.js` 的卡名映射；
- 回放段**完全不碰 socket**：不 join 房间、不发任何事件、不订阅观战通道；段内**没有一处 `emit(`**。
  那个 `replayState.socket` 字段只在退出时 `disconnect()`；
- 回放屏**没有观战席、没有聊天输入框**（契约 A5）。

两条源码级守卫（去掉注释后扫关键词，**都证明过能红**）：

| 守卫 | 判据 | 能红的改法 | 结果 |
| --- | --- | --- | --- |
| 观战渲染不吃回放 | `renderSpectateBoards` 函数体里不许有 `replay` / `match_replays` / `alive` | 在开头加 `const leak = gameState.replayPayload.ships` + `leak.alive` | `FAILED ... AssertionError: 观战棋盘渲染里出现了 'replay'` |
| 回放渲染不碰观战 | ① 回放段里不许有 `spectate*` 名字；② `renderReplayBoard` 里不许有 `renderSpectateBoards` / `applySpectateSnapshot` | 在 `renderReplayBoard` 开头加 `renderSpectateBoards(); void applySpectateSnapshot;` | `FAILED ... 回放段里出现了观战那套的名字：['renderSpectateBoards', 'applySpectateSnapshot']`（两条用例同时红） |

⚠️ **判据必须"去掉注释"再扫**：本段头部的说明注释里当然解释过"不许出现 spectate"，
那是文档不是耦合；而且这几条说明被**故意放在函数体之外**，函数体里连注释都不留这些词
（否则守卫会被自己的说明书误伤）。`ship` 这个词**允许**出现在观战渲染里 ——
那几处是 `mark.ship_sunk`（服务端告诉观众的**唯一**信息），不许据此推断旁边还有没有船。

## R3. `board_resets.side` 的方向 + 增量时间线的口径（照契约实现，未遇到歧义）

- `board_resets[].side` = **哪一块棋盘被重置**（`replay.py:399` 的 `board_reset(room, board_owner_id)`
  里 `_side_label(room, pid)` 就是被重置那位），所以重置只清**那一侧**的攻击标记；
  `回光返照` 传 `caster_id`、`灵气复苏` / `败者食尘` 不传（= 双方），与 `test_replay_guards.py` 一致。
- 两条时间线是**增量**（某条只带变化的那一侧）⇒ 前端按 `step` 升序**把所有 `step ≤ k` 的条目叠上去**
  （`replayFoldTimeline`），不是"取最后一条"。实测一条真回放的 `ships` 时间线：
  `step=0` 带 `p1+p2`，后面 6 条**只带 p1**（AI 那一侧的船被逐艘打沉），
  所以 p2 的船位必须从 `step=0` 那条一直沿用 —— 这正是"增量"最容易写错的地方。
- `detail.attacker` 是**原始座位 key**（实测就是 uuid user_id / 人机房里是入座 sid），
  **拿来当身份用会错**。前端判"这一炮画到哪块棋盘"的顺序：
  ① `detail.attacker === 'p1' || 'p2'`（通用）；② 退回按 `step.actor`（显示名）对齐座位名；
  ③ 两者都认不出**就不画这一炮**（宁缺勿错 —— 画错一侧比少画一炮更难查）。
  本次实测的 AI 房走的是 ②（`detail.attacker` 是 uuid）。

## R4. 后端契约让人"卡一下"的三个地方（都不是 bug，但都得知道）

1. **第 0 帧双方手牌本来就是空的**。`hands` 时间线的第一条（`step=0`）是 `p1: [] / p2: []`，
   真正的第一份手牌在 `step=1`（猜拳之后才发牌：先手 1 张、后手 2 张）。
   本批的 E2E 第一次就是这么**假红**的（"双方手牌不可见"）—— 其实工具读的是第 0 帧。
   判据改成"走到最后一帧，画面上的牌与后端最后一份手牌逐张相同"后才对。
   **给下一个人的话**：别把"开局那一刻的空手"当成渲染失败。
2. **阶段类节点的 `label` 自带行动者名字**（`note_action` 的 label 是 `_log_name(...)` 拼的），
   所以 tooltip 无脑拼 `actor + label` 会得到「第 3 步 · 甲 · 甲 进入战斗阶段」（实测读出来过）。
   修法：**标签里已经有这个名字就不补**（`replayNodeTipText`）。
3. **`steps[].sides` 在真数据里几乎不出现**：它是快照变化时用的（`build()` 把录制期的 `_side` 换成 `sides`），
   AI 房这一局的 10 步里一条都没有 —— 所以"这一步是谁做的"只能靠 `actor` / `detail.attacker`，
   不能指望 `sides`。

**没有发现后端 bug。**

## R7. E2E 工具踩到的坑（**工具自身**的，不是产品的）

`tools/replay_check.mjs` 从"跑不起来"到全绿，红了 6 轮。**每一轮都是工具/判据的问题**：

1. **`place_ships` 的每艘船必须带 `hits`**：服务端 `PlayerShip(**x)` 直接展开 dict，
   少了 `hits` 就是 `TypeError: missing 1 required positional argument: 'hits'`
   ⇒ handler 抛异常 ⇒ **连 ack 都不回** ⇒ 工具侧只看到 `timeout Runtime.evaluate`
   （正是 CLAUDE.md §1 那条"ack 帧没有长度位、handler 抛异常连 ack 都不回"）。
   当时是靠**看服务端日志的 traceback** 才定位的 —— 别先怀疑网络。
2. **猜拳会平局**（AI 随机出拳，1/3）：只发一手，撞上平局房间就永远停在 `rock_paper_scissors`。
   工具改成**循环出拳直到进入 attacking**。
3. **回合不是一次调用就换人**：一轮要走
   `enter_battle_phase` → 打光次数 → `enter_end_phase` → `end_turn`。
   只调前两步的症状是"404 炮打了 150 秒、`attacks_remaining` 一动不动"。
4. **目标集合必须本地记住"试过的格"**：服务端**拒掉的**那一炮不会出现在
   `test_get_game_state` 的 `attacks` 里，只看服务端状态就会反复挑同一个格子 ⇒ 活锁。
5. **不能把次数浪费在空海上**：不筛"还没沉的船"就会 30 炮 / 7 回合还赢不了（AI 把我方船打光、
   攻击次数掉到 3）。筛了之后 6 炮收工。
6. **我方摆船要用固定间隔的 6 格**：随机摆放偶尔会把 6 艘挤在一起，AI 几炮打掉一半 ⇒ 同 5。

**产品侧的两个真问题也是这轮翻出来的**（都不报错）：
- **战绩行的点击是 `bindHistoryButtons` 绑的**，工具直接把 HTML 塞进容器就绕开了它 ⇒
  点了没反应。为此加了 `window.__bindHistoryForCheck`（**只为工具存在**）。
- **进回放屏时旧浮层没关**：`#user-stats-modal` 与 `#match-detail-modal` 还挂着，
  于是"进了回放屏却还看着战绩弹窗" —— **是截图抓出来的**（截图里是战绩弹窗，不是回放屏）。
  修法：`openReplayForMatch` 调 `closeOverlaysExcept(null)`（按类名取全量 `.overlay`，不手抄 id）。
  ⚠️ 这条如果不修，玩家从战绩点进回放就**看不到回放**，而且页面上不报任何错。
