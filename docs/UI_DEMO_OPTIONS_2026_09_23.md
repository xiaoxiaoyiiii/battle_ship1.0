# UI 方案示意稿：15 版（2026-09-23）

给「战舰棋」做了 15 版**静态示意稿**，分四批。**第四批（M–P）是按反馈精修后的当前候选**。
总览页（带全览图与代价对照）：`docs/ui_demos/index.html`。

- **第一批 A–D**：暗色专业 / 暖色实体 / 深色游戏化 / 浅色移动 —— 重画现有界面
- **第二批 E–H**：主题深蓝（声呐）/ 极简排版 / 霓虹赛博 / 像素复古 —— 重画现有界面
- **第三批 I–L**：统一战场 / 工作台 / 组件化 / 航线 —— **产品级重设计**，不受现有布局约束；
  每版都是**同一个响应式页面**在手机与桌面各出一套图（`1440×900` + `390×844`）
- **第四批 M–P**：按反馈精修 —— **以 C 为底**、主页综合 I 的主行动、**两块棋盘都放大**、
  **实体手牌 + 自适应扇形 + 一级/二级预览**、去掉通行证等商业化内容

> 这些是 HTML+CSS 示意稿，**不是可运行版本**，也不接 socket / 不读真实数据。
> 但文案、卡名、段位名、DOM 惯例全部取自真实实现（`static/magic_card.json`、`ranks.py`、
> `templates/index.html` 的 id 与 label），所以看密度与信息量就是真的。

## 1. 八个方向（讲结构差异，不是配色）

### 第一批

**A · 战术指挥台** — 暗色作战终端，发丝线 + 等宽数字。**改的是信息架构**：首页 = 模式面板 +
指挥官状态栏 + 最近对局；对局屏 = 固定三栏（日志轨 / 战场 / 手牌轨），浮窗不再压棋盘。
**顺带修掉 `FLUENT_UI_2026_09_21.md §10.3` 那个未修缺陷**（宽屏两块棋盘并排，不再堆叠压住 12–18 格）。

**B · 桌面棋室** — 暖纸 + 黄铜 + 墨线。棋盘是主角（400px，现状 300–340），手牌是底部扇形实体卡，
日志是航海笔记本，弃牌堆是可见的牌堆。

**C · 卡牌竞技场** — 魔法卡当主角（132×186 大卡）。**信息优先级刻意不对称**：对手海域占中场，
自己的舰队缩成左下角小图；连锁做成"真的叠起来的一摞卡"。

**D · 口袋舰队** — 手机 App 范式：底部标签栏、底部抽屉、横向滑动手牌、单格 48px。
一次只看一块棋盘（现有 `#board-tabs` 机制），抽屉对应现有 `#aux-dock`。

### 第二批

**E · 声呐舰桥** — 深海蓝 + 磷光绿，主题上最贴"战舰棋"的一版。首页把「在线/队列/延迟」做成三个**环形仪表**；
对局屏把对手棋盘做成**声呐显示区**（背后同心圆环 + 十字基线 + 扫描扇面）。
> ⚠️ **刻意不做圆形棋盘**：真圆形会把 6×6 的四个角裁掉、格子在圆外点不到。这里用
> "方形棋盘 + 圆环背景 + 扇形扫描"，观感到位且每格完整可点。这是这一版最重要的取舍。

**F · 极简纸白** — 编辑式排版，近单色、无阴影无圆角。棋盘是**只用 1px 线画出来的表**
（舰=实心黑块、命中=红块带 ×、打空=空心圆）；魔法卡是**一张表**（卡名 / 速阶罗马数字 / 效果），
选中行左侧一道黑杠并展开全文 —— 不画卡面。全局只有两个语义色。**信息密度最高、视觉噪音最低**。

**G · 霓虹赛博** — 近黑底 + 霓虹发光 + 扫描线 + `clip-path` 切角 + 故障字（青/洋红错位）。
手牌是底部一排切角霓虹卡；连锁做成会呼吸的洋红警示条 —— 全屏最"吵"的元素就是当前该你决策的地方。

**H · 像素复古（8-bit 街机）** — 首页是**街机标题画面**（像素标题 + `▶` 光标选单 + HIGH SCORE/EXP/SYSTEM/RECENT）；
对局屏底部是 **JRPG 对话框**（三行战报 + HIT/MISS/RATE 分数 + 闪烁 ▼），日志从浮窗变成常驻条。
> ⚠️ **诚实取舍**：中文没有可用的像素字体（本项目不许引外部资源），像素感只能靠
> **边框与结构**做（明/暗斜面对边框、等宽大写、格点 logo、扫描线），中文仍是系统字。

### 第三批（产品级重设计）

这一批**不重画现有界面**，重新设计信息架构。三批的关键差别：前两批回答"界面长什么样"，第三批回答"这个产品怎么组织"。

**I · 同一片海** — 把「你的棋盘 / 对手的棋盘」两块互不相干的对象，合成**一片 6×12 的海图**，中间一条「前线」：
上方是敌方海域（你开火的地方），下方是你的海域（对手开火的地方）。
两端打通的方式是**同一个对象的两种折法**：窄屏上下折成长卷（前线是横线），宽屏左右折成双页（前线变书脊）。
首页的"我的舰队"小图与对局里的海图是同一个东西，视觉连续。
> 参考：Clash of Clans（自己与敌方基地同屏）、Legends of Runeterra（双方区域共用中轴）、
> Chess.com（棋盘是唯一视觉中心）、Duolingo（移动端主导航收成底部标签栏）。

**J · 工作台** — 左轨道 + 画布 + 右检查器；**选中即详情**。魔法卡不再是"一排卡面"而是检查器里的**列表**，
点一行就在上面展开全文与「确认使用」；战报是画布上的**时间线**而不是浮窗。
手机上同一套三区收成"画布 + 上拉面板 + 底部标签" —— 这一批里两端差异最自然的一版。
> 参考：Linear / Height（轨道 + 列表 + 右侧详情）、Figma / Blender（画布与检查器分离）、
> Notion（属性区随选中对象变）、VS Code（活动栏 / 侧栏 / 编辑器 / 面板 的密度分配）。

**K · 组件主页 · 焦点对局** — 主页是一屏**可扫读的组件**（快速开战 / 段位环 / 赛季进度 / 每日任务 / 卡牌图鉴 /
最近对局 / 在线好友 / 本周最佳 / 成就 / 排行快照），同一组组件手机 2 列、桌面 4 列。
对局是**焦点模式**：顶栏只剩回合与阶段，手牌是底部浮动 dock，日志与统计全收进一个「更多」
（桌面是右侧抽屉、手机是上拉面板）。棋盘放大到 430px，装饰几乎为零。
> 参考：iOS 小组件 / Apple Fitness（组件化主页）、Spotify「正在播放」（焦点模式：内容满屏、控件最小）、
> Xbox Dashboard（大色块 + 单一主行动）、Whoop / Oura（环形进度承载核心指标）。

**L · 航线 · 赛季通行证** — 把段位从**一个数字**变成**一条可走的航线**：每个节点 = 一个段位，
写清"到这里解锁什么"，你的船停在当前节点上；玩一局 = 往前推一程。模式选择从"5 个并排按钮"收成
**一个主按钮 + 一行段控件**。赛季通行证是**双轨**（免费 / 高级）。对局屏在桌面也保持**竖屏街机台**，
两侧填战报与手牌 —— 这正是移动优先产品上桌面的常见做法。
> 参考：Duolingo（路径上的节点表达长期进度，进度本身就是导航）、
> 皇室战争 / 英雄联盟手游 / Fortnite（赛季通行证双轨）、皇室战争（竖屏对局上桌面：两端留白 + 侧栏）、
> Super Mario World（地图式选关）。
>
> ⚠️ **这一版含新功能**（航线可视化 + 赛季通行证涉及商业化与赛季结算），不只是 UI —— 选它要先做产品决策。

### 第四批（按反馈精修 · 当前候选）

反馈里逐条落地的取舍：

| 反馈 | 落到哪里 |
| --- | --- |
| C 真不错、局内稍微改一改 | **M / P** 都是以 C 为底；P 是"只改局内两处"的最小改动版 |
| 局内看自己的棋盘太小 | C 里自己舰队只有 200px 缩略图 → **M 双盘等大（各 400）**、**P 你的海域 352 真棋盘** |
| 做成真实手牌样式很好 | **M / P / O** 的手牌都是实体卡（保留 B 的思路，去掉 B 的复古皮） |
| 手牌按数量自适应排布 / 一级二级预览 | **O** 专门做了一版规范：3-5-8 三档扇形 + 两级位移量写死成可抄的 CSS |
| 确认使用按钮到底好不好用 | **O** 把「再点即用」与「按钮确认」并排对照，并给出建议：**按"这张卡要不要选目标"分流** |
| 外面的主页做得很不错 / I 的局外主页也很好 / 两者可以综合一下 | **M 的主页** = C 的骨架（倾斜名片 + 热门卡墙 + 段位阶梯）+ I 的主行动（一个「出海」按钮 + 模式段控件） |
| 这怎么商业化的内容都出来了 / 还有通行证 | 第四批**没有**通行证、赛季、双轨、付费相关内容 |
| 那几个复古风的都淘汰了 | H（像素）与 B 的暖纸黄铜观感淘汰 |
| 手机端优先的就算了 | D 淘汰 |
| I 的主页里的航线有点唐乐 | L 的航线节点体系停用（文件保留作参照） |

**M · 竞技场精修**：主页保留 C 的观感、模式收成一个主按钮 + 段控件；局内**两块 6×6 等大（上限 400px）**，
对手那块标「开火区」、自己那块标「受击区」；手牌是实体卡，扇形按数量自适应，悬停一级预览、点击二级预览（右侧出介绍窗）。

**P · 竞技场最小改动**：**主页与配色完全沿用 C**，只改两条 —— ① 你的海域 200px → **352px 真棋盘**；
② 底部手牌换实体卡 + 两级预览。对手海域仍是中场最大的一块。这一版改动最小、回归风险最低。

**O · 手牌与预览行为（规范稿）**：不换皮，三个视图讲清三件事 ——
① **自适应扇形**：3 张几乎不重叠 / 5 张 −18px ±7° / 8 张 −46px ±12°，牌永远居中，抬起的牌始终读得全；
② **两级预览的位移规范**：一级 `translateY(-30px) scale(1.05)`（不改状态、移开回位），
二级 `translateY(-56px) scale(1.09)` + 金色描边 + 右侧介绍窗；
③ **用牌流程对照**：A「再点即用」vs B「按钮确认」，并给出建议 **C：按卡是否需要目标分流** ——
无需目标的卡（失灵！/看破！）点两次即用，需要目标的卡（神威！/轰炸/增援）选完目标再确认，
且按钮文案随状态变（未选目标时置灰显示「在棋盘上选区域…」，选好后变「确认使用 神威！」）。

> 建议的推进顺序：**先落 P（改动最小、能立刻看到效果），同时按 O 的规范做手牌**；
> 若你更看重"两块棋盘都看得清"，则用 M 的等大布局替代 P 的不对称布局。主页两者一致（M 的版本）。

| **M 竞技场精修** | 局内两块棋盘等大 → 宽屏"浮窗留白"规则重写；手牌从卡面行改成扇形实体卡（要动 `game.js` 手牌渲染） | 局内布局 + 手牌渲染 + 主页主行动收束 | C 里"自己棋盘 200px 太小"；卡牌描述不再依赖浮窗 | 中 |
| **P 竞技场最小改动** | 只把"你的海域"从缩略图换成真棋盘；其余不动（对手海域仍居中） | 一处布局 + 手牌渲染 | 同上，但改动面最小、回归风险最低 | **低** |
| **O 手牌与预览行为** | 无结构冲突（是行为规范，可套在任一皮上）；但需要补 hover/选中两态与目标高亮 | 手牌交互 + 目标选择态 + 按钮文案状态机 | 用牌流程终于有了明确答案（按是否需要目标分流） | **低** |

**共同前提（8 个方向都一样）**：所有 id 一个都不动 —— `tools/*.mjs` 是按 id 点击的，
`dom_contract_check.mjs` 会查悬空 id。示意稿里每个按钮的 id 与现有实现一致，就是为了这个。

**一个容易误判的点**：手牌**本来就是**底部一排卡片（`#magic-hand` / `.magic-card`，见 `style.css` 的
贴底手牌与 `FLUENT_UI_2026_09_21.md` §10.1）。所以 B/G/H 的"底部手牌"是**换皮**、不是结构改动；
真正的结构改动只有 C/E（新增迷你棋盘）与 A/G/H（宽屏留白规则）。

## 3. 建议

- **只改皮肤、风险最低 → D**（紧凑档机制现成）；**次低 → F**（纯排版层，两块棋盘与零滚动都不动）。
- **要"产品级重做、且手机与桌面是同一套设计" → 第三批**。其中：
  **I 最贴这个游戏的题材**（一片海 + 前线），**J 最像成熟效率产品**（选中即详情），
  **K 最稳**（主页是纯展示组件，改动集中在"弃用浮窗"），**L 最需要产品决策**（含通行证等新功能）。
- **桌面观感提升最大、且顺手修掉 §10.3 → A**；想更"有主题"就用 **E** 替 A（代价接近，但要多一个迷你盘）。
- **最"有味道" → B**（代价中等，落在 `style.css` 为主）。
- **C 与 E 是同一档最高的**：都要新增一种棋盘渲染，宽屏断言要重定。
- **G / H 是"性格选项"**：技术代价都是中（都在 A 的结构上换皮），选它们主要是选气质 ——
  H 还能顺带把日志从浮窗变成常驻。

可混搭：**D 管紧凑档 + （A/E/F/G/H 之一）管宽屏档**在机制上并不冲突，这正是
`adaptive_layout.js` 既有的 `side/stack/tabs` 分层。

## 7. 做这两批示意稿踩到的、值得记的两条

1. **示意稿一样会排版溢出，唯一靠谱的办法是量矩形、不是估。**
   `tools/ui_demo_shots.mjs --probe` 就是为这件事加的。实测抓到的都不是"看着不对"，
   而是"量出来压住了"：A 的图例被情报条压 45px（wrap 396 vs 可用 351）、
   B 的 `max-height:100%` 因为**网格行按内容长高**而失效（要钉 `grid-template-rows:minmax(0,1fr)`）、
   D 的抽屉压在手牌上（竖向预算 987 > 844）、E 的中栏情报条顶出视口 22px、
   **H 的图例压到对话框上（一个 `calc()` 常量不可能同时适配 900 与 720 两档，改成两档分别标定）**。
   全部靠探针定位，没有一处是靠反复调 CSS 试出来的。
2. **响应式"两端同一套设计"最容易栽在三件小事上，第三批四版各栽过一次：**
   ① **宽屏专属的规则必须先有基础层**：`@media (min-width:900px)` 里写的 `display:flex` 一旦没在基础层
   给"窄屏隐藏"，就会漏到手机上（I 的右栏、J 的检查器、I 的连锁条都是这么漏的）；
   ② **flex 列必须写 `min-height:0`**：不写就按内容最小高度撑着，底部标签栏被顶出屏幕（I 实测 884 > 844）；
   ③ **并排区块要显式定宽**：不定宽时 flex 会按内容最小宽度撑开，5 张 132px 的卡会把一栏顶到 724px、跑出 390px 屏幕（L）。
   这三条都不是"看着不对"，全是 `--probe` 量出来的。
3. **每张图都要看过再看下一张。** 三批共 50 张图逐张看过，改掉了 16 处观感问题
   （B 横格线与文字错位 6px、C 的叠牌压 46px 把卡名整个盖住、A/D/BD 手牌被静默裁掉最后一张、
   E/H 右栏装饰网格塞不下而溢出、C/E/F 各处的空白区）——
   与 `FLUENT_UI_2026_09_21.md` §8 的教训同源：**归档截图不看，等于没测**。
