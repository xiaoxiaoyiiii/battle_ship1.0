# Battle_ship1.0 基础代码渐进式重构设计

> 状态：设计基线已获批准，尚未开始业务代码迁移。
> 日期：2026-10-12

## 1. 背景与目标

项目经过两年多迭代，实时对局、卡牌连锁、回放、观战、AI、账号和前端页面已经形成可用产品，但核心实现仍集中在少数巨型文件中。当前目标是建立可交付生产级的基础架构，同时保持线上行为和已有客户端兼容。

重构同时追求三项结果：

1. 稳定性：输入校验、状态转换、结算、重连和并发行为可验证。
2. 可维护性：业务规则有清晰边界，避免同一判断多份实现。
3. 交付能力：测试、配置、部署、观测和回滚形成完整闭环。

采用兼容式渐进重构，不进行一次性重写。

## 2. 不可变原则

- 现有 HTTP 路径、状态码、Socket 事件名和主要 payload 默认保持兼容。
- 在事件使用情况完成审计前，文档未记录的现有 Socket 事件也按公开契约处理。
- 现有 SQLite 数据和回放读取能力保持可用；早期阶段不改表结构。
- 任何有意的外部行为变化都必须单独记录、测试并获得确认。
- 每个迁移阶段都必须能启动、可验证、可回滚。
- 不覆盖工作树中已经存在的用户修改。

## 3. 目标架构

```text
客户端
  页面渲染 / 客户端状态 / HTTP 与 Socket 适配
        ↓
接口适配层
  Socket handlers / HTTP routes / 输入校验 / DTO
        ↓
应用层
  攻击、回合、卡牌、房间、重连、结算等用例编排
        ↓
领域层
  棋盘、船只、攻击、回合、卡牌、连锁、领域事件
        ↓
基础设施层
  SQLite 仓储、回放、AI、定时器、日志、指标、配置
```

### 3.1 领域层

领域层只处理业务规则和状态转换，不导入 Flask、Flask-SocketIO、SQLite 或浏览器代码。候选模块包括：

```text
domain/board.py
domain/ships.py
domain/combat.py
domain/turns.py
domain/cards.py
domain/chain.py
domain/events.py
```

### 3.2 应用层

应用层负责权限、事务边界、用例编排、事件顺序和旧状态的协调。候选服务包括：

```text
application/attack_service.py
application/turn_service.py
application/card_service.py
application/match_service.py
application/reconnect_service.py
```

### 3.3 适配层与兼容层

适配层保持现有外部接口不变，将请求转换为命令，将结果转换回旧 payload。兼容层暂时承接 `GameRoom`、旧事件和旧状态字段，待新路径稳定后逐步删除。

### 3.4 基础设施层

基础设施层提供仓储、回放、AI、时钟、后台任务、日志和指标。早期只抽象接口，不急于替换 SQLite 或部署运行时。

## 4. 当前风险分类

### P0：生产安全与正确性

- 调试事件和生产配置必须有明确的环境门禁。
- `SECRET_KEY`、`CORS_ORIGINS` 等配置不能依赖不安全默认值。
- 布船、攻击坐标、魔法目标和权限必须在服务端校验。
- 对局结束、房间清理、统计和回放必须只有明确的结算收口。

### P1：状态和并发

- `GameRoom` 内存状态、匹配队列、掉线宽限和连锁计时器需要明确所有权。
- 重连快照必须覆盖连锁、临时选择和放置流程等可恢复状态。
- 前端 Socket 连接必须只有一个生命周期管理入口。

### P2：结构和维护

- `server.py` 中的事件、房间、规则和结算需要分层。
- `replay.py` 不应继续反向绑定整个服务器模块。
- `ai_brain.py` 不应直接依赖完整运行时房间对象。
- 卡牌数据需要逐步收敛到单一真源。

## 5. 分阶段迁移计划

### Phase 0：现状冻结与安全网

产物：

- HTTP、Socket、数据库、房间状态、重连快照和回放格式清单。
- 真实对局、连锁、重连、结算和回放黄金样本。
- 测试分类和当前实际基线。
- 生产配置、启动、健康检查、备份和回滚清单。
- 当前工作树快照和迁移影响范围。

门槛：现有版本可启动；真实人机对局、回放和重连可复现；关键外部契约有固定样本。

### Phase 1：Combat Kernel

先抽出不依赖运行时框架的纯攻击规则：

```text
AttackCommand
  → 输入规范化
  → Combat.resolve()
  → AttackResolved / ShipSunk / MatchFinished
  → LegacyRoomAdapter
  → 现有 Socket、回放、统计和结算
```

覆盖普通攻击、重复攻击、越界、命中、沉船、最后一艘船和强制击杀。旧入口仍负责身份、房间查找、事件发送和持久化。

门槛：新旧状态、事件序列、回放和结算结果一致；领域模块不依赖服务器运行时；可通过开关回退旧实现。

### Phase 2：攻击流程适配

将旧 `handle_attack` 改为适配器，保留旧事件和 payload。运行新旧路径对照，确认后再关闭旧规则实现。

### Phase 3：回合与阶段状态机

统一准备、战斗、连锁等待、结束和交接状态，明确每个状态允许的命令和超时动作。

### Phase 4：卡牌与连锁引擎

将卡牌目标规范化、连锁栈、响应窗口和效果结算迁移到领域/应用层，并保留现有卡牌事件兼容。

### Phase 5：房间、匹配与重连

收敛房间所有权、匹配队列、掉线宽限、重连快照和清理策略，补并发和资源生命周期测试。

### Phase 6：回放、观战、AI 与反作弊

让这些能力读取领域快照或领域事件，移除对完整 `GameRoom` 的直接耦合，并固定可复现 AI 的时钟和随机源。

### Phase 7：数据库与基础设施

先以仓储接口隔离 SQLite，再评估连接、事务、迁移和横向扩展方案。数据库表结构变更必须有迁移和回滚路径。

### Phase 8：前端模块化与生产交付

拆分 Socket 生命周期、客户端状态、页面渲染和卡牌数据；补齐部署、观测、安全检查、发布和回滚流程。确认新路径稳定后清理兼容代码。

## 6. 测试与验收策略

- 领域单元测试：规则、状态转换和不变量。
- 契约测试：HTTP、Socket、重连、回放和公开字段。
- 对照测试：新旧实现的状态、事件和持久化结果。
- 真实流程测试：人机对局、连锁、回放、观战和重连。
- 安全测试：鉴权、输入边界、调试事件和敏感信息泄漏。
- 部署测试：配置检查、健康检查、备份、回滚和进程重启。

每个阶段都必须记录：代码范围、测试命令、实际结果、已知限制、回滚方式和下一阶段入口。

## 7. 交付与协作规则

- 整体重构维护一条长期分支和一条长期 PR 线，作为后续阶段的唯一集成载体。
- Phase 0 完成后创建 PR；Phase 1、Phase 2 及后续阶段继续提交到同一分支并更新同一个 PR。
- 每个阶段完成时只提交代码、测试结果和阶段报告，不将 PR 合并进 `main`。
- PR 描述按阶段追加迁移范围、验收证据、已知限制和回滚方式，保持完整审查上下文。
- 只有用户明确授权时才合并；在最终合并前，`main` 保持不变。
- 不将无关的工作树修改混入重构提交。
- 先完成可验证的垂直切片，再扩大模块边界。
- 合并和部署仍需按项目既有协作流程单独授权。
- 设计文档、迁移记录和验收报告使用简体中文，并引用实际文件和命令证据。

## 8. 第一阶段执行顺序

1. 生成 Phase 0 的契约和状态清单。
2. 固定攻击、结算、回放和重连黄金样本。
3. 建立领域模块的最小包结构和导入边界检查。
4. 实现 `Combat Kernel`，不改变现有 Socket 契约。
5. 接入旧 `handle_attack`，运行新旧对照。
6. 通过 Phase 1 门槛后，再进入回合状态机。

本设计只定义方向和验收边界，不代表上述实现已经完成。
