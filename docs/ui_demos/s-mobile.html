三 条 查 实 的 问 题

① 安全区留白写了但恒为 0 （iOS）
templates/index.html:5 ← 缺 viewport-fit=cover
static/style.css:3665, 3978 ← env(safe-area-inset-bottom, 0px)
没有 viewport-fit=cover 时 env() 返回 0 —— 两处底部留白在带 home indicator 的 iPhone 上**永远不生效**。
改法：meta 加 viewport-fit=cover，并同时补 顶部 的 env(safe-area-inset-top)（否则顶栏会钻到刘海/状态栏下面）——本稿顶栏就是这么写的。
② 手机上牌读不了 （信息不可读）
static/style.css:3831 ← .magic-card { width:64px; height:92px }
64×92 的卡里塞卡名与效果文字，中文实际字号会落到 7–9px。点击目标够大（≥44px），问题在可读性。
改法：手牌小卡只承担"认得出是哪张"（卡名 + 速阶），点开底部抽屉给 200×280 的大卡面（正文 11.5px / 行高 1.6）——本稿第二屏。
③ 手机在"堆两块棋盘"这一档 （竖向预算被棋盘吃光）
static/adaptive_layout.js:135-136
W≥560 → side ；H≥560 → stack ；否则 tabs
390×844 上 W=390<560、H=844≥560 → 判为 stack：两块 364px 棋盘上下堆 = 728px，再加 HUD 与手牌必然超预算，只能靠 layout-tight/dense 往下压。
改法：手机档（宽度 < 560）直接走 tabs——一次一块、格宽 47px（比堆两块时的格还大），省下约 370px 给手牌与抽屉。#board-tabs 与 applyActiveBoard() 都是现成的。

两 条 被 独 立 印 证 的 决 定

① 手机一屏一块棋盘 —— 按实测可用高 763px 反算：两块 6×6（632）+ 手牌（110）+ 顶栏（44）+ 操作（48）= 834 > 763， 放不下；一块（316）时余 245px 给战报/卡牌详情。
② 需要选目标的卡要有确认步 —— Hearthstone 是"松手即生效、无确认"，但它选的是单点目标； 本作 神威！是 3×3 区域、轰炸是整行整列，误触代价大得多，而两款游戏提交后都没有撤销。 Balatro 的做法（先选、再按 Play/Use 确认）才是这一类目标的更安全先例。
另：不需要选目标的卡（失灵！/看破！）沿用"点两次即用"。

仍 为 推 测 的 部 分

调研里查不到、因此标注为推测：各游戏客户端的手牌像素尺寸（官方 wiki 与截图站均不可达，App Store 图是宣传画不是 UI）、 绿/黄/红拇指区的百分比（Hoober 原文只说图表是近似的）、320 宽机型安全区为 0（合理但未验证）、 以及"点开放大"对 CJK 小字的实际收益。
