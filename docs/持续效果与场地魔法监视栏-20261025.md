# 持续效果与场地魔法监视栏 + 三类魔法逻辑修复（2026-10-25）

本轮按「持续效果/场地魔法展示」契约与三类魔法逻辑缺陷处理。写入范围：
`backend/src/battleship/domain/magic/precheck.py`、`backend/src/battleship/services/magic.py`、
`backend/src/battleship/domain/room/sync.py`、`frontend/src/screens/game/EffectMonitor.vue`（新增）、

## 1. 盗亦有道：第一次就生效，不再「打两次」

- 现象（服务层复现）：对手没有可盗记录时，卡片仍然入连锁并扣牌，结算时 `EffectResult(False)`
  走 `_refund` 把卡塞回手牌。玩家看到「打出成功但卡还在」，再打一次才盗到。
- 根因：可在扣牌前判断的条件只写在效果体里，`_resolve_chain` 只能在入链后发现。
- 修法：`domain/magic/precheck.py` 新增 `STEAL_CARD` / `steal_error()`（对手 `magic_history`
  里没有 `stolen != True` 的记录就拒绝），`precheck()` 在扣牌前调用，返回
  「对方还没有使用过魔法卡，盗亦有道无法发动」。
- 证据（`probe_r3.py` R1/R2）：无记录 → `status=error` 且手牌仍 1 张、弃牌堆 0、未开连锁；
  有记录 → 第一次打完手牌只剩盗来的「轰炸」，弃牌堆里「盗亦有道」入堆而「轰炸」被移出（真实转移），
  第二次打出被拒。

## 2/3. 持续效果与场地魔法统一监视栏

- 缺口：`active_effects` 的 `_badges(player)` 只读 `player.effect_flags`（10 个一次性 flags），
  `无暇圣心`「极限增援」这类多回合效果存在 `room.game_effects` 里，场地魔法只有一行纯文本名字。
- 后端载荷：`services/magic.py::_badges(room, player_id, player)` 合并 flags 与
  `LONG_EFFECT_BADGES = (("holy_heart","无暇圣心"),("reinforcement_check","极限增援"))`，
  每块附 `card`（名称/速阶/类型/服务端 `description`）；`active_effects` 增加
  `field`（当前场地卡的同一份 `card` 载荷）与 `field_owner`。`domain/room/sync.py::_effect_badges`
  同步扩展（重连快照与实时帧同构），`RoomSync.effect_badges` 结构不变（仍是 dict 列表）。
- 前端：新增 `EffectMonitor.vue`，占据原 `.field-magic-area` 位置（沿用 `data-testid="game-field-magic"`
  与高度预算），固定高度、`1/2/4` 等分、超出在栏内横向滚动；每块显示真实卡图（`cardArtUrl`）、
  卡名、场地/持续标签与到期信息；hover 出固定层效果预览，点击打开整卡效果弹窗（`Teleport` 固定层，
  不推动棋盘）。`view.ts` 的 `effectBadgeList` 透传 `card`，`battle.ts` 的 `active_effects`
  reducer 透传 `field`/`field_owner`，`gameStateSchema.ts` 补字段。
- 证据（`shots_monitor.mjs`，5482 独立栈 + `ENABLE_TEST_EVENTS=1` 夹具标注）：
  1440×900 / 1920×1080 / 390×740 均 4 区块、每块真实卡图、栏高 56/56/49px、无整页滚动、
  hover 预览与点击弹窗均可达；截图 `dsh/shots/monitor-<尺寸>.png`、`monitor-hover-*`、`monitor-dialog-*`。

## 4. 恶魔契约主动牺牲 → 公开的红色叉叉

- 根因：`_sacrifice_ship` 只把船从 `player.ships` 删掉并同步自家棋盘，没有写进**对手**的
  `attacks`，对手视角那格什么都没有，看起来像船凭空消失。
- 修法：新增 `_publish_sunken_cells()`（把被献祭格以 `hit=True, ship_sunk=True` 写进对手
  `attacks`，去重后 `_emit_board_attacks`），在 `_sacrifice_ship` 计算 `positions` 后立即调用。
- 证据（`probe_r3.py` R3）：牺牲后对手 `attacks` 出现该格、`board_attacks_updated` 向两座位各发一帧、
  己方舰船 5 艘、其它隐藏船格未泄漏。

## 5. 恶魔契约增船：走部署 + 攻击次数

- 现状：`_mirror_contract_gain` 已经会开 `contract_gain` 部署请求；攻击次数由
  `_finish_placement` 的 `_sync_attacks_after_ship_change(room, player_id, placed)` 统一结算，
  逐艘再加会重复计数（本轮先加后删，实测 6 → 8 而不是 7）。
- 结论与证据（`probe_r3.py` R4）：部署请求 `kind=contract_gain`、`caster=己方`；确认后己方 7 艘、
  `attacks_remaining` 6 → 7（`教皇旨意` 0 / `伊甸园` −1 的既有规则不变）。
